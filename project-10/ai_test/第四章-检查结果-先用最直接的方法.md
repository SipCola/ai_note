# 第四章：检查结果——先用最直接的方法

> 这一章只讲一个思路：能直接查清楚的事，就直接查，不必把所有问题都交给另一个 LLM。

## 1. 先找有确定答案的部分

用户让助手把本轮推荐的第二款加购物车，数量一个。本轮第二款是 P102 云帆通勤包，价格和库存都符合要求。

助手回复：“已为你加入云帆通勤包一个。”

怎样检查？先把有确定答案的部分拿出来：选中的商品是不是 P102，数量是不是增加一个，购物车有没有真的变化。

这些问题不需要另一个模型发表意见，程序就能检查。

同样，要求返回指定字段，就检查字段；要求计算总价，就重新算一遍；要求调用某个商品编号，就比对编号。

而“介绍是否清楚”“有没有曲解商品资料”，需要理解意思，适合交给人工或 LLM。

**先把可以直接验证的事实查清楚，再处理需要语义判断的部分。** 这样既简单，也方便解释失败原因。

## 2. 格式能解析，不代表内容正确

为了让应用读取结果，我们可能要求助手输出 JSON：

```json
{
  "product_id": "P102",
  "quantity": 1,
  "status": "added"
}
```

`quantity` 表示本次增加的数量，`added` 表示声称已完成加购。先检查格式和类型，再检查字段值：

```python
import json

raw = '{"product_id":"P102","quantity":1,"status":"added"}'
result = json.loads(raw)

format_ok = (
    isinstance(result, dict)
    and isinstance(result.get("product_id"), str)
    and type(result.get("quantity")) is int
    and isinstance(result.get("status"), str)
)

content_ok = format_ok and (
    result["product_id"] == "P102"
    and result["quantity"] == 1
    and result["status"] == "added"
)

print({"format_ok": format_ok, "content_ok": content_ok})
```

第一项说明结果能否按约定使用，第二项说明结果是否符合本题预期。一个字段齐全的 JSON，仍然可能把商品写成 P101，或把数量写成十个。

这里比对的 P102 来自本题给定的推荐列表。批量评测时，应从各用例的预期中读取，不能永远把“第二款”写死为 P102。

价格、数量这样的业务字段也适合直接比。例如商品接口返回 `price_cents=29900`，用户预算是 `max_price_cents=30000`，程序比较大小就知道当前是否超预算。但程序不会凭空知道预算是多少，这些值都要从本题的用户条件和工具记录中取得。

如果 JSON 无法解析，真实评测程序应捕获错误，记录本题格式失败，然后继续下一题。上面只保留了最核心的检查过程。

## 3. 再看系统里实际发生了什么

就算上面的两个检查都通过，也只能证明助手输出了预期字段，还没证明购物车真的变了。

要看实际状态，可以用一个很小的模拟购物车。下面的 `before` 是操作前保存的快照，`after` 是工具执行后的状态，两者都不是从模型回复里抄来的：

```python
before = {"P101": 1, "P102": 2}
after = {"P101": 1, "P102": 3}

selected_id = "P102"  # 本题预期选中的商品
expected_cart = before.copy()
expected_cart[selected_id] = before.get(selected_id, 0) + 1

state_ok = after == expected_cart
print({"state_ok": state_ok})
```

这个检查同时验证两件事：P102 从两个变成三个，其他商品不变。如果把 `after` 中的 P102 改成两个，说明没加成；改成一个，说明把增量误当成总量；改成四个，可能发生了重复加购。

如果偷偷多加了别的商品，或者删掉了原来的 P101，比较整个购物车也能发现。只检查 P102，就会漏掉这些变化。

同一请求重试的测试也沿用这个思路：先保存初始快照，使用同一个 `request_id` 调用两次，再检查最终只增加一个。这里检查的是实际效果，不能因为调用两次就直接认定多加了，也不能因为工具说成功就认定数量正确。

状态检查需要独立的事实来源。模拟状态由工具维护；真实项目则查询对应业务系统。拿模型输出证明模型输出，仍然没有增加证据。

加购接口明确失败的题，预期则不同：购物车应和操作前完全相同。不能把上面“增加一个”的规则原封不动套过去。检查函数可以复用，输入的预期要跟着题目走。这也解释了为什么前面要先写标准、再写检查代码。

## 4. 别把容易检查的东西当成真正目标

一个常见的省事办法，是检查回复里有没有“加入成功”。

但“加入成功”和“暂时无法确认是否加入成功”都包含这几个字，意思却不同。回复里出现了 P102，也不能证明加进购物车的就是 P102。

所以，关键词只能说明文字有没有出现，不能代替事实检查。

自然语言也不宜整句比对。“云帆通勤包已加入购物车”和“已加购云帆通勤包一个”可能表达同一件事，没必要因为措辞不同就判错。

起步时，把检查拆开记录就够了：格式是否通过、选中商品是否正确、数量变化是否正确、回复是否符合实际。这样看到失败，你就知道该先查哪一层。

开始时不必设计精细分数。有明确标准的项目，用通过或不通过就很清楚。如果十道题有八道完成，可以汇总成功率；但那两道失败的记录仍要保留。一个比例能帮助比较版本，具体的失败证据才告诉我们下一步该改哪里。

还要记住完成程度：购物车加购成功，不等于已经下单，也不等于已经支付。程序能检查状态，回答有没有夸大这个状态，则需要理解语义。

假如字段和购物车都正确，回答却说“已经支付完成”，前面的程序检查依然可能通过。这不矛盾，因为每个检查只负责一部分要求。我们要把它们合起来看，不能把某一项通过，当作整个任务都没有问题。

下一章就来处理这类判断：当不能简单比字段时，怎样让 LLM 帮忙评分，又怎样检查它有没有判错。
