# 第三章：准备考题——怎么建立评测集

> 这一章只讲一个思路：准备一批有代表性的任务，让我们知道助手在哪些情况下能做好，在哪些情况下容易出错。

## 1. 一道题做对，不代表整个系统可靠

上一章，我们写清了一个任务：用户让助手把推荐列表中的第二款加入购物车，助手正确选中 P102，数量增加一个。

但做对这一题，只能说明这一种情况处理好了。商品突然涨价呢？用户说“第二款”，前面却没有推荐列表呢？加购接口失败呢？

这些情况都可能发生，不能靠一条正常用例推断表现。

所以，要准备一批不同任务。这批任务就是**评测集**，可以把它理解成给助手做的一套考卷。

把题固定下来，还有一个直接好处：方便比较。修改前后都做同一批题，我们才能看出哪里变好、哪里变差。如果每次临时换题，成绩变化也可能只是题目难度变了。

## 2. 从一个真实任务，逐步补上变化

最好的起点，是用户实际会说的话。

我们的模拟项目可以先从“300 元以内推荐两款通勤包”开始，再测试“把第二款加购物车”。接着改变一个条件，看看助手是否还能正确处理。

| 情况 | 题目怎么变 | 想看什么 |
| --- | --- | --- |
| 正常推荐 | 两款都满足尺寸、预算和现货要求 | 能否找对商品、说清依据 |
| 正常加购 | 列表第二款是 P102，价格 299 元且有货 | 能否选对商品并加一个 |
| 商品超预算 | 选中的 P102 现价变成 349 元 | 能否发现变化并确认 |
| 缺少上下文 | 用户直接说“把第二款加购物车” | 会不会先问清楚 |
| 商品缺货 | 资料还在，接口显示当前无货 | 会不会照旧执行 |
| 接口失败 | 加购接口明确返回失败 | 会不会谎称成功 |
| 已有数量 | 购物车里已经有 P102 两个 | 能否正确增加到三个 |

这里最重要的是**覆盖不同情况**。把“加购物车”改写成二十种说法，主要测的是表达变化；它不能代替价格、库存、上下文、工具状态这些变化。

还可以把推荐顺序调换一次，防止助手把“第二款”死记成 P102。预算刚好 300 元和略高于 300 元，也适合拿来检查边界。

起步时，先准备十几道自己能判断清楚的题。每道题有明确用途，比先生成几百道没人核对的题更有价值。

## 3. 一条用例，要有输入、背景和预期

评测文件里只有“把第二款加购物车”还不够。我们不知道第二款是谁，也不知道当前价格、库存和购物车情况。

一条可用的题，至少记清三件事：

- **输入：**用户说了什么，必要时保留前面的对话。
- **背景：**商品、工具和购物车的初始状态。
- **预期：**在这些条件下，助手应该做到什么。

例如：

```text
编号：shopping_005

输入：
前文依次展示 P101 轻行通勤包、P102 云帆通勤包。
用户说：“把第二款加购物车，数量一个。”

背景：
用户预算 300 元以内。
get_product 查询 P102，返回价格 299 元、库存充足。
当前用户购物车已有 P102 两个，另有 P101 一个。
加购接口正常。

预期：
P102 变成三个，P101 仍是一个。
回复与操作结果一致。

检查：
核对商品编号、调用参数、购物车变化和最终回答。
```

实现时，可以把它保存为 JSON，用 `input`、`world`、`expected` 分别记录输入、模拟背景和预期。金额用整数分表示，例如 `price_cents=29900`，预算是 `max_price_cents=30000`，避免金额比较时的浮点误差。

注意，业务背景要通过对话或模拟工具提供给助手；“P102 应变成三个”属于评测程序掌握的答案，不能作为提示直接告诉助手。否则考的就不是它能否完成任务，而是能否照着答案做。

每次独立运行，也要恢复相同的初始状态。如果第一遍从两个加到三个，第二遍却从三个开始，面对的条件已经变了。

教学时把商品信息和工具返回值固定下来，就能稳定复现。今天 299 元，明天真的涨到 349 元，如果测试仍沿用原来的预期，就容易把环境变化误认为助手退步。因此，先在可控的模拟环境练习，等检查思路清楚以后，再考虑接入持续变化的实际数据。

## 4. 把真实犯过的错留下来

最值得保留的题，往往来自助手实际犯过的错。

例如，它把“加一个”理解成“总数设为一个”。修好以后，就留下“已有两个，再加一个”这道题。以后换模型、改提示词，都再跑一下，检查老问题有没有回来。

这就是回归检查：**已经解决的问题，不能因为后面的改动重新出现。**

同时，留一小批题，平时不要反复拿来调试，等版本改完再验收。因为我们每天盯着同几道题修改，可能只是越来越适合这些熟题，并没有学会应付同类新情况。

评测集可以随着项目慢慢长大：先有正常任务，再补边界和异常；发现一次有代表性的失败，就整理成一条题。

维护时也问自己：这道题在检查什么？失败后能说明什么？如果只剩下一句含糊提问，或者连预期都说不清，就先把它整理好。
