# 第二章：先定标准——什么才算做好

> 这一章只讲一个思路：先弄清用户想办成什么，再确定怎样算完成，最后想好拿什么证据检查。

## 1. 标准从用户的目标出发

继续用电商导购助手。用户先说：

> 预算 300 元以内，推荐两款通勤双肩包，要能装 15.6 英寸电脑，而且有现货。

这一步的目标是找到合适商品。助手需要给出两款符合条件的商品，并根据真实资料介绍它们。

假设它依次展示：

1. P101 轻行通勤包，259 元。
2. P102 云帆通勤包，299 元。

两款商品都支持 15.6 英寸电脑、防泼水，当前都有货。用户接着说：

> 把第二款加购物车，数量一个。

目标就变了：把本轮列表中的第二款 P102，正确地加入当前登录用户的购物车。

不能只检查商品推荐得好不好，因为用户还要求实际操作。也不能因为用户想看推荐，就提前把商品加进购物车。

所以，定标准的第一步很简单：**这次用户到底要问清楚一件事，还是要办成一件事？**

## 2. 把目标变成几件能检查的事

“推荐准确”“加购合理”太笼统。继续往下问，就能变成具体标准：

| 阶段 | 怎样算做好 |
| --- | --- |
| 推荐 | 两款商品都满足预算、尺寸和现货要求，介绍有资料依据 |
| 选择 | “第二款”能对应本轮推荐列表中的正确商品 |
| 加购 | 选中商品的数量增加一个，其他商品保持不变 |
| 回复 | 如实说明结果，只完成加购就不能说已下单或支付 |

这里有几个细节，提前讲清楚，后面评测才不会各说各话。

300 元以内，包括 300 元；“数量一个”在本教程里表示增加一个，如果购物车原有两个，操作后应有三个。同一请求因超时而重试，仍然只能增加一次。

“第二款”也不是永远等于 P102。它来自当时的推荐顺序；这一轮 P102 排第二，才能选中它。没有前面的列表，就应先确认，不能猜一个编号去操作。

本例还保留了用户的预算条件。如果选中商品加购前涨到 349 元，助手应说明变化，先确认用户是否接受。本次任务不能直接当成正常加购完成。

**标准要抓住决定成败的事实。** 推荐超预算、选错商品，不能被漂亮介绍或友好语气抵消。

反过来，也别把所有偏好都当成成败标准。商品条件全部满足，介绍稍微长一点，通常只是体验问题；商品已经缺货，却仍推荐用户立即购买，才是这道题要重点抓的问题。先把这些轻重关系想清楚，比做一个复杂的加权总分更有帮助。

## 3. 每项要求，都要想好拿什么证明

有了标准，再问一句：我看到什么，才能知道它做到了？

商品能装多大的电脑，可以查商品知识库；当前价格和库存，要查业务接口 `get_product`。这两类信息更新速度不同，不能只因为旧文档写着“299 元、有货”，就认定现在仍然如此。

要检查选中了谁，就对照推荐列表和调用参数；要检查加购是否成功，就看工具执行后的购物车。不能只看模型自己输出的“成功”。

| 要求 | 主要证据 |
| --- | --- |
| 尺寸和卖点准确 | 召回的商品资料、最终介绍 |
| 满足当前价格和库存条件 | `get_product` 返回值 |
| 加对商品和数量 | `add_to_cart` 参数、购物车前后状态 |
| 回复符合实际 | 操作结果、最终回答 |

工具接口可以很简单：`add_to_cart(product_id, quantity, request_id)`。它操作当前登录用户的购物车，`quantity=1` 表示这次增加一个，`request_id` 用来识别重复请求。

我们并不需要所有要求都用同一种方式评分。商品编号、数量变化，程序能直接比；介绍有没有夸大“防泼水”，需要读懂资料和回答，可以人工看，也可以请 LLM 判断。

在后续评测中，选择检查方法，要从需要的证据出发。

假如工具明确返回失败，购物车也没变化，那么“没有完成加购”就是实际结果。助手如实告知失败，说明它没有编造，但不能因此说加购任务成功了。可以分别记录“任务未完成、回复真实”，这样才能看出失败来自外部服务，还是来自助手对结果的误解。

同理，检查标准不能只留一句“全部通过”。保留几项清楚的判断，后面才有办法针对问题改进。

## 4. 写到能判断，就可以开始

标准不用写成大段条款，也不必规定唯一措辞。

“已加入云帆通勤包一个”和“云帆通勤包已加入购物车，数量增加一个”，只要事实相同，都可以。我们要判断的是意思是否正确，不是是否复述了参考答案。

起步时，把一条任务写成下面这样就够了：

```text
任务：把前面推荐的第二款加入购物车，数量一个。

背景：本轮第二款是 P102，现价 299 元且有货。
      用户预算 300 元以内，购物车原有 P102 两个。

预期：P102 变成三个，其他商品不变，如实告知加购完成。

检查：对话列表、商品接口、加购调用、购物车状态和回复。
```

这份记录已经把目标、标准和证据连了起来。

如果系统没有通过，我们也更容易找到问题：认错“第二款”，看上下文理解；数量错了，看工具调用；购物车没变却说成功，看执行结果和回复是否脱节。

下一章，我们把这样的记录变成一批考题，看看应该选哪些情况，才能考出系统真实的能力。
