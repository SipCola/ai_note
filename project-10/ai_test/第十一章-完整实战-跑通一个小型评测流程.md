# 第十一章：完整实战——跑通一个小型评测流程

> 这一章只做一件事：把“准备题目、执行、检查、留证、比较”真正串起来。

## 1. 从用户选定商品之后开始

贯穿教程的任务是：用户预算 300 元，找能装 15.6 英寸电脑、有现货的通勤双肩包。助手介绍两款虚构商品：

```text
第一款：P101 轻行通勤包，259 元。
第二款：P102 云帆通勤包，299 元。
```

用户接着说：“把第二款加入购物车，数量一个。”

本章先把这个后半段跑通：根据本次展示列表确定商品，检查当前价格和库存，再执行加购。

示例文件在 [examples/shopping_eval](./examples/shopping_eval/README.md)，只用 Python 标准库：

| 文件 | 做什么 |
| --- | --- |
| `cases.json` | 六道题的输入、模拟背景和预期 |
| `run_eval.py` | 运行模拟助手、执行工具并检查 |
| `report_baseline.json` | 修改前的运行记录 |
| `report_fixed.json` | 修改后的运行记录 |

助手由普通分支逻辑模拟，不调用真实 LLM。候选列表、用户选择的位置和预算已经整理成字段，所以本例主要演示选购后的加购检查。真实的商品检索、自然语言理解和推荐质量，需要另行评测。

## 2. 一道题怎样跑起来

每道题都使用一份独立数据：

```text
读取用户输入和模拟背景
    ↓
助手确定选中商品，查询当前价格和库存
    ↓
符合用户要求时调用加购工具
    ↓
保存调用记录和购物车状态
    ↓
拿预期检查，再继续下一题
```

两个工具分别是：

- `get_product(product_id)`：查询当前价格和库存。
- `add_to_cart(product_id, quantity, request_id)`：向当前用户购物车增加指定数量。

知识库中的商品介绍可以用于推荐，但加购前不能只凭旧价格、旧库存。这里由模拟查询接口提供当前数据。

用户选择第二款，代码会去读本次列表的第二项，并没有把“第二款”永远写死成 P102。如果展示顺序换了，选中的商品也要跟着变。

检查函数会核对选中商品、回复状态、购物车最终数量、其他商品是否被误改，以及调用前是否有价格库存依据。还会把成功调用对应的数量变化和实际购物车对照，避免只看回复。

一个细节很重要：用户说“再加一个”，指的是数量增加一个。原来有两个，执行后应该是三个。不能每次都把数量设成一，也不能把已有商品一律当成不允许再次操作。

## 3. 留一个错误，再用同一批题验证修复

六道题分别检查：

```text
正常加购
选中商品涨到 349 元，超过预算
缺少候选列表，无法知道“第二款”是谁
加购接口明确失败
购物车已有两个，再加一个
选中商品已经缺货
```

初始版本留了一个错误：调用加购工具后，不检查结果，直接告诉用户已经加入。

在项目目录运行：

```powershell
python examples/shopping_eval/run_eval.py --version baseline
```

结果是：

```text
shopping_001: PASS
shopping_002: PASS
shopping_003: PASS
shopping_004: FAIL | response_status, reported_addition_confirmed
shopping_005: PASS
shopping_006: PASS
规则检查通过：5/6 (83.3%)
```

打开 `shopping_004` 的报告，可以看到工具明确返回失败、购物车没有变化，助手却说已加入。

修正版本补上对工具结果的判断，再运行：

```powershell
python examples/shopping_eval/run_eval.py --version fixed
```

规则检查变成 `6/6`。失败那道题中，助手会如实说明本次未加入购物车。它通过的是异常处理要求，不表示商品已经加进去了。

每份报告都保存 `trace`、回复、`cart_before`、`cart_after` 和各项检查结果。同一道题前后对照，就能看到改了什么、为什么通过。

## 4. 再接入真实模型和前半段推荐

读代码时，先找三个位置：

```text
run_agent：被测助手怎样执行任务。
grade：怎样判断是否符合预期。
main：怎样逐题运行并保存报告。
```

接真实 Agent 时，主要替换执行部分：把对话和候选列表交给模型，通过同一工具层执行，并返回约定的结构化结果。实际购物车状态仍由工具层维护，不能拿模型自己写的 JSON 充当购物车记录。

代码中的请求 ID 用来识别同一次加购。因为网络问题重试时，后端返回原结果，不再增加数量；用户后来明确要求再加一个，则是新的操作，需要新的请求 ID。

当前脚本没有制造“加购成功但响应超时”的故障，这部分可按第八章继续补题。

前半段推荐则按第六章单独检查：商品资料是否找对，尺寸是否符合要求，再结合实时价格和库存筛选。回复语义按第五章复核，例如不能把“防泼水”夸成“完全防水”。

因此，报告里的 `semantic_review` 仍为 `pending`。六道题全过，只说明这批模拟题满足了已有规则，不能证明真实模型的推荐和表达也都可靠。模拟程序的本地耗时，也不代表模型调用延迟。
