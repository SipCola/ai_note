# 第六章：评测 RAG——有没有找对资料、用对资料

> 这一章只讲一个思路：把找资料、筛商品和生成回答分开，出错时才能知道该改哪里。

## 1. 找到资料，只完成了第一步

RAG 可以先理解为：回答之前，先去知识库找资料，再把资料交给模型。

用户要两款 300 元以内、能装 15.6 英寸电脑、而且有货的通勤包。知识库能告诉我们商品的电脑仓尺寸和防泼水等卖点，但当前价格、库存要查 `get_product`。

这条链路可以拆成：

```text
检索商品说明
→ 查询当前价格和库存
→ 筛选并排列候选商品
→ 把需要的证据交给模型
→ 生成用户看到的回答
```

某款包没有被推荐，可能是说明没找到，也可能是查到已经缺货。两者不能都叫“召回失败”。

还有一种情况：检索到了 P102，但组装上下文时把它截掉了，模型根本没看见。这时调整回答提示词，通常解决不了资料缺失。

所以，评测要保留检索结果和顺序、实时接口结果、实际进入模型的上下文、用户看到的候选列表，以及最终回答。每个阶段分别看一眼，问题就清楚得多。

## 2. 先约定“相关资料”是什么意思

算指标之前，先说清本节的口径：**我们检查知识库能否找回明确支持 15.6 英寸电脑的通勤包说明。** 当前价格和库存另查，不混进这一步的静态相关性标注。

假设固定知识库只有下面五份商品说明，一款对应一份：

| 商品说明 | 本节是否标为相关 | 原因 |
| --- | --- | --- |
| P101 轻行通勤包 | 是 | 支持 15.6 英寸电脑 |
| P102 云帆通勤包 | 是 | 支持 15.6 英寸电脑 |
| P103 远途商务包 | 是 | 支持 15.6 英寸电脑 |
| P104 轻巧日用包 | 否 | 只支持 13.3 英寸电脑 |
| P105 城市通勤包 | 是 | 支持 15.6 英寸电脑 |

这里相关集合已经完整标出，共四份。P103 可能超预算，P105 可能缺货，但它们的尺寸说明仍符合本节的检索口径。

取前三条，也就是 K = 3。假设检索结果为：

```text
P104、P101、P102
```

前三条有两份相关资料，因此：

```text
Precision@3 = 前三条相关数量 / 3 = 2/3
Recall@3 = 前三条相关数量 / 全部相关数量 = 2/4
```

Precision 看“找回来的有多少有用”，Recall 看“该找到的有多少找到了”。

修改后结果变成 `P101、P102、P105`，则 Precision@3 为 3/3，Recall@3 为 3/4。召回改善了，但不能直接宣布最终推荐正确，因为 P105 还要过库存这一关。

这个例子按固定商品说明编号计数，重复返回同一份说明不会增加命中。真实项目也要先定资料粒度和相关性口径。如果只标出了部分有用资料，完整分母未知，就不能声称得到了精确的 Recall。

比较两个检索版本时，使用同一份知识库和同一组相关性标注。否则，分数变化可能只是资料变多了。价格、库存可以另准备一份固定的模拟快照，让筛选阶段的前后对比也有共同起点。

## 3. 资料找到以后，再看筛选和排序

拿到候选说明后，调用实时接口。我们这批虚构商品的当前情况是：

```text
P101：259 元，有货
P102：299 元，有货
P103：399 元，有货
P105：缺货
```

因此，P103 因价格超出预算被排除，P105 因缺货被排除。最终向用户展示：

```text
第一款：P101 轻行通勤包
第二款：P102 云帆通勤包
```

这时评测的问题是：筛选是否使用了实时价格和库存，排除理由是否正确，展示顺序是否保存了下来。

为什么要保存顺序？因为用户下一句可能是“把第二款加入购物车”。这里的第二款来自用户刚看到的列表，本次是 P102，不能拿检索系统内部的第二条代替。

检索结果里的排序也值得单独检查。关键资料虽然找到了，如果排得太后，可能在截断时丢失。起步不用急着学习复杂排序公式，先看关键资料是否排在前面、最终是否进入上下文，就能发现不少问题。

注意区分三份东西：检索候选、传给模型的资料、展示给用户的商品列表。它们可能不同，评测时不能互相冒充。

## 4. 最后检查，回答有没有把资料说变样

假设 P101、P102 的资料和实时信息都准备好了，助手却说：

> 两款都完全防水，任何 15.6 英寸电脑都保证装得下。

知识库只写支持 15.6 英寸电脑、防泼水，这段回答增加了没有依据的保证。

检查方法可以很直接：把回答拆成主要事实，逐条找证据。“259 元”对照实时接口；“支持 15.6 英寸”对照商品说明；“完全防水”找不到支持，就标出来。

这叫检查忠实性，也就是回答是否忠于给它的资料。可以人工看，也可以让上一章的 LLM 裁判辅助逐条对照。

但忠实不等于当前正确。旧文档写 P102 售价 279 元，模型照着说，可能忠于旧文档，却不符合接口显示的当前 299 元。评测还要检查资料来源是否适合这个事实：尺寸卖点看商品说明，当前价格和库存看实时接口。

反过来，模型碰巧猜中了价格，也不说明链路可靠。下一次价格变化，猜测就可能失效。

一条最终回答错了，沿着这条线查即可：资料有没有找到，动态条件有没有核验，候选有没有筛对，证据有没有交给模型，回答有没有曲解证据。我们需要的是找到故障发生的位置，而不只是得到一个“RAG 分数”。
