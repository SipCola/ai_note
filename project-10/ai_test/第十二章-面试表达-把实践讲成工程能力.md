# 第十二章：面试表达——把实践讲成工程能力

> 这一章只讲一个思路：讲清楚你怎样判断系统好坏、怎样发现和修复问题，比堆指标名更能体现工程能力。

## 1. 先说清自己实际做到了哪一步

面试时，围绕一个具体任务讲，会容易理解得多。

比如：“用户要在 300 元以内选一个能装 15.6 英寸电脑的通勤包，看到推荐后，让助手把第二款加入购物车。”接着解释，你怎样知道推荐符合要求、选的是正确商品、购物车真的增加了一个。

听的人就能顺着业务理解设计，不需要先记一堆术语。这里的任务终点是加购；购物车变化，不能说成已经下单或支付成功。

同时，表达要和实际工作对应。第十一章用的是虚构商品、模拟工具和模拟助手。候选列表、用户选择的位置等输入已经整理好，没有调用真实 LLM，也没有测试真实自然语言理解或实际检索质量。

所以，可以说“我做了一个可运行的离线评测演示，跑通了检查与回归流程”；不能据此说“我把生产模型的成功率提高到了某个水平”。模拟脚本的结果，只能说明它在给定用例和规则下的表现。

有真实项目经历，就补充实际数据和自己的工作范围。没有，就说清演示范围，再说明接真实 Agent 后需要补测什么。这同样能体现工程判断。

## 2. 用一分钟讲清整体思路

下面这段可以作为参考，按自己实际完成的内容调整：

> 我的评测思路，是先定义任务怎样才算完成，再选择检查方法。比如电商导购和购物车助手，推荐要符合预算、尺寸和库存要求；用户说加第二款时，还要确认商品对应正确，并检查购物车确实增加了一个。
>
> 我会准备一批固定用例，覆盖正常推荐、筛选条件、多轮选择和工具异常。商品编号、当前价格、调用参数、购物车数量这类能直接核对的内容，用程序检查；商品介绍是否有资料依据，再结合人工或 LLM 判断。
>
> 失败后沿检索、实际输入、工具调用和最终状态定位。修改后，在相同条件下回跑，既看问题有没有修好，也看其他类型是否退步。
>
> 目前我用模拟数据跑通了这套流程。接真实 Agent 后，还要补测自然语言理解、真实检索和重复运行的稳定性。

这一分钟回答了四件事：评什么、怎么评、如何查错、做到哪一步。面试官对哪部分感兴趣，再展开。

## 3. 用一个问题讲三到五分钟

需要深入时，可以围绕“加购失败却回复成功”展开。下面是叙事提纲，不需要背成长稿。

**先讲任务和成功标准。** 展示列表第二款是 P102 云帆通勤包，价格 299 元，符合用户预算和尺寸要求，也有库存。用户要求加 1 个。成功意味着当前用户的购物车新增 1 个 P102，并且回复符合实际结果。

**再讲怎样发现问题。** 把加购工具设置为明确返回失败。运行后，工具响应和购物车都表明没有加成，助手却说已加入。展示输入、响应、状态和回答，比只展示一个失败分数更直观。

**接着讲如何缩小范围。** 核对候选列表、当前价格库存和请求参数，发现都正确，因此重点检查工具结果如何影响回复。这是定位线索，还不能从一次运行就断言真实模型的根因。

**然后讲改动和验证。** 教程里只改模拟助手处理明确失败的回复逻辑，其他行为保持一致。按同样的 6 道题回跑，规则检查从 5/6 变为 6/6；同时保留语义复核为待处理，不能据此宣称回答质量已经全面通过。

**最后讲结论范围。** 这证明模拟脚本中的目标错误被修复，检查流程能够发现它。真实 LLM 是否能理解“第二款”、检索是否可靠、重复运行是否稳定，都需要接入后继续测。修过的问题保留下来，作为以后每次改版的回归题。

面试需要数字时，只使用自己保存的报告。没有测过的指标，不要补一个“看起来合理”的百分比。

## 4. 五个高频追问怎么回答

**问：LLM 当裁判，你怎么相信它？**

答：先明确它要判断什么，并给商品资料、用户要求和实际结果。用人工核对过的样本检查它会不会误判，再抽查评分理由。商品编号、价格、库存和购物车数量可以直接核对，我会用程序检查。LLM 裁判也需要校准，不能把它的分数直接当事实。

**问：评测集是怎么来的？**

答：有真实业务时，从实际问题和失败记录整理；没有时，先按业务流程设计模拟题并标清来源。每题写清输入、背景和预期，覆盖预算变化、缺货、选择不明确、接口失败等情况，再留一些不常用于调试的题做验收。

**问：结果正确，为什么还要看过程？**

答：结果正确，仍可能有多加商品、替用户换商品等问题。比如用户只想加 1 个，网络重试却加了 2 个，不能因为目标商品出现在购物车就判成功。我检查必要步骤和约束，不要求所有任务走完全相同的调用序列。

**问：你怎么证明修改有提升？**

答：固定用例、环境和评分标准，让前后版本从相同初始状态运行。有随机性就重复测。除了总分，还看各类任务和失败记录，确认目标问题改善，其他能力没有明显退步。结论只覆盖本次实际测试的范围。

**问：最小怎么落地，要用什么框架？**

答：一个用例文件、一个运行脚本和几个检查函数就能开始。第十一章的 `examples/shopping_eval/run_eval.py` 展示了这种做法，保存工具记录与购物车状态供复核。接真实 Agent 时替换执行部分，再补真实输入、检索测试和语义评分。框架方便管理规模，业务标准和检查证据仍然要自己想清楚。
