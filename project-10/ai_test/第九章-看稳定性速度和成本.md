# 第九章：看稳定性、速度和成本

> 这一章只讲一个思路：除了看能不能做对，还要看做得是否稳定，以及完成任务需要多少时间和资源。

## 1. 先看有多少题达到了预期

假设我们准备了 20 道电商助手测试题，逐条检查后有 16 道通过，通过率就是 80%。

计算很简单：通过的次数，除以评测的总次数。但只看这个总数，容易忽略问题集中在哪。下面的数字都是**假设数据，只用于说明分析方法**：

| 用例类型 | 通过数 / 总数 |
| --- | --- |
| 正常推荐 | 7 / 8 |
| 预算、尺寸、现货等筛选条件 | 4 / 4 |
| 多轮选择并加购 | 4 / 5 |
| 加购接口异常 | 1 / 3 |
| 合计 | 16 / 20 |

这张表说明，接口异常是当前的明显短板。下一步应该打开这几条失败记录，看看是不是把失败说成成功，而不是继续打磨商品介绍的措辞。

这里还有一个容易混淆的地方：**用例通过，不等于商品已经加入购物车。**

一道题故意让接口返回加购失败，预期就是“购物车不变，并如实告诉用户未成功”。助手这样处理，可以判这道异常题通过；但不能把它算成一次成功加购。

因此，报告里把“满足用例预期的比例”和“实际加购成功的比例”分开写，并说明各自统计哪些任务。前者看各种情况是否处理得当，后者看真正有多少加购任务完成了。

报数字时带上范围：“这批 20 条模拟用例通过 16 条”，比笼统地说“系统准确率 80%”更清楚。小样本适合帮助找问题，还不能代表所有真实用户的表现。

## 2. 同一道题多跑几次，检查是否稳定

LLM 应用有时会出现这样的情况：同一个任务，这次选对商品，下次却把“第二款”对应到了另一件商品。

因此，除了增加不同的题，还可以把同一道题独立运行几次。

比如，候选列表依次是 P101 轻行通勤包和 P102 云帆通勤包。用户说“把第二款加入购物车，数量一个”。相同条件下跑 5 次，4 次加入 P102，1 次加入 P101，说明这道任务的表现不够稳定。

增加不同的题，主要看情况覆盖得够不够；重复同一道题，主要看相同条件下结果是否可靠。一道题跑 100 次，仍然没有检查缺货、价格变化、候选列表丢失等情况。

重复运行时，需要固定模型、提示词、工具和数据版本，也要恢复相同的初始状态。假如最初购物车里已有 2 个 P102，每次测试都从 2 个开始，正确加 1 后应该变成 3 个。不能让上次运行留下的数量影响下次结果。

还要区分两种重试：独立测试每次是一个新任务；同一次加购请求因网络问题重试，则应沿用同一请求标识，避免多加。把这两件事混在一起，测出来的数量就不好解释。

起步时使用固定的模拟工具，更容易看清助手本身的问题。接真实服务后，再记录网络、服务状态等环境变化。

## 3. 在质量满足要求后，再比较效率

两个助手都能正确完成任务时，我们才更关心谁更快、谁更省。

最容易开始记录的几项是：

```text
从收到任务到结束的总耗时
整次任务的模型 Token 用量
工具调用次数
整次任务的费用
```

统计要覆盖完整执行。失败调用、重试、重复查询也消耗资源，不能只算最后成功的那一步。一个 Agent 多次调用 LLM，就把这些调用的用量加起来。

耗时的起止点也要一致。例如，从收到“把第二款加入购物车”开始，到返回最终答复结束。如果中间要等用户补充选择，用户思考的时间可以单独记录，避免和系统处理时间混在一起。

费用按照实际使用的服务和计费方式计算。教学时也可以用虚构费用，例如版本 A 完成一次任务花 0.02 元，版本 B 花 0.03 元；这只是演示计算方法，不是真实产品报价。LLM 裁判的费用属于评测开销，和助手处理任务的费用分开记录。

少调用一次工具，也不一定是优化。省掉实时价格查询后，助手可能把已经涨到 349 元的商品按旧价推荐给预算 300 元的用户。虽然变快了，却没有满足任务要求。

## 4. 用一致的条件比较两个版本

版本 A 平均耗时 4 秒，版本 B 平均耗时 3 秒，能直接说 B 更好吗？

先看它们是否使用同一批题、相同运行次数和初始数据。候选顺序、当前价格、库存和购物车数量都可能影响结果。一个版本面对有货商品，另一个版本面对缺货商品，就很难公平比较。

把模型、提示词、工具配置、重试次数和运行预算记下来，结果才容易复查。如果这次就是要调整重试策略，也可以，但要说明比较的是整套方案，不能把变化都归因于某一句提示词。

速度除了看平均值，也要看看最慢的几次。平均 3 秒，仍可能有少数任务等待很久。P95 可以粗略理解为：把耗时排好，大约 95% 的执行在这个时间内结束。样本很少时，先看原始耗时和慢案例，不必急着追求一个漂亮的统计数。

一份简单报告能说清哪些题容易失败、重复运行是否稳定、完成一次要多久和花多少，就已经有用了。每个数字后面保留对应记录，才知道下一步该改哪里。
