# 第七章：评测 Agent——工具有没有用对，事情有没有做成

> 这一章只讲一个思路：把用户意图、实际调用和最终状态放在一起看。

## 1. 会说“已加入”，不代表真的加进去了

用户先要求推荐两款 300 元以内、能装 15.6 英寸电脑、而且有货的通勤包。助手依次展示：

```text
第一款：P101 轻行通勤包，259 元
第二款：P102 云帆通勤包，299 元
```

用户接着说：

> 把第二款加入购物车，数量一个。

正确目标是给当前登录用户的购物车增加一个 P102。这里“第二款”来自用户刚看到的展示列表，不能靠商品名称猜，也不能照着另一份候选列表取第二条。

助手回复“已加入购物车”，背后可能有好几种情况：没有调用工具；调用了工具但商品编号错误；接口明确失败，却仍然说成功。

所以评测需要连起来看：

```text
用户当前要什么 → Agent 调用了什么 → 购物车实际变成什么样
```

执行记录帮助我们解释问题，业务状态帮助我们确认事情有没有完成。[Anthropic Agent 评测说明](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)也讨论了执行轨迹与实际结果的区别。

本例到加入购物车为止。加购成功不能说成已经下单，更不能说已经付款。

## 2. 留下一份简单的调用记录

不用先接复杂平台。记录工具名称、参数、返回结果，就能开始检查。

假设此前的商品资料已经确认 P102 支持 15.6 英寸电脑，本次初始购物车中 P102 数量为 0。执行记录可以是：

```json
[
  {
    "tool": "get_product",
    "args": {"product_id": "P102"},
    "result": {"ok": true, "price_cents": 29900, "stock": 5}
  },
  {
    "tool": "add_to_cart",
    "args": {
      "product_id": "P102",
      "quantity": 1,
      "request_id": "cart_add_demo_001"
    },
    "result": {"ok": true, "cart_quantity": 1}
  }
]
```

这份记录可以叫 `trace`。金额按分记录，299 元就是 `29900`。加购接口操作当前登录用户的购物车，`quantity: 1` 表示本次增加一个。

拿到记录，就可以逐项核对：第二款是否映射到 P102；加购前查到的价格是否仍在预算内；是否有货；传给工具的数量是不是一个；返回失败时有没有被误读。

调用结束后，再由评测程序读取模拟购物车。初始是 0，本次成功增加 1，最终应为 1。工具返回与实际状态也要一致，不能只看到调用名称就算成功。

如果初始已经有两个 P102，本次增加一个，最终应为三个。评测应检查“数量增加了一个”，不能永远要求最终数量等于一。初始状态不同，预期结果也要跟着变。

我们记录的是可观察证据：对话、展示列表、检索资料、工具调用和实际状态。无需模型提供隐藏的思维过程；它写一篇理由，也不能代替真实调用记录。

批量运行时，再给整次测试一个用例编号，把这些记录放在一起。否则，同一道题跑了多次，很容易误把上一次的商品查询和这一次的加购拼在一起。记录的目的，是让别人能还原这一次实际发生了什么。

## 3. 检查必要条件，不必规定唯一走法

假设某次助手先查 P101，再查 P102；另一次先查 P102，再查 P101。两次都确认了当前价格库存，推荐和加购也正确，没有必要仅因查询顺序不同就判错。

更值得检查的是这些关系：

- 选中的商品来自当前展示列表，符合用户的选择。
- 加购前已有商品尺寸依据，并确认实时价格和库存满足需求。
- 加购使用正确的商品编号和数量，写入当前用户的购物车。
- 最终回复与已确认的操作结果一致。

这里约束的是完成任务需要具备的证据与行为，而不是要求所有 Agent 走同一条路线。

如果没查当前价格，只凭旧介绍就加购，即使这一回价格碰巧没变，也存在过程问题。下次 P102 涨到 349 元，就可能违背用户预算。

反过来，额外查了一次商品信息，也不一定让任务失败。先判断有没有做错事，再把多余调用放进效率评测。这样才能分清错误和优化空间。

不过，拿到了正确调用记录，也要继续核对购物车。参数正确、调用正确和最终写入正确，是有关联但不同的检查点。

## 4. 多轮对话，要跟着用户最新的意思走

“第二款”只有放在前面的展示列表里才有意义。因此，多轮用例不能只留最后一句话，还要保存用户实际看到的候选及顺序。

如果记录里根本没有这份列表，合理行为是先问用户指哪款，暂不加购。不能为了让流程跑下去，随便拿 P102 补上。

再看用户改变需求：

```text
用户：把第二款加入购物车，数量一个。
执行前用户补充：先别加，帮我比较一下两款。
```

这时应停止加购，继续比较。即使 P102 符合原来的条件，也不能忽略最新的要求。

如果用户把预算改成 250 元，原来 299 元的 P102 就不再满足条件，需要重新筛选或解释，而不能沿用旧结论。用户改成另一款商品，也要使用对应商品的信息，不能把旧商品的价格和库存套过去。

同款商品有多个颜色或规格时，也要确认选中的具体款式。本教程先用一个商品编号代表一个明确款式，不展开复杂规格系统，但评测思路相同。

把这些证据连上以后，很多错误都能直接定位：映射错查展示列表，参数错查调用记录，数量错查初始和最终购物车，回复夸大查实际结果。Agent 评测不必一开始就复杂，先让每个结论都能找到证据。
