# 电商导购与购物车评测示例

用户预算 300 元，要求推荐能装 15.6 英寸电脑且有货的通勤包。展示两款虚构商品 P101（259 元）、P102（299 元）后，用户选择本次列表的第二款，加购一个。

本例用普通分支逻辑模拟后半段的选择、实时查询和加购，只使用 Python 标准库。候选列表、选择位置和预算已整理成字段，不调用真实模型或真实电商，也不自动测商品召回和自然语言理解。

## 运行

在教程项目目录执行，需要 Python 3：

```powershell
python examples/shopping_eval/run_eval.py --version baseline
python examples/shopping_eval/run_eval.py --version fixed
```

分别生成 [修改前报告](./report_baseline.json) 和 [修改后报告](./report_fixed.json)。再次运行会覆盖相应报告。

初始版本规则检查通过 5/6；修正版本通过 6/6。唯一的决策改动是：加购接口明确返回失败时，不再宣称成功。数字只描述这批确定性模拟题，不代表真实模型效果。

## 看哪里

1. [cases.json](./cases.json)：六题的输入、背景、预期。
2. [run_eval.py](./run_eval.py) 中的 `run_agent`：按列表位置确定商品，查询当前价格和库存，然后加购；不读取预期。
3. `grade`：核对目标商品、回复状态、数量、其他商品、前置依据和调用记录。
4. 两份报告中的 `shopping_004`：查看接口结果、购物车和回复为什么矛盾。

## 几个约定

- 所有商品和价格都是教学用虚构数据，价格以整数分保存。
- `ShoppingWorld` 维护当前用户的模拟购物车，记录 `trace`；每题重新创建独立环境。
- 加购表示数量增加：初始两个，加一个后是三个；其他商品保持不变。
- 购物车不预留库存；模拟接口会限制当前购物车数量不能超过给定库存，加购不等于下单或支付。
- 同一次请求使用同一 `request_id`，重试不会重复加数量；新的加购意图使用新的 ID。
- 六题包含正常、超预算、缺少候选列表、明确失败、已有数量、缺货。超时结果未知、商品检索、提示注入等需要另外补题。
- `semantic_review` 为 `pending`：结构化结果通过，仍可能存在错误解释或夸大商品卖点，需要人工或 LLM 复核。

接真实模型时替换执行部分，通过同一工具层调用并继续核对状态，再补上文本理解、商品检索和裁判校准。详细讲解见 [第十一章](../../第十一章-完整实战-跑通一个小型评测流程.md)。
