```python
async def setup_checkpointer() -> BaseCheckpointSaver:
    global _checkpointer, _connection_pool

    if _checkpointer is not None:
        return _checkpointer

    # 使用 PostgreSQL Checkpointer (数据持久化)
    print(f"[Checkpointer] Connecting to PostgreSQL: {settings.postgres_uri.split('@')[-1]}")

    # 首先使用 autocommit 模式的连接来执行 setup()
    # 因为 CREATE INDEX CONCURRENTLY 不能在事务块中运行
    async with await psycopg.AsyncConnection.connect(
        settings.postgres_uri,
        autocommit=True
    ) as setup_conn:
        # 创建临时 checkpointer 用于 setup
        temp_checkpointer = AsyncPostgresSaver(setup_conn)
        await temp_checkpointer.setup()
        print("[OK] Checkpointer tables created/verified")

    # 创建异步连接池用于正常操作
    _connection_pool = AsyncConnectionPool(
        conninfo=settings.postgres_uri,
        min_size=1,
        max_size=10,
        open=False,  # 稍后手动打开
    )

    # 打开连接池
    await _connection_pool.open()

    # 创建 PostgreSQL Checkpointer
    _checkpointer = AsyncPostgresSaver(_connection_pool)

    print("[OK] PostgreSQL Checkpointer initialized - data will persist")

    return _checkpointer
```

### 原理解释与注释教学代码

以下继续解释已有机制，并补全本句话涉及的其他实现；它们是文档示例，不会自动改动线上服务。


### 1. 用人话理解

把内容生产想成一条流水线：选题部门出题，编辑部门写稿，审核人员确认，美术部门配图。State 是随任务流转的工作单，节点是工序，边是流转规则，子图是一个相对独立的小部门。

为什么不写几个函数顺序调用？因为任务要等人确认，也可能退回重写。顺序函数可以实现，但暂停点、历史记录和恢复逻辑会越来越分散。LangGraph 把它们集中到图里。

```text
选题子图 → 写作子图 → 人工审核
                       ├─ 驳回：带反馈回写作
                       └─ 通过：配图子图 → 结束
```

子图适合封装多步业务，例如“生成候选选题 + 人工选择”。不必每个简单函数都拆成子图。

### 2. 暂停恢复到底怎么发生

1. 任务使用唯一 thread_id，像任务单号。
2. 图运行到 interrupt，把进度交给 checkpointer 保存，返回人工提示。
3. 当前 HTTP 请求可以结束，不需要占着线程等人。
4. 用户选择或审核时，另发请求，使用同一个 thread_id 和 Command(resume=...)。
5. 中断节点恢复执行，读取人工决定，再继续或回退。

### 重点追问：State 何时保存，中断后究竟怎么恢复

本节按实际追问整理，重点是“节点过程是否保存”和“恢复时是否重新执行 interrupt”，先用串行链条理解，再补充并行边界。

#### 1. 节点执行过程中的计算会不会保存？

**普通节点通过 return 成功返回后，LangGraph 才接收它的 State 更新；函数内部的局部计算不会逐行保存。** State 更新也可以通过返回 `Command(update=...)` 提交。这里讨论常规节点返回更新的写法，不要直接修改传入 State 来模拟提交。

```python
def node_b(state):
    a = state["count"] + 1  # 局部计算，不会在这一行自动存档
    b = a * 2              # 局部计算，不会在这一行自动存档
    return {"count": b}    # 成功返回后，LangGraph 接收这次更新
```

串行流程可以先这样记：`A 成功返回 → 保存 A 完成后的状态 → B 开始执行`。B 中途失败时，之前的存档仍在；恢复可以用这份状态重新执行 B，通常不必重做 A。恢复并不代表失败后必定自动重试，还要由重试配置或后续恢复调用驱动。

严格区分：成功节点的结果可以单独保存；**完整 State 检查点在超级步边界创建**。初始输入阶段也会创建检查点，所以“只有节点完成时才会有存档”并不准确。创建检查点与实际写入存储完成的时机还受 durability 模式影响。

#### 2. interrupt 时保存的是上一个节点的状态吗？

**在普通串行流程里，当前节点尚未返回时，已提交的 State 通常还是上一个节点完成后的状态；中断时还会记录当前任务的中断信息。** 当前节点尚未返回的局部计算，不会因为调用 interrupt 就自动提交为 State。

```python
def review_node(state):
    draft = "刚生成的草稿"
    answer = interrupt({"question": "是否通过？", "draft": draft})
    return {"draft": draft, "answer": answer}
```

暂停时，`draft` 尚未通过 return 写入图的 State；但草稿内容作为 interrupt 的参数，会被记录为中断信息。因此，“State 里没有”和“中断信息里有”可以同时成立。局部变量本身没有作为 Python 函数现场保存。

#### 3. 恢复是不是从节点开头执行，也会再次执行 interrupt？

**是。当前中断节点从头执行，interrupt 前面的代码也会重跑；再次到达对应的 interrupt 时，它返回恢复值，而不是再次在同一处暂停。**

```python
config = {"configurable": {"thread_id": "task-001"}}

# 第一次调用：到达 interrupt 后暂停
result = graph.invoke(inputs, config)

# 后续调用：沿用同一个 thread_id，提供回复
result = graph.invoke(Command(resume="通过"), config)
```

```text
第一次：节点开头 → 计算草稿 → interrupt，没有回复 → 暂停
恢复后：节点开头 → 重新计算 → interrupt 返回“通过” → return 提交更新
```

这里假设恢复到的是同一个中断，节点内 interrupt 的调用顺序没有改变。若节点后面还有另一个 interrupt，仍可能在新的位置暂停。

想保存某段计算、恢复时不重做，可以将它放进前一个节点，先返回结果写入 State，再进入人工审核节点。发送请求、写文件等外部操作不会因恢复存档而自动撤销，也可能因节点重跑而重复执行。

#### 4. thread_id 和 checkpoint_id 何时创建，分别找什么？

注意名称是 `checkpoint_id`，不是 `checkpointer_id`；checkpointer 是负责存取的组件。

| 名称 | 谁创建、何时创建 | 用来定位什么 |
| --- | --- | --- |
| thread_id | 直接使用 Python 图时，通常由业务代码在首次调用前指定 | 整条会话或工作流程，可跨多次调用 |
| checkpoint_id | LangGraph 每次创建新检查点时自动生成 | 该流程中的某一份具体存档 |

可以把 thread_id 理解为存档文件夹，checkpoint_id 理解为里面每份存档的编号。State 和中断信息属于同一套检查点体系，**不是“中断只按 thread_id 存，State 只按 checkpoint_id 存”**：中断记录与相关任务、检查点关联。子图还会涉及 `checkpoint_ns`，用于区分检查点所属的图。

恢复中断通常只需相同 thread_id 和 `Command(resume=...)`，无需自己填写 checkpoint_id。查看最新存档编号：

```python
snapshot = graph.get_state(config)
checkpoint_id = snapshot.config["configurable"]["checkpoint_id"]
```

#### 5. 中断信息只能存在内存里吗，字段叫什么？

**不只能存在内存。图状态和中断信息由配置的 checkpointer 管理。**

| Checkpointer | 存储位置 | Python 进程退出后 |
| --- | --- | --- |
| InMemorySaver | 内存 | 丢失 |
| SqliteSaver，连接本地数据库文件 | 本地磁盘 | 保留 |
| PostgresSaver / AsyncPostgresSaver | PostgreSQL 数据库 | 保留 |

使用持久化存储时，可以关闭程序，之后重新加载图代码、连接同一存储，用同一个 thread_id 恢复。并不需要一直保留原来的 Python 函数或进程。

从默认 invoke 返回值读取中断内容：

```python
if result.get("__interrupt__"):
    content = result["__interrupt__"][0].value
    print(content)  # interrupt(...) 传入的内容
```

从已保存的图状态读取等待中的中断：

```python
snapshot = graph.get_state(config)
for task in snapshot.tasks:
    for item in task.interrupts:
        print(item.value)
```

#### 6. 超级步到底是什么？

**超级步（super-step）就是图执行的一轮。这一轮可以只有一个节点，也可以有多个并行节点；它们不必在同一时刻完成。**

```text
串行 A → B → C：第 1 轮 A，第 2 轮 B，第 3 轮 C。
分叉 A → [B、C] → D：第 1 轮 A，第 2 轮 B 和 C，第 3 轮 D。
```

假设第二轮中 B 用 1 秒完成，C 用 5 秒完成，仍然是同一轮。如果 C 失败，这一轮没有正常完成，但 B 成功的结果可以作为 pending writes 保留，恢复时避免重复运行 B。**这些单独保存的结果，与整轮完成后的完整 State 检查点不同。**

面试时可以这样回答：我把 State 理解成已提交的工作单。节点内部的局部计算不会逐行保存，成功返回后才提交更新。interrupt 会记录等待信息，恢复时从当前节点开头重跑，执行到对应 interrupt 时返回人工回复。thread_id 定位整条流程，checkpoint_id 定位某份存档；能否跨进程恢复取决于 checkpointer 是否持久化。

参考：[检查点与超级步](https://docs.langchain.com/oss/python/langgraph/checkpointers)、[中断和恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)。

### 3. 注释代码

下例演示真实 LangGraph 的核心形态，使用内存 checkpointer 便于学习；生产持久化将其替换为 AsyncPostgresSaver，并使用异步调用。

```python
from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command, interrupt
from langgraph.checkpoint.memory import InMemorySaver


class State(TypedDict, total=False):
    topic: str
    article: str
    feedback: str


def write_article(state):
    # 教学时用文本模拟模型输出；业务中在这里调用模型服务。
    return {"article": f"文章：{state['topic']}；修改意见：{state.get('feedback', '')}"}


def review_article(state) -> Command[Literal["write", "__end__"]]:
    # 重点：恢复会从本节点开头重放，中断前不要做付费调用或重复写入。
    answer = interrupt({"article": state["article"], "options": ["approve", "reject"]})
    if answer["action"] == "approve":
        return Command(goto=END)
    # 重点：update 改工作单，goto 决定下一步，二者分别负责数据与流程。
    return Command(update={"feedback": answer.get("feedback", "")}, goto="write")


builder = StateGraph(State)
builder.add_node("write", write_article)
builder.add_node("review", review_article)
builder.add_edge(START, "write")
builder.add_edge("write", "review")
graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "content-task-001"}}
graph.invoke({"topic": "AI 编程入门"}, config)  # 写完后暂停。
graph.invoke(Command(resume={"action": "reject", "feedback": "增加案例"}), config)
graph.invoke(Command(resume={"action": "approve"}), config)
```

PostgreSQL 版本的装配关系如下，需安装 checkpoint-postgres 与 psycopg；连接地址从配置注入：

```python
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver


async def run_persisted(builder, postgres_uri, initial_state, thread_id):
    async with AsyncPostgresSaver.from_conn_string(postgres_uri) as saver:
        # 重点：教学示例在这里 setup；实际应用通常在部署或启动时初始化。
        await saver.setup()
        graph = builder.compile(checkpointer=saver)
        config = {"configurable": {"thread_id": thread_id}}
        return await graph.ainvoke(initial_state, config)
```

### 4. 回滚、回放和重试要讲准确

- **人工驳回**：业务流程回到写作节点，不一定读取历史 checkpoint。
- **失败重试**：临时失败后再次执行相应工作，避免无意义地从选题开始。
- **历史回放**：选择旧 checkpoint，从它之后继续执行。
- **历史分叉**：基于旧快照修改 State，产生新路径。

这些都不是数据库意义上的“撤销一切”。历史点之后的模型调用可能重新收费，已发出的消息和已保存的图片不会被自动撤销。

```python
async def replay_history(graph, thread_id, checkpoint_id):
    config = {"configurable": {
        "thread_id": thread_id,
        "checkpoint_id": checkpoint_id,
    }}
    # 重点：从历史快照继续，后面的节点可能再次调用外部 API。
    return await graph.ainvoke(None, config)
```

### 5. 面试问答

**问：为什么用 LangGraph？**

答：业务不是一次性生成，而是有人工介入和循环的长流程。我用 State 统一数据，用图表达分支，用 checkpointer 保存进度，减少自己维护恢复逻辑的复杂度。

**问：thread_id 是线程吗？**

答：不是，是工作流实例标识。一个任务可以跨多个 HTTP 请求，同一任务有多个 checkpoint。

**问：checkpoint 能做到只调用一次外部服务吗？**

答：不能天然保证。外部调用成功但状态还没保存时崩溃，重试仍可能重复调用，所以收费请求和发布动作还要考虑幂等与结果去重。

**问：恢复时从哪执行？**

答：中断所在节点会重新进入执行，interrupt 接收到 resume 的值后继续，所以中断前代码必须可安全重放。

```python
import time


class MetricsContext:
    def __init__(self, node_name):
        self.metric = {"node": node_name, "success": False, "input_tokens": 0, "output_tokens": 0}

    def __enter__(self):
        self.started = time.perf_counter()
        return self

    def set_usage(self, usage, source="provider"):
        self.metric.update(usage)
        # 重点：区分供应商返回与估算值，避免把粗估当成精确账单。
        self.metric["usage_source"] = source

    def __exit__(self, exc_type, exc_value, traceback):
        self.metric["duration_ms"] = (time.perf_counter() - self.started) * 1000
        self.metric["success"] = exc_type is None
        self.metric["error_type"] = exc_type.__name__ if exc_type else None
        return False  # 重点：记录异常，但不吞掉异常，让上层决定是否重试。


async def tracked_call(service, messages):
    with MetricsContext("write_article") as tracker:
        response = await service.ainvoke(messages)
        tracker.set_usage(response.usage_metadata or {})
    # 重点：退出 with 后耗时才结算完成，不要在 with 内提前读取最终耗时。
    return response, tracker.metric
```

### 3. 成本与错误率公式

```text
文本费用 = 输入 Token / 100万 × 输入单价
         + 输出 Token / 100万 × 输出单价

节点尝试错误率 = 失败尝试次数 / 总尝试次数
任务最终失败率 = 重试后仍失败的任务数 / 总任务数
```

价格表按模型配置，缓存、图片、阶梯价格和币种另算。“一次任务失败过但重试成功”会计入尝试失败，不应计入最终任务失败。

### 补充实现：把指标变成费用和错误率

建议位置：`app/core/costs.py`。价格表由配置传入，没有把示例单价当成供应商当前价格；currency 和模型版本应与价格配置一起保存。

```python
from decimal import Decimal


def compute_text_cost(input_tokens, output_tokens, input_price, output_price):
    # 重点：这里约定价格单位为“每百万 Token”，输入与输出分别计价。
    million = Decimal("1000000")
    return (
        Decimal(str(input_tokens)) * Decimal(str(input_price)) / million
        + Decimal(str(output_tokens)) * Decimal(str(output_price)) / million
    )


def summarize_attempts(metrics, prices):
    # metrics 为教学增强版 MetricsContext 产生的字典列表。
    failures = sum(not item["success"] for item in metrics)
    total_cost = Decimal("0")
    unpriced = 0
    for item in metrics:
        rate = prices.get(item.get("model"))
        if rate is None:
            unpriced += 1  # 重点：未知价格不是免费，单独报告缺失。
            continue
        total_cost += compute_text_cost(
            item.get("input_tokens", 0), item.get("output_tokens", 0),
            rate["input"], rate["output"],
        )
    return {
        "attempts": len(metrics),
        "error_rate": failures / len(metrics) if metrics else None,
        "known_usage_cost": str(total_cost),
        "unpriced_attempts": unpriced,
    }
```

async def stream_graph_updates(
    graph, 
    input_data: Any, 
    config: Dict[str, Any]
) -> AsyncGenerator[str, None]:
    try:
        # 发送开始事件
        yield format_sse_event("start", {})

        # 用于收集 token 统计
        token_stats = {
            "input_tokens": 0,
            "output_tokens": 0,
            "total_tokens": 0
        }

        # 使用 astream_events 获取 LLM token 级别的流式输出
        async for event in graph.astream_events(input_data, config, version="v2"):
            event_kind = event.get("event", "")
            event_name = event.get("name", "")
            event_data = event.get("data", {})

            if event_kind == "on_chat_model_start":
                yield format_sse_event("llm_start", {
                    "model": event_name
                })

            elif event_kind == "on_chat_model_stream":
                # LLM token 级别的流式输出 - 文章生成的核心
                chunk = event_data.get("chunk", {})
                if hasattr(chunk, "content") and chunk.content:
                    yield format_sse_event("llm_token", {
                        "content": chunk.content
                    })

            elif event_kind == "on_chat_model_end":
                output = event_data.get("output", {})
                # 提取 token 使用信息
                usage_info = {}
                if hasattr(output, "usage_metadata") and output.usage_metadata:
                    usage_info = {
                        "input_tokens": output.usage_metadata.get("input_tokens", 0),
                        "output_tokens": output.usage_metadata.get("output_tokens", 0),
                        "total_tokens": output.usage_metadata.get("total_tokens", 0)
                    }
                    token_stats.update(usage_info)
                elif hasattr(output, "response_metadata") and output.response_metadata:
                    token_usage = output.response_metadata.get("token_usage", {})
                    if token_usage:
                        usage_info = {
                            "input_tokens": token_usage.get("prompt_tokens", 0),
                            "output_tokens": token_usage.get("completion_tokens", 0),
                            "total_tokens": token_usage.get("total_tokens", 0)
                        }
                        token_stats.update(usage_info)

                yield format_sse_event("llm_end", {
                    "model": event_name,
                    "usage": usage_info if usage_info else token_stats
                })

        # 获取最终状态
        final_state = await graph.aget_state(config)
        interrupt_info = extract_interrupt_info(final_state)
        next_nodes = list(final_state.next) if final_state.next else []
        is_completed = len(next_nodes) == 0 and not interrupt_info

        # 发送完成事件
        yield format_sse_event("done", {
            "status": final_state.values.get("status", "unknown") if final_state.values else "unknown",
            "next_nodes": next_nodes,
            "is_completed": is_completed,
            "interrupt_info": interrupt_info,
            "values": dict(final_state.values) if final_state.values else {}
        })

    except Exception as e:
        # 发送错误事件
        yield format_sse_event("error", {"message": str(e)})

async function readArticle(response, appendText) {
  const reader = response.body.getReader()
  const decoder = new TextDecoder()
  let buffer = ''
  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    // 重点：一次网络读取可能只有半个中文字符，流式解码保留状态。
    buffer += decoder.decode(value, { stream: true })
    const lines = buffer.split('\n')
    buffer = lines.pop() || '' // 重点：半条 JSON 留到下次再解析。
    for (const line of lines) {
      if (!line.startsWith('data: ')) continue
      const event = JSON.parse(line.slice(6))
      if (event.type === 'llm_token') appendText(event.data.content)
    }
  }
}

### 4. 面试问答

**问：SSE 和 WebSocket 如何选？**

答：文章生成主要是服务端单向推送，SSE 够用，接入 HTTP 也更直接；持续双向互动、复杂实时通信再考虑 WebSocket。

**问：为什么用 fetch 而不是 EventSource？**

答：生成接口要 POST JSON，并带 Authorization，fetch 方便设置；浏览器原生 EventSource 更偏向 GET 事件订阅。

**问：一个 llm_token 事件就是一个 Token 吗？**

答：不是，这是业务事件名，实际是文本 chunk，可能包含多个 Token；不能拿片段数量计费。

**问：首字延迟与总耗时有什么区别？**

答：首字延迟看多久能看到第一段正文，总耗时看全文多久完成。流式主要改善前者的体验，不代表模型算得更快。

**问：如何保证流式与非流式状态一致？**

答：两种方式运行同一张图、使用同一个 State 和持久化机制；chunk 只负责即时展示，完整正文由节点结束时更新。不要让前端拼接结果成为唯一业务存档。

### 1. 用人话理解

串行是先等第一张图，再请求第二张；并发是把几张图的请求一起发出去，网络等待交叠。asyncio 适合这种 I/O 场景，不是让 CPU 凭空多出几倍算力。

原生异步客户端可以直接 await；同步 SDK 会卡住事件循环时，才用线程池包装。两条路径别混淆。

### 2. 注释代码：包装同步 SDK

```python
import asyncio
from functools import partial


async def generate_one(sync_client, prompt):
    loop = asyncio.get_running_loop()
    # 重点：同步 SDK 放入线程池，避免阻塞事件循环。
    # 若本来就是 httpx.AsyncClient，直接 await，不需要套线程池。
    call = partial(sync_client.generate, prompt=prompt)
    return await loop.run_in_executor(None, call)


async def generate_batch(sync_client, prompts):
    jobs = [generate_one(sync_client, prompt) for prompt in prompts]
    # 重点：逐项收集失败，不让一张图失败就丢掉其他已成功结果。
    results = await asyncio.gather(*jobs, return_exceptions=True)
    return [
        {"prompt": prompt, "error": str(result)} if isinstance(result, BaseException)
        else {"prompt": prompt, "image": result}
        for prompt, result in zip(prompts, results)
    ]
```

### 3. 注释代码：指数退避

```python
import asyncio
import random


async def retry_transient(call, retryable_errors, max_attempts=4):
    if max_attempts < 1:
        raise ValueError("max_attempts 必须大于 0")
    for attempt in range(max_attempts):
        try:
            return await call()
        except retryable_errors:
            if attempt == max_attempts - 1:
                raise
            # 重点：最多 4 次尝试，失败间隔为 1、2、4 秒，加少量随机抖动。
            # 真正接服务时，还要识别状态码并尊重 Retry-After。
            await asyncio.sleep(2 ** attempt + random.uniform(0, 0.2))
```

### 4. 面试问答

**问：为什么重试要越等越久？**

答：下游拥堵或短暂故障时，立即重复请求会加重压力；逐步拉长间隔给服务恢复时间，随机抖动避免所有客户端同时再冲上去。

**问：什么错误不重试？**

答：认证失败、参数不合法通常重试无效；网络超时、部分 5xx、限流更适合分类重试。还要设置次数与整体超时。

**问：线程池能解决所有同步耗时吗？**

答：它适合隔离阻塞 I/O。CPU 密集任务可能需要进程池或外部服务；取消 await 也不代表正在执行的线程函数立刻停止。

**问：并发越多越好吗？**

答：不是。要根据服务商限额和资源容量限制并发，且关注多用户叠加。Semaphore 适合进程内限制，多进程场景还需要共享策略。

### 3. 为什么要 Pydantic、raw 和 parsed

- Pydantic：规定输出字段与约束，例如 topics 必须是标题列表。
- parsed：方便业务直接读取的结构化结果。
- raw：原始模型响应，通常包含用量和其他元数据。
- JSON Mode：让支持该功能的服务按 JSON 形式输出；仍需要 Schema 校验。
- 手动解析：兼容输出格式或服务能力不一致的情况。

```python
import json
from pydantic import BaseModel, Field


class Topics(BaseModel):
    titles: list[str] = Field(min_length=3, max_length=5)


async def generate_topics(model, messages):
    result = await model.with_structured_output(Topics, include_raw=True).ainvoke(messages)
    # 重点：解析失败不一定抛异常，也可能在 parsing_error 中体现。
    if result.get("parsed") is not None and not result.get("parsing_error"):
        raw = result.get("raw")
        usage = getattr(raw, "usage_metadata", None)
        return result["parsed"], usage

    # 重点：JSON Mode 需要供应商支持，不能假定所有兼容接口都实现。
    fallback = model.bind(response_format={"type": "json_object"})
    # Prompt 必须明确包含 JSON 格式要求，例如 {"titles": ["标题1", ...]}。
    response = await fallback.ainvoke(messages)
    data = Topics.model_validate(json.loads(response.content))
    return data, getattr(response, "usage_metadata", None)
```

```python
async def dispatch(self, request: Request, call_next: Callable) -> Response:
    # 跳过不需要记录的路径
    if request.url.path in self.SKIP_PATHS:
        return await call_next(request)

    # 生成 request_id（优先使用请求头中的，便于链路追踪）
    request_id = request.headers.get("X-Request-ID", str(uuid.uuid4())[:8])
    set_request_id(request_id)

    # 获取客户端 IP
    client_ip = self._get_client_ip(request)

    # 记录请求开始
    start_time = time.perf_counter()
    app_logger.request_started(
        method=request.method,
        path=request.url.path,
        client_ip=client_ip,
        query_params=str(request.query_params) if request.query_params else None,
    )

    # 处理请求
    status_code = 500
    try:
        response = await call_next(request)
        status_code = response.status_code

        # 添加 request_id 到响应头（便于客户端追踪）
        response.headers["X-Request-ID"] = request_id

        return response

    except Exception as e:
        # 记录异常
        app_logger.request_error(
            method=request.method,
            path=request.url.path,
            error=str(e),
            status_code=500,
        )
        raise

    finally:
        # 计算耗时并记录请求完成
        duration_ms = (time.perf_counter() - start_time) * 1000
        app_logger.request_finished(
            method=request.method,
            path=request.url.path,
            status_code=status_code,
            duration_ms=duration_ms,
        )
        # 清除 request_id
        clear_request_id()
```

### 1. 用人话理解

日志像文字版流水账：哪个请求报错、错误是什么。Trace 像这次任务的路线图：走了哪些节点、谁调用了谁、每步耗时多久。两者结合，才能从一个用户问题找到具体模型调用。

| 标识 | 含义 |
| --- | --- |
| request_id | 一次 HTTP 请求 |
| thread_id | 一次完整内容任务，可跨多次请求 |
| run_id | 某次图/模型追踪运行及其父子关系 |

### 2. 注释代码

LangSmith 需通过环境配置启用；以下重点演示关联 ID，不在代码中写真实密钥。

```python
from contextvars import ContextVar
from uuid import uuid4
import structlog

request_id_var = ContextVar("request_id", default=None)
logger = structlog.get_logger()


async def traced_invoke(graph, value, thread_id):
    request_id = str(uuid4())
    token = request_id_var.set(request_id)
    try:
        config = {
            "configurable": {"thread_id": thread_id},
            # 重点：把日志 ID 显式写进追踪 metadata，方便交叉查询。
            "metadata": {"request_id": request_id, "business_thread_id": thread_id},
        }
        logger.info("workflow_started", request_id=request_id, thread_id=thread_id)
        return await graph.ainvoke(value, config)
    finally:
        # 重点：恢复原上下文，避免请求结束后留下不正确的关联信息。
        request_id_var.reset(token)
```

### 3. 面试问答

**问：为什么不用普通全局变量存 request_id？**

答：异步请求会交错执行，普通全局变量可能串请求；ContextVar 用于当前任务上下文。跨独立进程或队列时仍要显式传递。

**问：如何定位“生成很慢”？**

答：先看整次请求和节点耗时，再看模型等待、重试、图片请求和数据库操作。通过 thread_id 找整条流程，通过 request_id 找本次操作，通过 trace 找最慢的调用。

**问：追踪时要注意什么？**

答：Prompt、模型返回和 State 可能包含个人信息。日志与追踪分别做脱敏、采样、权限和保留期限控制，不把所有正文无差别上报。

### 原理解释与注释教学代码

以下继续解释已有机制，并补全本句话涉及的其他实现；它们是文档示例，不会自动改动线上服务。


### 1. 先区分三个概念

| 机制 | 像什么 | 解决什么 |
| --- | --- | --- |
| 限流 | 门口控制进场人数 | 请求太多，先限制进入速度 |
| 重试 | 这次没成功，再试一次 | 临时失败可能恢复 |
| 熔断 | 设备持续故障，先断电 | 避免持续请求故障下游 |

降级是“暂时给一个可用替代结果”，例如模板选题、稍后再试提示；不能悄悄把模板当成真实模型输出。

### 2. 注释代码：SlowAPI 每分钟 10 次

需安装 SlowAPI。下面是可独立理解的最小示例；正式业务通常按用户或租户限流，而不只按 IP。

```python
from fastapi import FastAPI, Request
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.errors import RateLimitExceeded
from slowapi.util import get_remote_address

app = FastAPI()
limiter = Limiter(key_func=get_remote_address)
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)


@app.post("/generate")
@limiter.limit("10/minute")
async def generate(request: Request):
    # 重点：SlowAPI 需要 Request 参数以识别请求。
    # 限流超出返回 429；多实例应使用共享存储，而不是各自独立计数。
    return {"message": "已通过限流检查"}
```

### 3. 熔断的三个状态

```text
Closed：正常调用，累计失败
  → 失败达到阈值 → Open：短时间拒绝调用，返回降级结果
  → 冷却时间结束 → Half-open：只放少量探测请求
       ├─ 成功：回到 Closed，清理失败计数
       └─ 失败：回到 Open，再等一段时间
```

设计时需要明确失败阈值、时间窗口、冷却时间和半开并发数。不能仅写一个 try/except 返回模板，就称为熔断器。

### 4. 注释代码：优雅关闭

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI


def make_app(open_resources):
    @asynccontextmanager
    async def lifespan(app):
        resources = await open_resources()
        app.state.resources = resources
        try:
            yield  # 重点：yield 期间才是应用接收请求的正常运行阶段。
        finally:
            # 重点：无论如何退出，都应释放连接池、客户端等资源。
            await resources.close()

    return FastAPI(lifespan=lifespan)
```

### 5. 面试问答

**问：10 次/分钟是不是只能处理 10 个请求？**

答：要看限流键和作用范围。按 IP 就是每个 IP，按用户就是每个用户；接口级和全局级也不同。这个配置不是服务器最大吞吐能力。

**问：为什么有了限流还要熔断？**

答：限流解决请求过多，熔断解决下游已经不健康；即使流量不大，下游持续故障也应该暂时停止调用。

**问：健康检查该检查什么？**

答：存活检查表示进程是否正常；就绪检查表示能否接业务，例如数据库连接是否可用。不应每个健康探针都发一次收费模型请求。

**问：优雅关闭就是关闭数据库吗？**

答：不止，还要停止接新任务、给在途请求合理时间、保存必要状态、释放 HTTP 客户端与连接池。超时后如何取消和恢复，也要有策略。

### 补充实现：可接到模型调用处的简化熔断器

建议位置：`app/core/circuit_breaker.py`。下例是单进程 asyncio 教学版：包含状态、冷却、半开单探针和取消处理。真实多实例部署要考虑共享状态和统一策略。

```python
import asyncio
import time


class CircuitOpen(Exception):
    pass


class AsyncCircuitBreaker:
    def __init__(self, threshold=3, cooldown=30, failures=(TimeoutError, ConnectionError)):
        if threshold < 1 or cooldown < 0:
            raise ValueError("threshold 必须大于 0，cooldown 不能小于 0")
        self.threshold, self.cooldown, self.failures = threshold, cooldown, failures
        self.state, self.failed, self.opened_at = "closed", 0, 0.0
        self.lock = asyncio.Lock()
        self.generation = 0

    async def call(self, operation):
        async with self.lock:
            if self.state == "open":
                if time.monotonic() - self.opened_at < self.cooldown:
                    raise CircuitOpen("下游恢复中")
                self.state = "half_open"
                probe = True  # 重点：只有首个进入者能执行恢复探测。
            elif self.state == "half_open":
                raise CircuitOpen("已有探测请求在执行")
            else:
                probe = False
            generation = self.generation

        try:
            # 重点：网络调用不持有锁，否则会把所有模型请求变成串行。
            result = await operation()
        except BaseException as error:
            async with self.lock:
                if generation == self.generation:
                    if isinstance(error, self.failures):
                        self.failed += 1
                    if probe or self.failed >= self.threshold:
                        self.state, self.opened_at = "open", time.monotonic()
                        self.generation += 1
            # 重点：取消等控制信号仍向上传播，不包装成普通模型成功。
            raise
        else:
            async with self.lock:
                if generation == self.generation:
                    self.failed = 0
                    if probe:
                        self.state = "closed"
                        self.generation += 1
            return result


# 在应用生命周期内复用实例，不能每次请求都重新创建。
breaker = AsyncCircuitBreaker()


async def protected_topics(real_call):
    try:
        return {"degraded": False, "value": await breaker.call(real_call)}
    except (CircuitOpen, TimeoutError, ConnectionError):
        # 重点：降级结果有明确标记，避免把模板伪装成真实模型生成。
        return {"degraded": True, "value": ["AI 编程入门路线", "机器人学习清单"]}
```

如何接入：在 LLMService 的真实请求外调用 breaker.call；将服务商的可重试异常映射到 failures，参数错误或无权限不要当作持续下游故障。generation 用于忽略熔断前仍在途的旧请求结果，避免旧请求成功后错误地关闭新一轮熔断。

这段代码只说明完整状态转换，未接入 SlowAPI 或生产业务；限流放 HTTP 入口，熔断放下游调用边界，两个保护点各有职责。

## 十、优先记住的 12 句话

1. State 是工作单，节点是工序，子图是独立小流程。
2. interrupt 暂停，Command(resume) 回答人工问题。
3. Command(update, goto) 负责改状态和路由。
4. thread_id 标识任务，checkpoint_id 标识任务快照。
5. 恢复会重放中断节点，中断前避免副作用。
6. checkpointer 不是“外部请求只执行一次”的保证。
7. 指标退出 with 后结算，Token 用量优先看供应商 usage。
8. SSE 要同时打通模型流和 HTTP 流，chunk 不等于 Token。
9. 原生异步直接 await，阻塞 SDK 才考虑线程池。
10. 模型分工要一起比较质量、延迟、成本和返工率。
11. 日志看事件，trace 看调用路径，用 ID 关联。
12. 限流管流量，重试管临时失败，熔断隔离持续故障。
