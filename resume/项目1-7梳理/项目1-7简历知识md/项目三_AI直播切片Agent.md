## 一、业务背景与项目定位

- **业务痛点**：公司有直播带货场景（如 TK 带货卖鞋），主播直播后产生大量回放视频；传统方式需要剪辑师**人工观看回放、手动寻找高光片段并裁剪**，耗时耗力。
- **项目目标**：把直播回放交给 AI，**自动找出精彩片段、配上标题文案，直接输出短视频切片**，大幅减轻剪辑师工作。
- **服务形态**：部署在**公司内部**、用**自己的服务器**（对外宣称是内部工具，非对外 SaaS）。
- **项目定位**（讲义 26 小结口径）：**辅助业务项目，非核心项目**——解决的是主播直播后高光片段人工裁剪效率低的问题。
- **数据闭环**：转写结果同步**回流数据中台**留存，供后续内容分析或模型训练复用；切片视频一键关联 SKU → 素材管理中心 → 数据中台 → AI 客服。

## 二、端到端链路

### 2.1 总流程（大纲版）

```
上传视频到浏览器 → ffmpeg.wasm 分离 MP3 → 上传到 ASR 服务 → 返回带时间戳的转写文本
→ 文本丢给 LLM → LLM 给出切片建议（时间段 + 主题 + 吸引力评分）→ 浏览器切片 → 下载切片结果
```

### 2.2 分步说明

1. **上传视频到浏览器**：用户将直播回放视频上传至前端。
2. **FFmpeg.wasm 分离 MP3**：在浏览器内利用 **WebAssembly** 技术运行 FFmpeg，从视频中提取音频并压缩为 MP3 格式。
3. **上传音频到 ASR 服务**：将压缩后的 MP3 文件上传至 ASR（自动语音识别）服务。
4. **ASR 返回转写文本**：ASR 服务返回完整的转写文本，**并携带每句话对应的时间戳**。
5. **文本丢给 LLM 分析**：将带时间戳的文本发送给大模型。
6. **LLM 给出切片建议**：LLM 分析文本内容，输出多个切片建议，每个建议包含：
   - **时间范围**：例如"第 1 秒到第 80 秒"（讲义另提到"通常 5 秒到 1 分钟"）；
   - **内容主题**：例如"产品特点介绍"；
   - **吸引力评分**：例如"爆款分：8.5"。
7. **浏览器执行切片**：前端根据 LLM 返回的时间范围，**再次调用 FFmpeg.wasm 在浏览器内**进行视频裁剪。
8. **下载切片结果**：用户直接下载裁剪好的短视频切片。

### 2.3 简历版（更工程化）的口径

- 三层架构：**React 19 + FFmpeg.wasm 前端**、**FastAPI + SQLAlchemy 2.0 后端**、**Groq Whisper + DeepSeek 外部 AI**。
- **WORKERFS 零拷贝挂载**源文件，转码为 **16kHz / 单声道 / 64kbps MP3**，把 2.5GB 视频压到约 30MB 再上传，**上传体积降低 99%**，用户等待从分钟级降到秒级。
- **PostgreSQL 做任务队列**：API 写入 pending 秒回，Task Runner 后台协程每秒抢占一条串行执行 Pipeline；进程崩溃时启动自动重置"进行中"任务回 pending → **零云依赖 + 崩溃可恢复**。
- **可观测 Pipeline**（音频准备 → ASR → LLM 分析 → 切片 → 入库）：进度统一写库 + SSE 每秒读库推送，**进度源唯一、断线可续、多端一致**。
- **长音频**用 `ffmpeg -c copy` 按 **25 分钟**无损分段串行转录，时间戳加 offset 还原绝对时间轴。
- **LLM 分析**按约 **6000 token** 分批 + **双向重叠去重**（重叠 >30% 取高分项），支撑 **6 小时**长视频不爆上下文；内置直播/面试/讲座场景化 Prompt，按场景切换切片时长与去重阈值。
- **导出阶段**二次复用 FFmpeg.wasm 在浏览器内按 AI 时间段批量裁切打包 ZIP，后端不碰重型转码；ASR 转写结果回写数据中台。

## 三、核心架构决策：为什么全部在浏览器切片

### 3.1 架构演进

| 阶段 | 方案 | 问题 |
|---|---|---|
| 最初 | **服务端安装 FFmpeg** 切片，所有切片任务由服务器 CPU 处理 | FFmpeg 切片非常消耗 CPU 资源；多个用户（如 10 人）同时使用时服务器压力巨大，容易崩溃或响应缓慢 |
| 现在 | **客户端（浏览器）切片** | 服务器不再承担切片计算 |

### 3.2 为什么能搬到浏览器

- 现代浏览器完全具备运行 **FFmpeg.wasm** 进行视频处理的能力，且对用户个人电脑性能影响不大。
- 架构设计师的思路：**将服务器的压力转移，变相提升并发**。

### 3.3 优化收益

- **提升并发能力**：服务器不再承担切片计算，理论上能处理的并发请求数**只受限于 ASR 服务的上限**。
- **降低成本**：无需为应对峰值压力而配置高性能服务器。
- **最终效果**：整个直播切片系统的处理上限**完全取决于 ASR 服务的处理能力**——ASR 能处理多少并发，系统就能同时处理多少切片任务。

### 3.4 新旧方案对比

| 对比维度 | 服务端切片方案（旧） | 客户端切片方案（新） | 优势 |
|---|---|---|---|
| 性能压力 | 全部集中在服务器，CPU 消耗大 | 分散到各用户浏览器 | 并发能力大幅提升 |
| 扩展性 | 受限于服务器资源，10 人同时跑可能顶不住 | 用户越多，处理能力越强 | 瓶颈仅剩 ASR 服务 |
| 资源利用 | 服务器需安装 ffmpeg，占用系统资源 | 利用用户本地计算能力 | 成本更低、效率更高 |
| 适用场景 | 适合小规模、低并发 | 适合大规模、高并发直播切片 | 更符合实际业务需求 |

## 四、高并发怎么回答（本节是最容易被问倒的点）

### 4.1 面试问法

"你的视频处理遇到高并发怎么办？" / "为什么不用消息队列？"

### 4.2 核心应答结构

1. **架构层**：之所以把服务端的 FFmpeg 移到浏览器，就是为了释放服务端压力。
2. **真正的瓶颈**：**ASR 服务能抗多少，是项目的关键**，服务端的主要压力来源就是 ASR 服务。
   - 解决方案一：充钱（把 ASR 的额度买上去）；
   - 解决方案二：**同时接入多个 ASR 服务商**（阿里云、腾讯云、Groq），实现负载切换——当一个服务商压力过大时，自动切换到另一个，确保服务不中断。
3. **进度展示**：前端订阅后端服务（SSE），瓶颈不在这里，数据量小、处理逻辑简单。
   - 消息队列？**不需要**，见下文。

### 4.3 为什么不需要消息队列

| 判断维度 | 本项目实际情况 | 结论 |
|---|---|---|
| 处理时长 | 一个视频处理需要 **10 分钟**，用户只需点击一次发起任务 | 长任务、低频 |
| 并发量 | 即使同时处理 100 个视频，**QPS（每秒查询数）也远低于 100** | 对服务端和数据库压力极小 |
| 场景匹配度 | 消息队列适用于**实时性要求高、消息频繁交互**的场景（如微信聊天） | 本项目是长时间任务处理，不适合用消息队列 |

核心结论：**高并发不是盲目追求，要明确瓶颈所在**。本项目的瓶颈在 ASR 服务，通过接入多个 ASR 服务商来提升并发能力。

### 4.4 任务调度与进度展示

- **创建 task**：后端为每个视频处理任务创建一个任务记录。
- **订阅 SSE 进度条**：前端通过 SSE（Server-Sent Events）实时订阅任务处理进度，让用户实时了解进度，提升体验。
- **协程 task 调度（串行版 → 并行版）**：后端用协程调度任务，初始为串行处理；后续优化为并行处理，提升效率。
- 瓶颈分析：进度展示与任务调度本身都**不是瓶颈**——数据量小、对服务端和数据库压力小。

### 4.5 新旧方案对比（高并发维度）

| 对比维度 | 本方案 | 传统方案 |
|---|---|---|
| 服务端压力 | 低（FFmpeg 移至浏览器） | 高（服务端处理视频） |
| 并发瓶颈 | ASR 服务（需多供应商切换） | 服务端计算资源 |
| 消息队列需求 | 不需要（任务 10 分钟、非高频） | 需要（高频实时场景） |
| 适用场景 | 公司内部非高频视频处理 | 对外高频视频处理服务 |

## 五、导出结果与数据中台打通

### 5.1 核心逻辑

**导出的切片视频不是终点，而是数据闭环的起点。**

### 5.2 一键关联商品（SKU）

- 在直播切片项目中，用户可以选择一个切片，**一键关联到具体的商品 SKU ID**。
- 例如：主播介绍某款鞋子的高光片段，可直接关联到该鞋子的 SKU。

### 5.3 自动生成备注与 Embedding

- **ASR 转写文本天然包含了主播对该商品的完整介绍**。
- 调用 LLM，基于 ASR 文本自动生成一段精炼的**商品介绍备注**。
- 把备注和视频一起写入**数据中台的视频素材表**。

### 5.4 反哺 AI 客服系统

- 数据中台的视频素材表结构：`sku_id`、`备注`、`Embedding` 向量。
- 当用户咨询商品时，AI 客服系统可以通过**向量检索**，精准匹配到对应的商品介绍视频，直接推送给用户观看，实现 AI 自动化的商品介绍流程。
- 业务场景闭环：主播卖鞋子的视频 → embedding 依据备注 → ASR 天然有鞋子的完整介绍 → LLM 生成备注 → 直接在素材管理中心关联商品 → 写入数据中台的视频素材表。

## 六、技术细节与实现要点

### 6.1 数据清洗

- ASR 返回的原始数据需要清洗：去掉多余空格、去掉 `Segments` 中的多余字段、统一数字类型。

### 6.2 LLM 分析细节

- 将 `Segments` 的时间戳和文本一起喂给 LLM。
- LLM 输出分析结果，构造 Clips（切片建议）。
- 切片建议的时间范围通常是 **5 秒到 1 分钟**（大纲另给出"第 1 秒到第 80 秒"的示例，属于具体某条的时长）。

### 6.3 长音频处理

- 当音频超过 **2 小时**时，`Segments` 可以不完整，LLM 有能力通过上下文分析兜底。
- 简历口径的工程化做法：按约 6000 token 分批 + 双向重叠去重（重叠 >30% 取高分项），`ffmpeg -c copy` 按 25 分钟无损分段并加 offset 还原时间轴。

### 6.4 环境准备

- 需要安装 **FFmpeg** 并配置环境变量；
- 需要启动 **PostgreSQL** 数据库，并执行数据库迁移命令 `uv run alembic upgrade head`；
- 需要开通 **Groq**（ASR 云服务）的 API。

### 6.5 项目演进方向

- **功能补充**：持续增加新功能，如视频结果一键关联商品（SKU ID）。
- **技术升级**：优化架构，提升性能和并发能力。
- **核心优化点**：将服务端的 FFmpeg 切片任务转移到浏览器，释放服务端压力。

## 九、高频面试问答速记

**Q1：这个项目解决了什么业务问题？**
A：直播带货主播一场直播两三个小时，以前剪辑师要人工看回放找高光片段。我们做了 AI 切片：浏览器提音频 → ASR 转写（带时间戳）→ LLM 分析给切片建议（时间段、主题、爆款分）→ 浏览器按时间段裁切 → 下载。一场 2~3 小时的直播，大概 15 分钟能切出 20~30 个视频。

**Q2：为什么切片放在浏览器做？**
A：一开始是服务端装 FFmpeg 切片，CPU 消耗极大，10 个人同时用服务器就顶不住。后来改成客户端切片——现代浏览器跑 FFmpeg.wasm 完全够用，对用户电脑影响不大，把服务器压力转移给用户端，变相提升了并发，也省了为峰值配置高性能服务器的钱。

**Q3：那现在系统的瓶颈在哪？**
A：在 ASR 服务。服务端只剩 ASR 请求，ASR 能处理多少并发，系统就能处理多少切片。应对方式是同时接阿里云、腾讯云、Groq 多家 ASR 做负载切换，一家压力大就自动切另一家。

**Q4：为什么不用消息队列？**
A：处理时长要 10 分钟、用户点一次就发起一个任务、并发只有几十到 100 个视频，QPS 远低于 100，服务端和数据库压力极小；消息队列是给高频实时交互场景用的，这里不匹配。

**Q5：进度条怎么做的？**
A：任务统一写库，前端用 SSE 订阅后端，后端每秒读库推送。进度源唯一、断线可续、多端一致。进度展示本身数据量小，不是瓶颈。

**Q6：长视频（2 小时以上）怎么办？**
A：早期发现 Segments 可能是不完整的，LLM 能靠上下文兜底；工程化做法是按约 6000 token 分批、双向重叠去重（重叠超 30% 取高分项），音频用 ffmpeg -c copy 按 25 分钟无损分段，时间戳加 offset 还原绝对时间轴，6 小时视频也不爆上下文。

**Q7：服务器崩了任务会丢吗？**
A：用 PostgreSQL 做任务队列，API 写入 pending 就秒回，Task Runner 后台协程每秒抢占一条执行。进程崩溃重启时，会把"进行中"的任务自动重置回 pending，实现零云依赖、崩溃可恢复。

**Q8：切片导出之后就结束了吗？**
A：不是。导出的视频可以一键关联 SKU，然后用 ASR 文本让 LLM 生成商品介绍备注，把 sku_id、备注、embedding 写入数据中台的视频素材表。客服系统咨询商品时用向量检索就能命中这段主播介绍视频，直接推给用户。

## 十、易混淆点自查

- "浏览器切片"解决的是**服务端 CPU 压力/并发**，不是"切片质量"。
- 项目真正的瓶颈是 **ASR 服务**，不是服务端、不是数据库、不是进度展示。
- 高并发 ≠ 上消息队列；要**先定位瓶颈**。
- 切片视频的终点是**数据闭环**（回流中台 → 反哺客服），不是下载。
- 讲述优先级：**架构 → 业务 → 扩展**，而不是钻技术细节。
