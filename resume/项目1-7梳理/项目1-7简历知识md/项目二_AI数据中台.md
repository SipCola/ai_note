## 一、项目定位

- **一句话定位**：整个 AI 体系的**数据底座 / 核心枢纽 / 航空母舰**。所有与 AI 相关的业务（客服、微调、考核、素材、直播）都从这里取数。
- **核心目标**：把微信原始聊天记录加工成**可训练、可检索、可考核**的高质量数据资产。
- **为什么要有它（故事线）**：最早期是程序员手动导出微信聊天记录、人工清洗，业务规模变大后每次都麻烦程序员，效率低；为了让运营/销售自己就能导出和清洗，就搭了数据中台。
- **技术定位（面试要点）**：数据中台**纯粹是业务层面的事情，技术上没什么难度**，核心难点在业务策略（清洗规则、数据分级、多业务分流），而不是技术难题。
- **在 8 个项目中的位置**：底座项目。项目一（客服 RAG）、项目四（自媒体 Agent 产素材）、项目五/直播切片（ASR 转写回流）、项目六（素材中心、销售考核）、项目七（模型微调 SFT/DPO）全部从它取数或向它回流。

## 二、文字消息的构建流程（6 步主流程）

### 2.1 总流程

```
微信消息 → 工具导出 SQLite（只读）→ 转成 PostgreSQL（可读可写，原始备份）
→ ETL 脚本机器清洗 → 人工批量审核打标签 → 手动补充数据 → 清洗后的高质量元数据表 A
```

### 2.2 第一步：微信消息导出（数据抽取）

- 通过**工具**把微信消息导出为 **SQLite** 格式（本地数据库：`MSG0-5.db` + `MicroMsg.db`）。
- **只读限制**：微信原始消息数据是只读的，无法直接修改或写入。

### 2.3 第二步：SQLite → PostgreSQL（数据转换）

- 转换目的：把只读的 SQLite 数据转换为 PostgreSQL 数据，实现**可读可写**。
- 原始备份：转换后的 PostgreSQL 数据作为**原始备份**（原始库），是后续所有处理的基础。

### 2.4 第三步：ETL 脚本机器清洗

- 核心作用：ETL 脚本即数据的**机器清洗策略**，负责对原始数据做初步过滤。
- 实现方式：两种均可——**Python 脚本**，或做成**可视化界面**（方便产品/运营人员自定义清洗规则）。
- 清洗维度：
  - **时间过滤**：按时间范围筛选有效数据；
  - **关键词过滤**：剔除无关或干扰关键词；
  - **业务类型过滤**：按业务场景筛选相关数据。

### 2.5 第四步：人工批量审核 + 打标签

- 必要性：机器清洗是**死板的**，需要人工介入批量审核，弥补机器判断的不足。
- **打标签**：为数据标记业务类型，如"成交""咨询"等。
- **数据分级**：人工判断数据质量，分为**高质量、中等、垃圾数据**三个等级。

### 2.6 第五步：手动补充数据

- 补充场景一：用户从未问过、但产品实际具备的功能或信息。例：课程有八个项目、对标大厂，但用户从未问过"课程是否对标大厂"，就需要人工补充这条信息。
- 补充场景二：聊天对话中没说清楚的内容，需要人工完善补充。
- 成本定位：人力成本最高，但按需触发，适合补冷门/隐含知识。

### 2.7 第六步：输出成果

- 得到**一张清晰之后的数据表**——高质量的元数据表，作为后续所有 AI 业务的数据基础（唯一可信数据源）。

### 2.8 三种清洗手段对比

| 对比项 | 机器清洗（ETL 脚本） | 人工审核 | 手动补充 |
|---|---|---|---|
| 执行效率 | 高（批量处理） | 中（逐条审核） | 低（按需补充） |
| 准确性 | 低（规则死板） | 高（人工判断） | 最高（业务知识介入） |
| 成本投入 | 低（开发一次长期使用） | 高（人力成本） | 中（按需触发） |
| 适用场景 | 初步过滤大量数据 | 精细化打标与分级 | 补充冷门/隐含知识 |

### 2.9 六步流程小结表（讲义 22）

| 流程步骤 | 核心操作 | 具体内容 | 工具/方法 | 关键要点 | 优先级 | 难度 |
|---|---|---|---|---|---|---|
| ① 数据抽取 | 微信消息导出 | 从微信本地抽取原始消息 | 导出工具 | 导出格式为 SQLite | P0 | ★★ |
| ② 数据转换 | SQLite → PostgreSQL | 将只读数据转为可读可写 | 数据迁移 | 形成原始备份库 | P0 | ★★★ |
| ③ ETL 脚本清洗 | 机器清洗策略 | 按时间过滤、关键词过滤、业务类型过滤 | Python 脚本 / 可视化界面 | 两种方案：脚本或界面化配置规则 | P1 | ★★★ |
| ④ 人工审核 | 打标签 + 数据分级 | 人工批量审核，打业务标签（成交/咨询），分级（高质量/中等/垃圾） | 人工操作 | 弥补机器清洗的死板性 | P1 | ★★★ |
| ⑤ 手动补充 | 补充缺失数据 | 用户未问过但产品实际具备的功能/对话内容 | 人工补充 | 例：课程对标大厂等隐含信息 | P2 | ★★ |
| ⑥ 输出成果 | 高质量元数据表 | 清洗 + 审核 + 补充后的最终数据表 | 数据表 | 作为 AI 客服训练数据源 | P0 | — |

## 三、数据过滤（DataFilter）与脱敏

### 3.1 DataFilter 的定位

- 属于 **ETL 脚本的一部分**，是**策略过滤环节**，位于原始数据（PostgreSQL 存档）与业务源数据之间。
- 重要认知：**原始数据是唯一存档，保持不动**；中间用策略过滤，得到派生出来的业务源数据。`Data Filter ≠ 数据存储，而是中间过滤层`。
- 实现方式：本质上就是**一行规则词 / 一段过滤脚本**（过滤条件），或搭成可视化界面进行规则配置——不是复杂算法。

### 3.2 过滤内容

- **脱敏**：身份证号、手机号、姓名、邮箱、API Key（简历口径还有银行卡）。
- **价格信息（硬红线）**：**价格脱敏是硬红线，杜绝微调模型泄露真实定价**。
- **骂人的、不安全的、黄色等危险信息**。
- **多层冗余脱敏**：清洗时 + 写入时 + 导出时**三次**脱敏。
- **过滤维度**：时间过滤、关键词过滤、业务类型过滤。

### 3.3 多策略支持（ABC 三套策略）

- 可定义 ABC 三套策略，对应生成**三套业务源数据**，服务不同业务。
- 关键认知：**一套原始数据 + 多套策略 = 多套业务数据**，而不是维护多套原始数据。
- 举例：
  - **A 数据（对外）**：客服系统需要的数据，对外，数据更保守合规，**不需要价格信息**；
  - **B 数据（对内）**：销售培训 / 模型微调使用，更开放，可以包含价格等内部数据；
  - **C 数据**：其他业务所需数据（按需定制）。

| 对比维度 | 客服系统（A 数据） | 销售培训（B 数据） |
|---|---|---|
| 数据方向 | 对外（客户） | 对内（销售） |
| 开放程度 | 保守、合规 | 更开放 |
| 价格信息 | ✗ 不需要 | ✓ 可以有 |
| 数据用途 | AI 实时对话 | 销售考核 |
| 人工干预程度 | 高（客服语义复杂） | 中（需人工标注偏好） |
| 数据格式 | 问答对 + SKU 关联 | 完整对话（SFT）/ 偏好对（DPO） |
| 下游服务 | 客服系统实时查询 | 模型微调训练 |

## 四、一键清洗

### 4.1 核心逻辑

- **同一套清洗流程，通过配置不同策略，为不同业务产出定制化数据**。
- 数据流转链路：

```
数据源（SQLite）→ 汇聚（PostgreSQL）→ 策略 A → 机器清洗 → 人工清洗 → 人工补充 → 数据 A → 服务业务 A（客服系统）
数据源（SQLite）→ 汇聚（PostgreSQL）→ 策略 B → 机器清洗 → 人工清洗 → 人工补充 → 数据 B → 服务业务 B（模型微调 SFT/DPO）
```

- 不同业务对人工清洗和人工补充的要求不同，因此要配置不同策略，形成**多条独立的数据流水线**。
- 面试要点：区分"机器清洗"与"人工清洗"的边界——**一键清洗 ≠ 全自动，人工环节不可省略**。

### 4.2 简历版的完整工程实现（比讲义 6 步更细）

**① ETL → 原始库 → 暂存区 → 人工审核 → 多下游 的全链路流水线**

- 从微信本地 SQLite（`MSG0-5.db` + `MicroMsg.db`）抽取消息；
- 完成通讯录 **wxid → 显示名映射**、**群消息发送者解析**；
- 时间过滤与 `(session, timestamp, content)` **去重**后落 `raw_chats` 原始库（**不可变**）。

**② DataFilter 内容过滤 + 脱敏引擎**

- 按 **9 级优先级分类**：系统 / 媒体 / 过短 / 敏感 / 闲聊 / 垃圾 / 高价值…… 丢弃噪声；
- 对手机号、身份证、银行卡、邮箱、API Key 做**正则脱敏**；
- **多层冗余脱敏**（清洗时 + 写入时 + 导出时三次）；价格脱敏设为**硬红线**。

**③ 「一键清洗」对话块构建**

- 基于 **5 分钟时间窗**切分会话、合并同角色连续消息、去重；
- 做**自动预标注**（分类 / 质量分 / Q&A 提取 / 敏感标记）；
- 高质量数据进 `staging_conversations` **暂存区**，经人工 `approve / reject / 编辑` 后作为**唯一可信数据源**。

**④ 训练数据导出清洗**

- 价格脱敏、风格修复、过短过滤、过长截断、占位符清理；
- **一份数据多格式导出**：
  - `ShareGPT` / `Alpaca` / `OpenAI JSONL` → 供微调（项目七）；
  - `RAG CSV` → 供知识库（项目一）。

**⑤ 构建向量知识库下游**

- 对 `approved` 数据做 embedding（**DashScope text-embedding-v3**）写入 `knowledge_chunks`；
- 经 LLM 提炼为结构化的 `knowledge_articles`（场景 / 客户话术 / 推荐回复 / 置信度）；
- 同时为项目一 RAG 检索、项目六 AI 考核出题提供素材。

**⑥ 中台作为数据总线对接全业务**

- 项目五直播切片的 ASR 转写结果**回流入库留存**；
- 项目六素材中心的图片/视频**反向补充**多模态语料；
- 真正实现"**AI 的一切都是数据**"的闭环。

> 讲义 24 在小结表里把"一键清洗"的链路写成 `数据源 → circulate → postgres → 策略A → 机器清洗 → 人工清洗 → 人工补充 → 数据V → 服务业务`，其中 `circulate` / `数据V` 属于板书转写（推测为 SQLite / 数据表），口径与上面的 SQLite→PostgreSQL→策略A 一致。

## 五、面试必背：知识库数据量怎么"编"

> 这一节是整个项目二最容易被打穿的地方，讲义 25 给了一套**自洽的数据故事**，务必按这套讲。

### 5.1 参考数据链路

| 阶段 | 数量 | 说明 |
|---|---|---|
| 原始脏数据 | **10 万条** | 微信脏数据，来自 **5 个销售**的数据合并，人均约 **2 万条** |
| 机器清洗后 | **2 万条** | ETL 脚本按时间/关键词/业务类型过滤 |
| 人工清洗后 | **2000 条** | 人工逐条审核、打标签、分级 |
| 人工补充后 | **100~200 条** | 补充用户没问过但产品有的功能、没讲清楚的内容 |
| 最终使用量 | **2000~2500 条** | 描述 20~30 款商品 |

### 5.2 数据与商品的对应关系

- 最终数据对应 **20~30 款商品**，用于构建 RAG。
- 构建 RAG 导出后**还会人工审核一遍**，最终约 2000 条数据描述商品信息。
- 平均一款商品约 100 条数据；**有重复很正常**，因为同一句话有多种表达方式（问法不同）。
- 灵活调整：也可以说 50 条、20 条、30 条都行，**关键是说得像真的**。

### 5.3 讲故事的几条纪律

- 数据规模要**自洽**：人均 2 万条 × 5 人 = 10 万条，避免前后矛盾。
- 清洗比例要**合理**：机器洗掉约 80%（10 万 → 2 万）、人工再洗掉约 90%（2 万 → 2000），**不能跳跃过大**。
- RAG 构建环节的**人工审核不可省略**，体现严谨性。
- 核心是**自圆其说**，数据范围可弹性调整；可以把这段故事丢给 AI 帮忙完善细节，让它更真实可信。

### 5.4 不同业务的"训练数据要不要价格"

- A 数据（客服 RAG）：对外，价格信息不需要（或脱敏）。
- B 数据（销售培训 / 模型微调）：对内，价格、成本、底价可以包含。
- 重要：销售考核的培训数据**必须包含产品价格、成本、底价**，否则销售无法回答客户"400 能不能卖"这类问题，容易导致亏损（详见项目六）。

## 六、数据格式认知（RAG / SFT / DPO）

面试准备要点：要明确数据中台导出的**各类数据格式**，即使面试官通常不会追问客服数据的细节，也要有整体认知。数据形态可直接向 AI 提问了解标准格式。

| 数据类型 | 格式特征 | 用途 |
|---|---|---|
| **RAG 知识库数据** | 客服系统的知识库数据格式（问答对 + 商品 ID + embedding） | 项目一 RAG 检索 |
| **SFT 数据** | **一整段完整对话**，多轮上下文，保留销售话术风格；形态为简单 QA 问答对或上下文对话（JSON 示例可向 AI 获取） | 模型监督微调（项目七） |
| **DPO 数据** | **一问一答 + 好的回答 + 坏的回答**（成对样本，偏好对齐） | 模型偏好对齐（项目七） |

补充口径（讲义 24 小结）：

- SFT "教你成才"——完整对话训练；
- DPO "教你成人"——同一问题下"好回答 vs 坏回答"的配对数据。
- 中台清洗产出的是**高质量数据，本身不含坏回答**，所以 DPO 必须额外人工构造负样本（详见项目七）。

## 七、中台与其它项目的联动（闭环）

### 7.1 素材管理中心 → 数据中台 → 客服系统

- 素材管理中心的数据（图片、视频、文字）可以**补充到数据中台**；
- 输出图片、视频，补充为**数据 A**，服务客服系统（客服系统本来就是三套数据：文字、图片、视频）。

### 7.2 自媒体运营系统 → 素材管理中心 → 数据中台

- 自媒体运营系统生成的商品图片提供给素材管理中心；
- 与 **SKU ID 挂钩**，补充到数据中台，与客服系统打通；
- 用户提问后，先做**意图识别**，识别到 SKU ID，获取商品上下文，**再查询数据**（链路顺序不可颠倒）。

### 7.3 直播切片 → 数据中台

- 直播切片的 ASR 转写结果**回流入库留存**，为后续内容分析 / 训练备用。

### 7.4 8 个项目统一架构（讲义 24 的口径）

讲义 24 列的 8 个项目编号与简历的 7 项目编号不同，此处照录，仅作"数据流"理解：

| 讲义编号 | 项目 | 与中台的关系 |
|---|---|---|
| 项目 1 | 实时语音对话 RAG | 消费数据 A |
| 项目 2 | 自媒体生图、生视频 | 生成素材回填 |
| 项目 3 | 直播切片 | ASR 结果回流 |
| 项目 4 | 数据中台 | 本体 |
| 项目 5 | AI 素材管理 Agent | 补充多模态语料 |
| 项目 6 | 销售考核 Agent | 消费数据 B |
| 项目 7 | MCP 和 Agent 集群 | 底座 |
| 项目 8 | 模型微调 | 消费 SFT/DPO |

核心逻辑：**数据中台是航空母舰，各业务系统是舰载机**，统一停靠与补给；把架构理清后，所有项目都是**一套逻辑**。

## 九、高频面试问答速记

**Q1：数据中台的价值是什么？**
A：它是整个 AI 体系的底座。所有 AI 业务（客服、微调、考核、素材、直播）都从这里取数；把微信原始记录加工成可训练、可检索、可考核的高质量数据资产。项目也因为"原来每次都要程序员导数据"这个痛点而生，后来让运营/销售自己就能导出清洗。

**Q2：数据流是怎么走的？**
A：微信消息 → 工具导出 SQLite（只读）→ 转 PostgreSQL（可读可写，作原始备份）→ ETL 脚本机器清洗（时间/关键词/业务类型过滤）→ 人工批量审核打标签（成交/咨询，高/中/垃圾分级）→ 人工补充（用户没问过的功能、没说清的内容）→ 输出一张高质量元数据表。

**Q3：原始数据会不会被改动？**
A：不会。原始数据（PostgreSQL 存档）**保持不动**，它是唯一存档；中间用 DataFilter 策略脚本过滤，得到的是**派生**出来的业务源数据。

**Q4：DataFilter 是怎么实现的？**
A：本质就是规则词 + 脚本（或在可视化界面配置规则），不是复杂算法。过滤身份证、手机号、姓名、邮箱、API Key、价格、辱骂和不安全内容。

**Q5：一套数据怎么服务多个业务？**
A：一套原始数据 + 多套策略。策略 A 产出对外的客服数据（保守合规，不要价格），策略 B 产出对内的微调/培训数据（含价格），需要多少业务就配多少策略。

**Q6：一键清洗是全自动的吗？**
A：不是。机器清洗之后必须人工审核、打标、分级，再人工补充冷门知识。一键清洗指的是"一套流程 + 可配置策略"，人工环节不可省略。

**Q7：知识库有多少条数据？（务必按第六节口径回答）**
A：5 个销售人均 2 万条合并成 10 万条脏数据，机器清洗剩 2 万，人工清洗剩 2000，人工补充 100~200 条，最终 2000~2500 条，对应 20~30 款商品，平均每款约 100 条，重复是同一句话的不同表达。

**Q8：SFT 和 DPO 数据长什么样？**
A：SFT 是一整段完整对话（多轮上下文，保留销售话术风格）；DPO 是一问一答 + 好回答 + 坏回答的成对样本。中台清洗产出的是高质量数据，DPO 的坏回答必须人工补充。

**Q9：中台和其它项目怎么联动？**
A：向下供 A 数据给客服 RAG、B 数据给销售考核与模型微调；向上接受素材中心的图片/视频补充、直播切片的 ASR 转写回流、自媒体 Agent 生成的商品素材（按 SKU ID 挂钩），形成"AI 的一切都是数据"的闭环。

**Q10：这个项目技术上难吗？**
A：技术上不算难，难在业务策略——清洗规则、脱敏红线、数据分级、多业务分流。数据中台本质是一个业务系统。

## 十、易混淆点自查

- `Data Filter` 是**中间过滤层**，不是数据存储。
- 原始数据是**唯一存档**、不可变；业务数据是**派生结果**。
- **一套原始数据 + 多套策略 = 多套业务数据**，不是多套原始数据。
- 一键清洗 ≠ 全自动，人工清洗/人工补充不可省略。
- 对**客服（对外）更保守合规**，对**销售培训（对内）更开放**。
- SFT = 完整对话；DPO = 一问一答 + 好坏回答配对。
- 数据量故事要自洽：10 万 → 2 万 → 2000 → 2000~2500 条 → 20~30 款商品。
