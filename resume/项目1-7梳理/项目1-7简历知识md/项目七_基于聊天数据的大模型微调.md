## 一、要解决的问题与定位

### 1.1 为什么需要微调

- **核心痛点：AI 味太重，影响用户体验。**
- 用 RAG 知识库只是**让模型"模仿"专家**——就像"模仿会导致大模型说着说着忘了自己是武汉人"，模型在长对话中会忘记自己的身份设定（角色漂移）。
- **微调的本质**：让模型**真正"变成"某个领域的专家**（如真正成为武汉人），改变模型参数与"血液"。
- **微调的核心收益**：用户体验更好、回答更稳定。

| 对比项 | 模型微调 | RAG 知识库 |
|---|---|---|
| 本质 | 改变模型参数与"血液" | 外部挂载知识检索 |
| 持久性 | 长期稳定，不会遗忘 | 临时调用，可能"说着说着忘了" |
| 用户体验 | 更优，角色代入感强 | 一般，存在角色漂移风险 |
| 数据要求 | 需 SFT + DPO 成对数据 | 需结构化知识文档 |

### 1.2 现实定位（面试要诚实）

- **真正做微调的企业很少，RAG 能解决 99% 的问题**；模型微调更多是**展示技术能力**，成本高且效果不一定好。
- 但仍要关注官方最新版本（如豆包 2.0），面试可能被问及使用的具体版本。
- **核心原则**：模型微调一定要真正实现**降本增效**，否则就是**秀操作**。

### 1.3 在 8 个项目中的定位

- 底座项目（绿色标识），与 MCP 集群并列，构成底层基础设施。
- 简历口径的职责分离："**微调管风格、RAG 管知识**"——SFT 数据（保留多轮上下文学销售话术风格）与 RAG 知识库数据（提炼课程、价格、优惠等结构化知识）分流，**知识更新只改知识库无需重训**。

## 二、两种训练数据：SFT 与 DPO

### 2.1 数据准备总览

- 需要准备 **SFT（监督微调）** 和 **DPO（直接偏好优化）** 两类数据。
- 数据源：**SFT 来自数据中台清洗（approved 的 ShareGPT / OpenAI 格式数据）**；**DPO 初稿来自中台清洗，但需要人工补充"坏的回答"**。

### 2.2 SFT（监督微调）

- **作用**：让模型模仿标准答案，学会"说对话"（学话术、懂业务）——解决"**从不会到会说**"的风格模仿问题。
- **核心逻辑**：只要输入 Prompt，就必须输出 Response。
- **数据结构**：简单的 QA 问答对，或**上下文对话（一整段完整会话）**，包含用户提示词与模型回复。
- **示例**："我是卖鞋子服装的，想进行模型微调"——一整段完整对话，保留多轮上下文与销售话术风格。

### 2.3 DPO（直接偏好优化）

- **作用**：让模型在两个答案中学会"趋利避害"，把话说漂亮（学情商、提转化、规避客诉）——解决"**会说但说不好**"的问题。
- **核心逻辑**：输入 **Prompt + 好的回答（Chosen）+ 差的回答（Rejected）**。
- **无需奖励模型**：直接通过"三元组"数据告诉模型哪个回答优秀、哪个回答糟糕（**不需要复杂的 Reward Model**）。
- **数据格式**：

| 字段 | 含义 |
|---|---|
| `Prompt` | 用户输入的问题 |
| `Chosen` | 优秀的回答（由销售主管标注） |
| `Rejected` | 糟糕或及格线以下的回答 |

- **好坏对比**：好的回答（chosen）体现共情与安抚；坏的回答（rejected）生硬、缺乏同理心。

**DPO 示例（鞋服电商场景）**：

- Prompt：买家反馈鞋子味道大，是不是假货？
- Chosen：亲亲，非常抱歉给您带来不好的体验。新鞋出厂后直接密封包装，可能会残留一些环保胶水的气味。
- Rejected：不可能，我们家都是正品。新鞋子有胶水味很正常，放通风处吹吹就好了，不是假货。

**Rejected 常见问题**：生硬顶撞客户、长篇大论没有重点、漏掉利益点（运费险、优惠券）、推卸责任。

### 2.4 数据来源与生成流程

- **SFT 数据来源**：通过中台清洗获得（高质量、多轮完整对话）。
- **DPO 数据来源**：初稿由中台清洗，但**必须人工补充"坏的回答"**。
  - 原因：**中台清洗的是高质量数据，本身没有坏的回答**；而 DPO 需要成对的好/坏回答，因此必须人工构造或补充 Rejected 部分。
- **DPO 数据生成流程**：中台清洗出好的回答（chosen）→ 人工补充坏的回答（rejected）→ 形成完整的 DPO 三元组数据。

### 2.5 为什么要 SFT 之后再做 DPO

- SFT 解决"**从不会到会说**"（风格模仿）；DPO 解决"**会说但说不好**"（优劣区分）。
- 选 DPO 而非 RLHF：**DPO 跳过奖励模型训练**，在偏好数据有限（几百条）时更稳定、成本更低。

### 2.6 SFT / DPO 对照

| 对比项 | SFT | DPO |
|---|---|---|
| 数据形态 | 一整段完整对话（多轮上下文） | 一问一答 + 好回答 + 坏回答（三元组） |
| 解决什么 | 不会 → 会说（风格模仿） | 会说 → 说得好（偏好对齐） |
| 是否需要负样本 | 不需要 | **必须有**（人工构造） |
| 是否有奖励模型 | 不需要 | 不需要（直接偏好优化） |

## 三、两阶段训练策略：本地验证 + 云端训练

### 3.1 策略

- **本地小模型验证 + 云端大模型训练**。
  - **本地验证**：早期阶段在本地搭建 **LLaMA-Factory** 环境，用**少量数据快速验证数据准备和训练方向是否 OK**。
  - **云端训练**：本地验证通过后，将大量数据上传至云端进行**生产级模型训练**。
  - 原因：云端训练速度慢且需要准备大量数据，本地验证可以**快速迭代、降低成本**。
- **先后逻辑**：**本地验证 OK 之后才上云**，而不是同时进行。

### 3.2 本地 vs 云端参数与数据量对照

| 对比维度 | 本地训练 | 云端训练 |
|---|---|---|
| 训练目的 | 验证数据质量与训练方向 | 生产级模型微调 |
| 数据规模 | **SFT 300~500 条 + DPO 100~200 对**（总结口径：SFT 300 条 + DPO 200 条） | **SFT 2000~5000 条（可表述为 3000 条）+ DPO 500~1000 对（可表述为 1000 对）** |
| 模型版本 | **Qwen2.5-3B-Instruct（也可用 7B）** | **豆包 1.6**（当前最新 2.0；简历建议写 1.6） |
| 平台 | **LLaMA-Factory** / 单卡 **RTX 4090（也有口径写 7090）** | **火山引擎方舟** |
| 训练方法 | **QLoRA**（rank=64, alpha=128, lr=2e-4，也可 1e-4~2e-4） | **LoRA**（rank=32, lr=1e-5；另有口径 lr 5e-5~1e-4） |
| 训练时长 | 约 **40 分钟/轮** | 未明确（云端较慢） |
| 成本效益 | 低成本快速验证 | 高成本大规模训练 |
| 效果 | 风格一致性人工盲评从 2.1 → 4.3（5 分制） | 直接上线（灰度） |

### 3.3 数据量规划

- **本地 SFT 300~500 条**：验证数据格式是否通、模型是否收敛、掌握基本设置。
- **本地 DPO 100~200 对**：验证 DPO 训练效果，观察语气是否明显改变。
- **云端 SFT 2000~5000 条**：让模型深入学习店铺的复杂业务对话和鞋帽知识。
- **云端 DPO 500~1000 对**：全面提升销售转化能力和品牌话术。
- 备注：大纲给的另一口径是"本地 SFT 300 条、DPO 200 条；云端 SFT 3000 条、DPO 1000 条"，与上表一致。

### 3.4 模型选择：Lite 与 Mini

- **功能层面**：两者支持完全相同的输入/输出模态（文本/图片/视频/音频 → 文本），精调类型和计费方式也完全一致。
- **核心区别**：主要体现在模型体量（参数量）、性能侧重和价格成本上。

| 版本 | 定位 | 特点 | 适用场景 |
|---|---|---|---|
| **Lite**（轻量平衡版） | 性价比与能力平衡 | 保持较强理解能力（复杂逻辑、多轮对话、复杂客诉意图分析）；响应速度快、Token 成本低 | 主线 AI 客服系统的**核心大脑** |
| **Mini**（极致轻量版） | 更快更便宜 | 比 Lite 更小、更快、更便宜，参数量进一步缩减；首字延迟（TTFT）极低，近乎瞬时秒回 | 单一、机械、高频的单轮对话（如快捷短语回复、尺码表查询、情感极性过滤） |

- **选型建议**：鞋服客服场景使用 **Lite** 版本即可满足需求。

### 3.5 火山的模型精调功能

- **功能位置**：火山方舟控制台 → **模型广场** → 搜索模型 → 进入"**创建精调任务**"。
- **支持的精调类型**：**SFT、DPO、强化学习（GRPO）**。
- **训练方法**：**LoRA、全量训练**。
- **模型选择**：支持豆包系列模型（如 Doubao-Seed-2.0-lite、Doubao-Seed-2.0-mini；此前为 1.5 / 1.6 版本）。
- **界面需关注的关键配置**：训练方式、数据集、训练配置。
- **成本认知**：**尝试微调的成本很低，十几块钱就可以跑一次实验**，鼓励亲自上手研究。
- **模型更新频率**：大模型更新速度快（1.5 → 1.6 → 2.0），**每次升级都需要重新训练，成本较高**。
- **简历建议**：简历建议写 **1.6 版本**而非最新的 2.0，因为新版本刚出，项目需要训练和运行一段时间才合理。

## 四、LoRA 与 QLoRA

### 4.1 LoRA（低秩适应）

- **本质**：模型微调是"**修修补补**"，而非"推倒重建"。
  - 比喻：房子哪里不好，就拆掉哪里重新装，而不是推倒重建整栋房子。
- **成本**：只调整少量参数，**不改变基座模型的大部分权重**。
- 简历口径：对预训练模型做"修修补补"，而非从零训练。

### 4.2 QLoRA（量化低秩适应）

- **本质**：在 LoRA 的基础上，**对基座模型进行量化**。
- **做法**：将模型精度从 **16 位（FP16/BF16）压缩到 4 位（4-bit NF4）**。
- **目的**：**降低显存占用**，让消费级显卡也能运行微调。

### 4.3 LoRA vs QLoRA 详细对比

| 对比项 | LoRA | QLoRA |
|---|---|---|
| 模型精度 | **16 位**（保持原样） | **4 位**（极致压缩） |
| 显存占用 | 高（对本地显卡压力大） | **极大降低**（能砍掉接近一半显存占用） |
| 训练速度 | 快（计算直接，无解压过程） | 稍慢（计算时需频繁做 4-bit → 16-bit 转换） |
| 精度损失 | **无损** | 有**微妙损失**（在极微妙的语气控制上有损失，但本地验证模型质量完全没问题） |
| 硬件要求 | 显存较宽裕的显卡或专业计算卡 | 消费级显卡甚至高端笔记本也能跑（8G/12G/16G 显存） |
| 成本 | 较高 | 较低 |
| 适用场景 | 云端/线上生产 | 本地验证/低显存环境 |

### 4.4 实践策略

- **本地验证用 QLoRA**（省显存，单卡 RTX 4090 快速验证数据质量）；
- **线上生产环境用 LoRA**（保效果，无精度损失），在火山引擎方舟做生产级微调。

### 4.5 参数示例（面试常见口径）

- 全局参数：**rank=64、alpha=128**（"二一杠四"的口播），配合 lr 2e-4。
- 云端正式：**rank=32、alpha=64、lr=1e-5**。

## 五、核心训练参数（面试重点）

### 5.1 五个核心参数总览

| 参数名称 | 本地验证阶段（Qwen2.5-7B + QLoRA） | 云端正式环境（豆包 1.6 + 标准 LoRA） | 为什么这么设置 |
|---|---|---|---|
| 1. 训练轮次（Epochs） | **3~5 轮** | **2~3 轮** | 本地数据少，需要多轮深刻记忆；云端数据多，轮次多易过拟合 |
| 2. 批次大小（Batch Size） | **1 或 2** | **8 或 16**（参考默认值） | 本地受限于显存只能设小；云端显存充裕，设大能让梯度更新更平稳 |
| 3. 学习率（Learning Rate） | **2e-4（0.0002）** | **5e-5（0.00005）** | 本地 4-bit 量化的 QLoRA 需要较大学习率快速收敛；云端 16-bit 标准 LoRA，5e-5 是最安全的甜点值 |
| 4. LoRA Rank（秩） | **64** | **32** | 本地用大 Rank 开辟更大容量，强行注入话术；云端面对大模型和丰富数据，32 的容量刚刚好 |
| 5. LoRA Alpha（缩放系数） | **128** | **64** | 严格遵循 Alpha = 2 × Rank 的黄金比例，确保调整 Rank 时模型风格稳定 |

- **核心避坑提醒**：在火山引擎上点火时，**务必检查最大文本长度（Max Length）**。对于服饰客服的多轮长对话，**建议设为 4096**，绝对不要用 512 或 1024，防止对话被截断。
- **面试讲故事**：能说清楚这五个参数在本地和云端为什么设置不同，并解释背后的道理（数据量、显存、量化方式等），比死记硬背数字更重要。

### 5.2 训练轮次（Epochs）

- **定义**：控制模型完整遍历训练数据的次数。
- **场景建议**：对于服饰客服这类特定话术注入的场景，官方建议设置在 **2~3 轮**，避免过度训练导致模型丧失电商泛化能力。
- **本地 vs 云端**：
  - 本地验证（300~500 条数据）：建议 **3~5 轮**——数据量少，需要更多轮次让模型充分记住特定话术；
  - 云端正式（2000~5000 条数据）：建议 **2~3 轮**——数据量大，轮次过多容易导致模型变成"复读机"（过拟合）。

### 5.3 批次大小（Batch Size）

- **定义**：单步训练时模型同时处理的样本数量。
- **类比**：就像看书，一眼看一页（大 Batch Size）还是一眼看一行（小 Batch Size）。
- **默认值**：通常使用默认值即可，一般为 **8 或 16**。
  - 算力紧凑/单卡：设为 8；
  - 算力充裕/大卡：设为 16。
- 本地受限显存只能设 1 或 2。

### 5.4 学习率（Learning Rate）

- **定义**：控制模型参数更新的步长，是精调最核心的参数。
- **LoRA 场景建议**：使用 LoRA 微调时，学习率不能太小，建议在 **5e-5 到 1e-4 之间**。
- **甜点值**：**5e-5 是一个非常安全的起始值**，既能有效学习话术风格，又不容易导致训练崩盘。
- **对比**：全量微调通常使用更小的学习率（如 1e-5），LoRA 需要更大的学习率来快速适应新任务。
- **本地**：使用 4-bit 量化的 QLoRA，需要更大学习率来弥补精度损失（2e-4，另有口径 1e-4）。

### 5.5 LoRA Rank（秩）

- **定义**：决定外挂低秩矩阵的**参数容量**，可以理解为"**备忘录的厚度**"。
- **可选值**：通常包括 **8、16、32、64** 等；默认值通常为 32，一般不需要频繁改动。
- **作用**：Rank 越大，投影矩阵放得越大，模型能学习到的参数越多；但算力消耗也越大。
- **配置建议**：
  - 本地验证：可用 **64**，开辟更大容量强行注入话术；
  - 云端正式：用 **32** 即可，容量刚刚好，模型既聪明又不会死板；
  - 针对豆包 1.6 这类中大型模型 + 几千条多轮对话数据，手动调整为 32 是非常稳妥的选择。

### 5.6 LoRA Alpha（缩放系数）

- **定义**：控制 LoRA 权重对基座模型的**影响权重**，可以理解为"**扩音器的音量**"。
- **黄金比例**：业界公认的稳定公式是 **Alpha = 2 × Rank**。
- **作用**：保持这个比例，当你以后调整 Rank（容量）时，模型的学习率和风格稳定性不会崩。
- **配置示例**：
  - Rank=32，Alpha=64（云端推荐）
  - Rank=64，Alpha=128（本地推荐）
  - 也可以遵循 Alpha = Rank 的原则配置（如 Rank=32 时 Alpha 也设为 32）
- **错误示例**：Rank 降到 32，但 Alpha 忘记改，依然保留 128，此时比值变为 4，模型会变得**极度激进，容易过拟合**。
- **易混点**：alpha 与 rank 的**比值**影响微调强度。

### 5.7 面试官可能追问的"为什么"

带着这些问题去问 AI、去理解，比背数字更重要：

- 为什么本地训练轮次是 3~5 轮？为什么批次大小是 1 或 2？
- 为什么学习率是 5e-5 到 1e-4？为什么 Rank 是 32？为什么 Alpha 是 64 或 128？
- 本地和云端为什么参数设置不同（数据量、显存、量化方式）？

## 六、验收标准：本地怎么验

### 6.1 目标

- 本地数据量少（**300~500 条**），主要用于 **MVP 验证**，即**验证微调思路是否正确**；核心看模型是否"**人味更重**"，不用太看重数据准确性，因为本地数据不如线上全。

### 6.2 方法：人工盲评（双盲测试）

1. **留出测试集**：训练前故意扣下 **10%~15% 的优质数据（如 50 条问答）**不参与训练，专门用于考试。
2. **双盲测试流程**：将同一个测试问题**同时喂给"未训练的 Qwen"和"微调后的 Qwen"**，**隐藏模型名字**，让优秀客服进行 **5 分制打分**。
3. **核心逻辑**：就像两杯酒（100 元和 500 元），遮住价格后能喝出 500 元的更好，说明它确实好。

### 6.3 评分标准（5 分制）

| 分数 | 表现 |
|---|---|
| **1 分（不及格）** | 依然是通用模型的回答，或者出现格式错乱、开始复读 |
| **3 分（及格线）** | 能稳定使用"亲亲""宝子"等电商客服语气开头；能准确从喂给它的数据里提取尺码表和面料知识 |
| **4 分以上（优秀）** | 语气到位，遇到客诉时表现出明显的 **DPO 倾向**（不再硬怼，而是高情商话术安抚，并主动提及运费险或售后保障） |

- **本地预期目标**：人工盲评综合得分能从 **2 分左右稳定提升到 4 分以上**，即可判断本地数据质量完全过关，可以打包上云。

## 七、验收标准：云端怎么验

### 7.1 目标

- 云端面对**几千条多轮对话**精调出来的豆包，目标是**直接上线**；评估要从"**模拟考**"走向"**实战演练**"。

### 7.2 怎么测

**① 准备测试用例（压力测试集）**

- 准备 **50 个**服饰行业最容易翻车的**客诉和逼单场景**，例如：
  - "衣服洗了一次缩水成狗，你们赔不赔？"
  - "别家便宜 20 块钱，你给我便宜点我就拍。"
- 测试用例的构成：
  - **高频问题**：准备尽量覆盖全场景的 **100 道**高频问题；
  - **多轮会话测试**：进行多轮对话，测试模型上下文保持能力；
  - **幻觉测试**：问数据源里没有的问题，看模型会不会瞎编。

**② 火山方舟平台对比评估（Model Evaluation）**

- 火山引擎后台支持**模型评测（Model Evaluation）**功能；
- 操作：创建一个评测任务，导入压力测试集，让"微调后的豆包"和"豆包基座模型"**同屏竞技**，做**胜率对比（Win / Tie / Lose）**。

**③ 业务指标是否真的提升**

- **成交率**、**投诉率**。

### 7.3 云端达到预期的标准（三大核心指标）

| 指标 | 含义 | 判定 |
|---|---|---|
| **多轮遵循能力（不跑调）** | 在拉扯 5 轮以上的对话中，能不能死死咬住鞋服客服人设？有没有被"请帮我写一段 Python 代码""谈谈你对当前经济的看法"给拐跑？ | 能拒绝回答无关问题或巧妙绕回商品销售，说明指令遵循过关 |
| **业务幻觉率（不瞎编）** | 测试它没学过的新款式，故意问它没有的信息 | 应话术化回答"亲亲，这款商品详情正在紧急更新中，您可以先参考我们的标准运动鞋码哦"，而不是自己瞎编面料或尺码 |
| **DPO 扭转率** | 对比基座豆包，微调后的豆包在面对差评、退换货时的客诉率是否大幅降低，销售逼单的转化感是否明显变强 | 客诉率降低、转化感增强 |

### 7.4 终极验收清单（达到以下 3 点，直接上线）

1. **语气一致性**：无论是问尺码还是问发货，模型吐字风格 **100%** 保持品牌要求的调性。
2. **核心业务 0 差错**：涉及店铺核心政策（如 7 天无理由、赠送运费险、特定面料洗涤注意项），AI 的回答**完全符合事实**。
3. **情商在线**：面对顾客退换货和质疑，模型首先进行**情感安抚（Chosen 话术）**，没有出现任何一句**生硬反驳（Rejected 话术）**。

### 7.5 通过标准

- 如果在云端经过火山评测，微调后的豆包在压力测试集上的**胜率超过 80%**，且**盲评接近 4.5 分**，就可以放心地接入**灰度流量**，让它去接待真正的买家。

### 7.6 本地 vs 云端验收对照

| 对比维度 | 本地模型 | 云端模型 |
|---|---|---|
| 数据量 | 少量（验证思路） | 真实几千条（压力测试） |
| 评估方法 | **双盲测试（人工盲评）** | **火山引擎平台评测 + 业务指标** |
| 核心关注点 | 是否表现出 **DPO 倾向** | **业务指标**是否真实提升（成交率、投诉率） |
| 测试类型 | 模拟考（思路验证） | 实战演练（压力测试） |
| 验收标准 | 全量数据模型效果优于残缺数据 | 微调后模型在业务指标上优于未微调模型 |

### 7.7 模型微调的终极目标

> 模型微调一定要**真正实现降本增效**，否则就是秀操作。技术指标通过 ≠ 业务指标提升，需以**实际业务效果**为最终验收标准。

## 八、模型接入：回灌 AI 客服（闭环）

- **微调后的模型作为 LLM 层**接入项目一的 RTC 实时语音链路：

```
客户语音 → ASR → RAG → 微调 LLM → TTS → 语音回复
```

- **通过微调缩短 system prompt 进一步降低 TTFT**，在实时对话场景下保障体验。
- 完成"**数据中台 → 微调 → 客服**"的回路闭合，确保数据持续优化、模型持续迭代。
- 配套的 RAG Pipeline（简历第 4 条）：**Embedding → 向量检索 → Rerank** 三阶段——火山引擎 Embedding 向量化 + 向量检索 **top-20** 粗召回，引入 **Cross-Encoder** 精排取 **top-5**，解决双编码器在语义相近文档上区分度不足的问题，知识命中率从 **72% 提升至 89%**。
  - **口径提示**：这一条与项目一"K=15、N=3、base-rerank、2500 条数据不需要额外优化"的口径不一致；如果被追问，要能说清"这是微调链路侧的独立评测数据/另一套口径"，否则建议弱化具体数字。

## 十、高频面试问答速记

**Q1：为什么要做模型微调？RAG 不够吗？**
A：RAG 是让模型"模仿专家"，说着说着会忘了身份设定，AI 味重；微调是让模型真正变成这个领域的专家，参数里就有这个人设，回答更稳定。不过企业里其实 RAG 能解决 99% 的问题，微调更多是提升体验的加分项——所以我们的分工是"微调管风格、RAG 管知识"，知识更新只改知识库，不用重训。

**Q2：SFT 和 DPO 的区别？**
A：SFT 是一整段完整对话，解决"不会 → 会说"的风格模仿；DPO 是一问一答加好回答加坏回答，解决"会说 → 说得好"的偏好对齐。SFT 之后的模型只是会说，语气情商还不行，所以再做 DPO。

**Q3：DPO 的数据怎么来？**
A：好的回答来自数据中台清洗的高质量对话，但中台的数据里根本没有坏回答，所以必须人工补充 Rejected——常见问题是生硬顶撞客户、长篇大论没重点、漏掉运费险和优惠券、推卸责任。

**Q4：为什么选 DPO 不选 RLHF？**
A：DPO 跳过了奖励模型训练，直接用偏好对告诉模型哪个好哪个差，在偏好数据只有几百条时更稳定、成本更低。

**Q5：为什么先本地再云端？**
A：云端训练慢、数据要求多；本地用 LLaMA-Factory + Qwen2.5 + QLoRA 只要几百条数据、单卡 4090 跑 40 分钟一轮，就能验证数据格式和方向对不对，验证 OK 再上云做豆包的生产级 LoRA。顺序不能反。

**Q6：LoRA 和 QLoRA 的区别？**
A：LoRA 是"修修补补"——只训少量参数、不改基座权重，16 位精度，无损但要显存；QLoRA 是在 LoRA 基础上把基座量化到 4-bit，显存砍掉差不多一半，消费级显卡就能跑，代价是语气控制上有微妙损失。所以本地验证用 QLoRA、线上生产用 LoRA。

**Q7：五个核心参数为什么本地云端不一样？**
A：轮次本地 3~5、云端 2~3——本地数据少要多记几遍，云端数据多跑多了会变复读机；batch 本地 1~2（显存限制）、云端 8~16（默认值，梯度更平稳）；学习率本地 2e-4（4-bit QLoRA 要更大学习率弥补精度损失）、云端 5e-5（16-bit 标准 LoRA 最安全的甜点）；rank 本地 64（大容量强行注话术）、云端 32（容量刚好）；alpha 严格按 2 倍 rank（128 / 64），否则比例失真模型会过拟合。

**Q8：Rank 和 Alpha 是什么关系？**
A：Rank 是外挂矩阵的容量，相当于"备忘录的厚度"；Alpha 是缩放系数，相当于"扩音器音量"。黄金比例是 Alpha = 2 × Rank。如果 Rank 从 64 降到 32 但 Alpha 还留在 128，比值变成 4，模型会变得极度激进、容易过拟合。

**Q9：本地怎么验收？**
A：留出 10%~15% 的优质数据（约 50 条）不参与训练做考试；双盲测试——同一问题同时喂给未训练的 Qwen 和微调后的 Qwen，隐藏模型名，让优秀客服 5 分制打分。1 分是不及格（还是通用回答、格式乱、复读），3 分及格（能稳定用"亲亲""宝子"开头、能准确提取尺码面料），4 分以上优秀（遇到客诉有 DPO 倾向、主动提运费险售后）。目标是从 2 分左右稳定到 4 分以上。

**Q10：云端怎么验收？**
A：准备 50 个服饰行业最容易翻车的客诉和逼单场景做压力测试集，导入火山方舟的 Model Evaluation，让微调后豆包和基座豆包同屏竞技做胜率对比。看三个指标：多轮遵循能力（5 轮以上不被"帮我写 Python"拐跑）、业务幻觉率（新款式应话术化兜底而不是瞎编）、DPO 扭转率（客诉率降、逼单转化强）。最终验收清单是语气一致性 100%、核心业务 0 差错、情商在线。胜率超 80%、盲评接近 4.5 分就可以灰度上线。

**Q11：怎么防止模型不瞎编？**
A：微调解决风格和话术，不让它承担知识更新的职责——知识类回答还是走 RAG；验收时专门测幻觉：问它没学过的新款式，要求它话术化兜底"详情正在紧急更新，您可以先参考标准运动鞋码"，而不是编造面料。

**Q12：你用的哪个版本？**
A：项目上用的是豆包 1.6（简历写 1.6），因为 2.0 刚发布，项目需要训练和运行一段时间才合理；新版本出来重新训练是有成本的。本地用 Qwen2.5-3B/7B。

## 十一、易混淆点自查

- **微调 = 改变模型本质（血液）；RAG = 临时模仿（表演）**，会说但会忘。
- **SFT → DPO** 是先后关系，不是二选一；DPO 不能替代 SFT。
- **中台清洗出的是高质量数据，不含坏回答**，所以 DPO 必须人工造负样本。
- **QLoRA 用于本地（省显存）**，**LoRA 用于生产（保效果）**。
- **Alpha = 2 × Rank** 是黄金比例，单独改 Rank 不改 Alpha 会出问题。
- Max Length 在服饰多轮对话场景要设 **4096**，不要用 512/1024。
- 本地看"人味"，云端看"业务指标"——**技术指标通过 ≠ 业务指标提升**。
- 火山精调在**方舟控制台 → 模型广场 → 创建精调任务**，支持 SFT / DPO / 强化学习（GRPO）。
