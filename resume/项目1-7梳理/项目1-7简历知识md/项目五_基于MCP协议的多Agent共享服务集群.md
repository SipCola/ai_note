# 项目五：基于 MCP 协议的多 Agent 共享服务集群

> 素材来源：`项目1-7简历知识大纲.md`、`项目1-7简历参考.md`，以及配套讲义《33 MCP集群1》《34 MCP集群2》《35 MCP集群3》《36 MCP集群4》《32 自媒体运营Agent5》（架构收口部分）、《02 将8个项目完全串联起来》《03 如何向面试官介绍我们的8个项目》。
> 本文只做归纳整理，所有数字与结论均出自上述材料；讲义里项目名叫"Rug服务"的地方是 MCP 之 **RAG 服务**的口误转写，正文一律按 RAG 表述。

## 一、项目定位

- **业务场景**：公司有 8 个业务项目，MCP 服务有几十个甚至上百个（LLM、RAG、Prompt 管理及其他通用服务）。
- **核心思想**：随着 AI 项目越多，做**架构层面的统一收口**——把 LLM 网关、RAG、记忆、Prompt 抽成**共享基础设施**，让所有业务（含数据中台）复用同一套底座。新业务接入仅需写 Agent 编排层。
- **项目动机**：项目众多，存在大量通用的 MCP 服务和 Agent 服务，需要抽离成公共基础架构来支撑整个 AI 生态体系。
- **在 8 个项目中的定位**：基础设施层（底座），与模型微调一起构成底层基础设施，贯穿并服务全部 8 个项目。
- **架构演进视角**：从"每个项目各自造轮子"到"统一收口成共享服务集群"，这是架构师视角的体现。

## 二、整体架构：网关 + 四类核心 MCP 服务 + 其他通用服务

### 2.1 业务项目与 MCP 服务的调用关系

- 8 个业务项目**需要调用这些 MCP 服务，但不能直接调用，必须经过网关层**。
- 网关层四件套：**认证、日志、限额、路由**。
- 四类核心 MCP 服务：
  1. **LLM MCP 服务**（大模型统一调用）
  2. **RAG MCP 服务**（知识检索增强）
  3. **Prompt 提示词管理**（系统提示词统一管理）
  4. 其他通用 MCP 服务（如**用户会话管理**）

### 2.2 四类核心组件职责对比（讲义 33 小结）

| 维度 | 网关层 | 大模型 MCP 服务 | RAG MCP 服务 | 提示管理 |
|---|---|---|---|---|
| 核心职责 | 认证 / 日志 / 限额 / 路由 | 提供大模型推理能力 | 提供检索增强生成能力 | 管理提示词模板 |
| 调用关系 | 所有请求必经网关 | 由网关路由后调用 | 由网关路由后调用 | 独立管理模块 |
| 优先级 | 最高（入口控制） | 高（核心能力） | 高（知识增强） | 中（辅助优化） |
| 配置复杂度 | 高（需配置多项目权限） | 中（模型参数调优） | 中（知识库对接） | 低（模板管理） |

### 2.3 简历版的架构描述

- 将 LLM 网关、RAG 检索、会话记忆、Prompt 管理抽离为 **4 个独立 MCP Server**，经 **Streamable HTTP** 暴露标准化 **Tool / Prompt 原语**，新业务接入仅需写 Agent 编排层。
- 设计 **REST → MCP 协议桥接网关**，基于 **FastAPI** 构建**四层中间件链**（认证 → 日志 → 配额 → 路由），用 **Trace ID** 全链路追踪；内置 **MCP Client Manager** 管理短连接，按项目维度做 API Key 认证与 Token 配额计量，保障多租户安全隔离与成本管控。

## 三、网关层：认证、日志、限额、路由

### 3.1 认证

- **作用**：解决 MCP 服务的**调用来源**问题。
  - 确认调用请求是否来自公司内部的项目；
  - 拒绝外部非法请求的调用，保障安全。
- **易混点**：认证是**"项目来源"认证**（哪个业务项目在调），不是"用户身份认证"（哪个终端用户在问）。

### 3.2 日志

- **作用**：通过 **Trace ID** 实现全链路追踪。
  - 一个项目指令可能调用多个 MCP 服务，日志用于追踪问题出在哪个环节；
  - 记录调用参数，便于排查和审计。
- **易混点**（讲义小结表里写成了 "Choice ID"，应为 **Trace ID** 的转写误差）：日志记录需包含调用参数和异常位置。

### 3.3 限额（配额）

- **作用**：对不同项目或不同 MCP 服务进行资源限制。
  - 限制 **Token 上限**，防止单个项目过度消耗；
  - 限制**调用次数**，实现成本管控。
- **易混点**：需结合业务场景设定具体限额数值。

### 3.4 路由

- **作用**：处理**调用权限**与分发。
  - 8 个项目并非都有权限调用全部 100 个 MCP 服务；
  - 例如：项目 A 只能调用其中 20 个 MCP 服务，路由层负责权限判断与分发。
- **易混点**：这里的路由是**权限控制**，不是单纯的技术路由（负载均衡）。

### 3.5 简历版补充

- 内置 **MCP Client Manager 管理短连接**；
- 按**项目维度**做 API Key 认证 + Token 配额计量；
- **多租户安全隔离 + 成本管控**。

## 四、LLM MCP 服务（大模型统一网关）

### 4.1 解决的核心问题

1. **统一管理多个大模型厂商**：将不同厂商（如 Flash、Net、Pro、千问、豆包等）的大模型封装成 MCP 服务，实现统一调用。
   - 解决业务对接多个厂商、多个大模型、多个场景的问题；
   - 支持多模态大模型、普通对话模型等不同类型（版本维度：Flash / Lite / Pro；厂商维度：千问、豆包）。
2. **统一的 Key 管理和额度管理**：将公司级 API Key 统一管理，**开发人员无需自行配置 Key**。
   - 核心原因：大模型的 Key 属于**敏感信息**，直接交给开发人员存在安全风险（如被用于个人项目，消耗公司额度）。
   - 实现方式：开发人员只需接入公司级的通用大模型服务，无需关心底层 Key 配置。
   - 精细化控制：可针对不同用户、不同账号设置不同额度，实现更细粒度的权限管理。

### 4.2 简历版实现

- 实现**逻辑模型名 → Endpoint 路由**（auto / pro / lite），**YAML 配置热切换**，业务无感；
- Embedding 兼容火山引擎 **text** 与 **vision** 两种向量化路径；
- **Token 消耗统一回传配额模块扣减**。

### 4.3 风险与应对

- **高风险节点**：大模型 MCP 服务是**强依赖外部大模型的高风险节点**。
  - 主要风险：高延迟、高并发下容易触发 **429（请求过多）** 或 **502（服务不可用）** 错误；
  - 熔断策略：**必须添加精准熔断机制，防止雪崩效应**。
- 网关层作用：在网关层统一处理业务对接多个厂商、多个大模型、多个场景的请求分发与容错。

### 4.4 小结表

| 知识点 | 核心内容 | 考试重点/易混淆点 |
|---|---|---|
| 多厂商多场景支持 | 支持 Flash、Net、Pro、千问、豆包、火山引擎等不同厂商和版本 | 注意不同大模型（多模态、文本型）的适用场景差异 |
| 统一 Key 管理与额度控制 | 集中管理 API Key，避免敏感信息泄露；按用户/账号分配不同额度 | **Key 是敏感信息，不能直接交给开发人员**，防止被私自用于其他项目 |
| 开发接入简化 | 开发无需配置 Key，直接接入公司级通用大模型服务 | 对比：传统方式需每个开发单独申请 Key vs MCP 服务统一管理 |

## 五、RAG MCP 服务

### 5.1 命名空间区分项目

- **作用**：通过不同的命名空间来区分不同项目，**类似操作系统中的文件夹**。
  - 每个命名空间下存放对应项目的知识库，实现**项目隔离**；
  - 这种结构便于管理和查找不同项目的知识内容。

### 5.2 接入云厂商 RAG 服务

- 如果接入的是**云厂商提供的 RAG 服务（API 形式）**，则**无需自行配置密钥（Key）**，同时可以利用云服务进行**配额管理**，控制资源使用。

### 5.3 跨项目用户记忆打通（亮点）

- **调用便捷性**：通过统一的 RAG 服务，调用知识库更方便。
- **核心功能**：基于 RAG 服务实现**跨项目的用户画像持久化**。
  - 工作原理：大模型在用户使用过程中**收集用户喜好信息，形成用户画像**；
  - 类比：类似抖音的推荐算法——系统在用户不断刷视频的过程中持续完善用户画像（爱好、偏好等）。
- **应用场景**：当公司有多个系统时，通过**账号体系打通**，可以共享用户的喜好信息。
  - 举例：用户在使用 AI 客服系统时透露"芒果过敏"，该信息被记录到用户画像中；当用户切换到其他系统时，**无需再次告知，系统已知晓**。
- **面试话术（架构先行）**：如果面试官问"具体哪几个项目打通了？"，可以回答"我们采用**架构先行**的策略，先搭建好这个功能架构，为未来公司项目增多做准备。目前尚未发展到用户会登录多个系统的阶段，但架构已就绪。"
  - 注意：如果自身业务确实有多个系统（如抖音、西瓜视频）且用户共用账号，可以具体描述；否则用"**为未来做准备**"作为解释。
  - 架构先行，是因为未来会形成产品矩阵。
- **技术难度**：技术本身不难，**关键在于业务场景的设计**。

### 5.4 简历版实现

- 基于**火山引擎 Viking DB** 按 `project_id` 划分**独立 Collection** 做**物理隔离**；
- 按 **Markdown 标题层级 + 段落边界**语义切分；
- 新项目调 `ingest_document` Tool 即可**自助接入**。
- 双层记忆架构（RAG/记忆服务）：
  - **对话记忆**按 `project_id + session_id` 隔离，支持最近 N 轮召回；
  - **用户画像**按 `user_id` **跨项目共享**，基于 PostgreSQL **UPSERT（ON CONFLICT DO UPDATE）幂等写入**；
  - 客服 Agent 自动提取用户事实（过敏/预算/偏好），写作 Agent 即时读取，实现跨项目用户认知同步。

### 5.5 小结表

| 知识点 | 核心内容 | 考试重点/易混淆点 |
|---|---|---|
| RAG 服务命名空间 | 通过命名空间区分不同项目，类似操作系统文件夹管理知识库 | 命名空间与文件夹的类比关系 |
| 云厂商 RAG 服务 API | 接入云厂商 RAG 服务无需配置 API 密钥，可进行配额管理 | 无需配 Key（密钥）的便捷性 |
| 跨项目用户记忆 | 基于 RAG 服务实现用户画像持久化，跨系统共享用户喜好信息 | 与抖音推荐算法的类比：用户画像持续完善 |
| 架构先行策略 | 先搭建跨项目用户记忆架构，为未来多系统打通做准备 | 面试回答技巧："架构先行，功能逐步完善" |
| 实际应用场景 | 用户登录同一账号后，多个系统共享用户喜好（如芒果过敏信息） | 需区分：已有场景 vs 未来规划 |

## 六、Prompt 提示词管理 MCP 服务

### 6.1 统一管理的价值

- MCP 不仅封装服务，还能**统一管理提示词**，实现"**一次编写，到处运行**"。
- **管理对象**：管理的是**系统提示词**，而**不是用户上下文**。
  - **系统提示词**：定义 AI 角色、行为规则、输出格式等固定指令；
  - **用户上下文**：指对话历史、用户画像等**动态数据**，应存储在数据库中。
- **管理方式**：将不同业务、不同项目的系统提示词封装成通用的 MCP **Prompt 服务**。
  - 例如：定义一个名为 `analyze-business-model` 的 Prompt，接收 `industry` 参数，用于分析特定行业的商业模式。
- **优势**：统一管理后，修改提示词**只需改动一处**，避免多个项目各自维护导致混乱和出错。
- **关键约束**：**管理的是系统提示词，不是用户上下文；用户会话上下文存在数据库里。**

### 6.2 简历版实现

- 基于 **MCP 原生 Prompt 原语**构建模板中心：**YAML 定义参数 Schema**、服务端渲染为 **PromptMessage**；
- 模板修改**即时生效、无需重启**，实现提示词工程与业务逻辑解耦。

### 6.3 MCP Resource：注入长上下文

- **核心概念**：MCP 的 **Resources（资源）** 功能用于注入长上下文；Resources 本质是**外部存储**，可以读取本地文件、数据库数据等。
  - 适合存储用户的会话上下文（如历史订单、前序对话日志）。
- **实现方式**：将长文本作为 Resource 暴露给客户端；当大模型需要特定背景时，客户端自动读取该 Resource，作为 user 消息的一部分附加到当前会话。
  - 通常配合**前缀缓存（Prefix Caching）**使用，降低 Token 成本和首字延迟（TTFT）。
- **用户会话管理示例**：通过传入**用户 ID、系统 ID、会话 ID**，查询用户的对话记录，实现会话持久化（如存储在 PostgreSQL 数据库中）。
- **代码实现**：在 MCP 服务端设置 `ReadResourceRequest` 请求处理器。
  - 根据请求中的 **URI** 返回对应的资源内容；
  - 例如 URI 为 `custom://docs/project-guide` 时，返回项目核心规范文本；
  - 若资源未找到，抛出 `Resource not found` 错误。

### 6.4 Prompt vs Resource vs 会话上下文管理

| 维度 | 提示词管理 | Resource 管理 | 用户会话管理 |
|---|---|---|---|
| 管理对象 | 系统提示词（固定模板） | 外部资源（文件/数据库） | 用户对话历史（动态数据） |
| 存储位置 | MCP 服务内部 | 本地文件或数据库 | 数据库（如 PostgreSQL） |
| 核心用途 | 统一管理提示词，避免项目间混乱 | 读取外部数据，提供上下文 | 持久化用户会话，支持刷新恢复 |
| 修改影响 | 改一处即生效，不易出错 | 依赖外部资源变更 | 需数据库操作，支持历史查询 |

**Prompt 与 Resource 的区别**：Prompt 管理系统提示，Resource 管理外部存储数据。

### 6.5 会话上下文谁来管理

- 会话上下文（Context）和对话历史（Chat History）是**有状态的记忆**。
- **由 MCP 客户端**（如 Claude Desktop、LangGraph 编排层）**负责管理**：包括上下文的滚动、截断、KV 缓存优化等。
- **MCP 服务端是无状态的**，无法感知对话的生命周期——所以要靠 Resource 等手段把上下文"注入"进来。

## 七、其他通用 MCP 服务与"通用"的定义

### 7.1 用户会话管理

- 传一个**用户 ID、系统 ID、会话 ID**，查询到用户的对话记录（存储在 **PostgreSQL**）。

### 7.2 如何定义"通用"

- **3 个及以上系统都用到的服务**，才可以抽成通用 MCP 服务。
- 设计方法：结合自身业务场景，梳理哪些功能是通用的；可以借助 AI 辅助——描述业务场景（如电商公司、多个系统），让 AI 提供封装通用 MCP 服务的思路。

### 7.3 自定义扩展思路

- MCP 服务可形成集群，支持自定义扩展（如电商公司可封装哪些通用 MCP 服务）。
- 扩展思路：用 AI 辅助设计，如询问"电商公司封装哪些通用 MCP 服务"。

## 八、Agent 编排层（简历版）

- 实现 **Agent 七步编排流水线**：**召回历史 → 读画像 → 检索知识 → 渲染 Prompt → LLM 推理 → 存记忆 → 提取事实**。
- 全部经 **GatewayClient** 统一调用，**Agent 无状态、状态下沉到共享服务**。
- 部署：各服务独立构建 Docker 镜像，部署至**阿里云 Serverless（FC/SAE）**，按拓扑**分层发布、灰度 + 秒级回滚**，**SIGTERM 优雅终止**保障在途请求不丢。

## 九、面试准备与要点

### 9.1 面试准备清单

- 回顾 MCP 集群的核心思想；
- 在**自己的业务场景**中梳理清楚：有多少项目？有多少 MCP 服务？网关在哪里？
- **讲故事形成闭环**：将限额的具体数值、业务范围、网关位置等细节串联起来，让面试官理解你的架构设计。
- 了解 MCP 如何管理 **Prompt** 和 **Resource**；如果让你设计其他通用 MCP 服务，你会设计哪些？
- 跨项目的用户记忆：根据实际情况研究一个场景或多个系统；如果没有，就说是**为未来做准备的（架构先行）**。

### 9.2 项目总结（一段话版本）

随着 AI 项目越来越多，我们做了一次架构层面的统一收口：把 LLM 网关、RAG 检索、会话记忆、Prompt 管理抽成 4 个独立 MCP Server，经 Streamable HTTP 暴露标准化的 Tool/Prompt 原语；前面加一层 REST → MCP 的桥接网关，做认证、日志、配额、路由这四层中间件；按项目维度做 API Key 认证和 Token 配额计量；RAG 按 project_id 做物理隔离，会话记忆按 project_id + session_id 隔离，用户画像按 user_id 跨项目共享。这样新业务接进来只需要写 Agent 编排层。

| 6. MCP 原生 Prompt 原语 + YAML 参数 Schema + 服务端渲染 PromptMessage | 六.1、六.2 | 管的是**系统提示词**，不是用户上下文 |
| 7. 七步编排流水线 + GatewayClient + 无状态 Agent + Serverless 部署 | 八 | 状态下沉到共享服务 |

## 十一、高频面试问答速记

**Q1：这个项目解决什么问题？**
A：项目变多之后，每个项目都在重复造轮子——各自连大模型、各自配 Key、各自维护知识库和提示词。我们做架构收口：把 LLM 网关、RAG、记忆、Prompt 抽成 4 个独立 MCP Server，前面加一层 REST→MCP 的桥接网关统一做认证、日志、配额、路由。新业务接进来只写 Agent 编排层。

**Q2：网关层为什么必须有？直接调 MCP Server 不行吗？**
A：需要解决四个问题：认证（调用来源是不是公司内部项目）、日志（一次指令会调多个 MCP 服务，靠 Trace ID 定位是哪个环节出问题）、限额（Token 上限和调用次数，控成本）、路由（8 个项目上百个服务，不是每个项目都有权限调全部）。

**Q3：认证认证的是什么？**
A：认证的是**项目来源**，不是终端用户身份。确认请求来自内部项目、拒绝外部非法调用。

**Q4：LLM MCP 服务为什么要把 Key 收上来？**
A：Key 是敏感信息，直接给开发人员，可能被拿去跑个人项目、消耗公司额度；统一收上来之后开发只需要接公司级服务，另外可以按用户/账号设置额度，做更细粒度的权限管理。

**Q5：多厂商怎么选型？**
A：把逻辑模型名映射到具体 Endpoint（auto / pro / lite），YAML 配置热切换，业务无感；Embedding 兼容 text 和 vision 两种向量化路径；Token 消耗统一回传配额模块扣减。

**Q6：RAG 服务怎么隔离多个项目？**
A：命名空间，类似文件夹。云上做法是 Viking DB 按 project_id 划独立 Collection 做物理隔离；新项目调 ingest_document 就能自助接入，不用改代码。

**Q7：跨项目的用户记忆怎么实现？**
A：两层——对话记忆按 project_id + session_id 隔离，只做最近 N 轮召回；用户画像按 user_id 跨项目共享，PostgreSQL 用 UPSERT 幂等写入。客服 Agent 提取"芒果过敏、预算、偏好"这类事实写进画像，写作 Agent 直接读。这是我们**架构先行**为未来产品矩阵做的准备。

**Q8：Prompt 管理管的是什么？**
A：管的是**系统提示词**（角色、规则、输出格式），不是用户上下文。用户上下文是动态数据，存在数据库里，由客户端（编排层）管理滚动和截断。MCP 服务端是无状态的。

**Q9：为什么要用 Resource？**
A：Resource 本质是外部存储，可以把长上下文（历史订单、前置对话）暴露给客户端，需要时自动作为 user 消息的一部分附加上去，通常配合前缀缓存一起用，省 token、降 TTFT。实现上在服务端挂 ReadResourceRequest，按 URI 返回内容，找不到抛 Resource not found。

**Q10：怎么判断一个服务"够通用"？**
A：三个及以上系统都用到的才抽。比如用户会话管理、提示词管理、RAG 服务。不确定的时候我会把业务场景描述给 AI，让它帮我想还能封装哪些通用服务。

## 十二、易混淆点自查

- 认证 = **项目来源**认证；不是用户身份认证。
- 路由 = **权限控制**（哪个项目能调哪些服务），不是负载均衡路由。
- Prompt 服务管**系统提示词**；用户上下文存在数据库，由客户端/编排层管理。
- **MCP 服务端无状态**，看不见对话生命周期；有状态的记忆由客户端负责。
- Resource = 外部存储（文件/数据库）；Prompt = 系统提示；会话管理 = 数据库里的动态历史。
- 大模型 MCP 服务是**高风险节点**（429/502），必须精准熔断。
- 跨项目记忆的标准话术是"**架构先行，为未来做准备**"，不要硬编具体已打通的项目。
- "通用"的判定标准：**3 个及以上系统共用**。
