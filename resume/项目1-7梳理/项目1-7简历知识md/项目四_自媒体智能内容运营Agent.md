## 一、业务背景与定位

- **业务场景**：电商公司要持续产出商品图、商品介绍、宣传文案（如卖服装、卖包包），做内容生成 Agent 降本增效。
- **核心链路**：Agent 生成的内容（图片、文案、视频）通过 **SKU ID 关联到素材管理中心**，反哺多模态知识库：
  - Agent 生成包包图片 → 素材管理中心，通过 SKU ID 关联；
  - Agent 生成包包产品介绍（文字）→ 素材管理中心，通过 SKU ID 关联；
  - Agent 生成包包的 Seedance 视频 → 素材管理中心，通过 SKU ID 关联。
- **在 8 个项目中的定位**：C 端辅助项目。早年商品图/视频全靠设计师和剪辑师人工制作，效率低；后来运营通过 Agent 自动生成商品组图和介绍视频，生成的素材对数据中台进行增强，最终服务 AI 实时语音对话。
- **面试核心**：整个体系必须全部打通，形成完整闭环，而不是零散的功能点。

## 二、LangGraph 多阶段内容生成工作流

### 2.1 工作流步骤

1. **选方向**：确定内容方向，例如"我要生成包包相关的内容"。
2. **定风格**：人为确定大致风格方向，例如"北欧风""复古风"。
3. **要什么（任务分发）**：确定输出类型——图片、文字描述还是视频：
   - 图片 → **图片 SubAgent**
   - 文字描述 → **文字描述 SubAgent**
   - 视频 → **视频 SubAgent**
   - 所有 SubAgent 接收**统一的风格输入**（定风格是后续所有生成任务的统一前置条件）。

### 2.2 技术方案

- 基于 **LangGraph** 构建多阶段内容生成工作流，用 **SubGraph 子图**将选题、写作、配图拆为**独立编排单元**。
- 主图负责整体流程，**子图负责具体任务分支**。

### 2.3 SubAgent 的核心价值

- **SubAgent 解决的核心问题：业务隔离、团队隔离、技术隔离**，即解耦与拆分。
- 类比说明：SubAgent 的拆分类似于**团队管理**——作为 Leader 带三个同学，一个专门负责图片，一个负责文字描述，一个负责视频。
- **架构师名言**："团队架构，决定技术架构；技术架构，决定团队架构。"
  - 一个人独立完成项目时，不需要 SubAgent，可以用一个复杂的网状图全部搞定；
  - 作为 Leader 带三个人时，必须拆分 SubAgent，每人负责一个独立模块，保证质量和效率。
- **面试包装技巧**：用"团队架构决定技术架构"这句话来包装自己的 Leader 角色。

| 对比项 | 单人开发模式 | 团队协作模式（Leader + 3 人） |
|---|---|---|
| SubAgent 使用 | 可不使用，全部用 Node 节点串联 | **必须使用**，一人负责一个 Agent |
| 架构复杂度 | 网状图（恐怖但可控） | 分层解耦，业务隔离清晰 |
| 核心优势 | 了解每个细节，无需拆分 | 团队隔离、技术隔离、并行开发效率高 |
| 适用场景 | 个人项目、小型任务 | 图片/文字/视频均复杂的中大型项目 |

| 流程步骤 | 具体操作 | 关联模块 | 关键要点 |
|---|---|---|---|
| 第一步：选题 | 确定方向（如"包包相关内容"） | SubGraph 生成子图选题 | 明确内容主题范围 |
| 第二步：定风格 | 人为确定风格（北欧风/复古风） | 统一输入 | 风格是后续所有生成任务的统一前置条件 |
| 第三步：任务分发 | 选择生成图片/文字描述/视频 | SubAgent 分发 | 对应团队三人分工，一人负责一个 Agent |
| 第四步：结果关联 | 生成内容与素材管理中心 SKU ID 关联 | 素材管理中心 | 形成完整业务闭环，体现体系化思维 |

## 三、Checkpoint 持久化与时间旅行

- **Checkpoint 持久化**：LangGraph 自带的功能，用于保存工作流的进度状态（通过 **PostgreSQL Checkpointer**）。
- **核心价值**：支持工作流**中断与恢复**——"搞到一半关掉电脑，第二天可以继续"。
- **时间旅行**：Checkpoint 持久化实现的核心目标，可保持工作流的进度状态，支持中断和恢复；进一步支持**任意历史节点回滚与增量重试**，将故障恢复粒度从**整图细化到单节点**。
- **复习建议**：回顾 LangGraph 的 Checkpointer **在数据库中存储的是什么内容**，这是 LangGraph 原生的能力（参数配置即可，无需自定义实现）。
- 简历补充口径：还要保证**流式/非流式下 Checkpointer 数据结构一致**。

## 四、MetricsContext：LLM 全链路追踪与成本核算

### 4.1 为什么要做

- **核心痛点**：自媒体运营 Agent 每天大量调用大模型生成图片、视频、文字，这些调用成本较高，**老板需要知道每天花了多少钱**，因此单独开发 MetricsContext 做成本统计。
- **成本核算流程**：统计大模型调用情况 → 结合云厂商计价规则计算费用 → 汇总统计结果。
- **核心收益**：精确计量每个节点的资源消耗（Token 消耗、推理延迟、错误率），算出单次调用的实际成本，为模型选型与资源调优提供数据支撑。

### 4.2 MetricsContext vs LangSmith（两者互补，而非对立）

| 对比维度 | MetricsContext | LangSmith |
|---|---|---|
| 核心功能 | 成本核算（Token 消耗 + 定价计算） | 链路稳定性观测（节点状态、调用过程可视化） |
| 数据获取能力 | 可获取 Token 消耗数据 | **无法获取图片/视频调用的 Token 消耗**（按张计费） |
| 定价感知 | 结合云厂商定价完成费用计算 | **不了解云厂商定价规则** |
| 适用场景 | 老板要知道每天花多少钱、预算限制 | 排查链路中哪个节点挂了、调用是否成功 |
| 补充说明 | 可设置金额阈值进行调用限制 | 提供可视化看板展示完整调用上下文 |

- **LangSmith 定位**：研发调试、可视化 Debug、查看 Prompt 质量，是开发/调优利器。
  - 长处：原生对 LangGraph 支持完美，能自动将嵌套的 Subgraphs、Nodes、Conditional Edges 以树状图（Trace）展示，节点输入输出、耗时清晰可见。
  - 用途：查看整个调用过程经过哪些节点、哪些节点挂了、大模型每个上下文的拼接情况——负责"显微镜调试"。
- **MetricsContext 定位**：采集数字 → 结合火山引擎定价算钱 → 推送 Grafana/触发业务熔断，是生产/运营工具，负责"数字化纳税"。

### 4.3 LangSmith 的三个局限（MetricsContext 存在的必要性）

1. **成本核算的精准性**
   - LangSmith 无法对 Gemini 等服务复杂的定价策略（缓存命中/未命中、Token 阶梯计费、输入/输出价格非线性比例）进行精准、实时的本地核算。
   - MetricsContext 是自有代码，可以在 `__exit__` 钩子中传入 `volcengine_pricing_calculator(model_name, input_tokens, output_tokens)` 函数，节点跑完一秒钟内算出人民币开销并写入业务数据库。
2. **数据的内网落地与业务联动**
   - LangSmith 是独立 SaaS 平台，私有化部署成本极高，运营/财务团队无法直接查看 Trace 数据。
   - MetricsContext 作为结构化数据"捕获器"，可将 Latency、Token、Cost 实时推送至 Prometheus/Grafana、ELK 或关系型数据库，支持 BI 大盘报表与自动化成本熔断（如用户月消耗超 50 元自动限制调用）。
3. **可编程性与动态选型路由**
   - LangSmith 是"观察者"，只能看到过去发生了什么，无法在运行时读取实时数据做逻辑判断。
   - MetricsContext 是"上下文管理器（Context Manager）"，可在运行时读取数据，实现动态路由决策。

**为什么不用 LangSmith 做成本核算**：
- LangSmith 只能获取大模型的 Token 消耗，**图片调用等场景看不到 Token 消耗**（直接按张计费）；
- LangSmith **不知道企业的实际定价策略**；
- MetricsContext 只记录数字（Token、延迟），**不记录敏感的文本内容**，更轻量、安全。

**最佳实践**：生图生视频成本较高，老板需要成本核算 → 用 MetricsContext；整个 LangGraph 链路的稳定性排查 → 用 LangSmith。两者职责不同、不矛盾、不冲突。

### 4.4 底层原理与极简实现

- **依赖**：Python 的上下文管理器协议（Context Manager Protocol）+ 线程/协程安全的上下文存储（`contextvars` 模块）。
- **工作原理**："进门卡位、出门算账、中间传递"。
  - `__enter__`（进门卡位）：进入节点时触发，记录当前精确系统时间（时间戳 t1），初始化空计数器准备接收 Token 消耗。
  - `__exit__`（出门算账）：离开节点时触发，再次记录时间戳（t2），计算耗时 Δt = t2 - t1；异常时记录错误率；按定价公式计算成本。
  - **`contextvars` 传递**：子节点通过 `contextvars` 容器追加数据（如 `current_metrics.tokens += 500`），外层 MetricsContext 离开时从容器读出累计值，拿到整条链路上所有子节点上报的数据。
- **业务接入方式**：在 LangGraph 节点或任意业务函数中，通过 `with` 语句包裹即可实现无感接入。

讲义中的极简代码（照录）：

```python
import time
from contextvars import ContextVar
from typing import Optional

#### 二、1. 创建一个线程/协程安全的上下文变量容器
current_metrics_var: ContextVar[Optional[dict]] = ContextVar("current_metrics", default=None)

class MetricsContext:
    def __init__(self, node_name: str):
        self.node_name = node_name
        self.start_time = 0.0
        self.metrics = {"input_tokens": 0, "output_tokens": 0, "errors": 0}

    def __enter__(self):
        self.start_time = time.perf_counter()  # 记录进入时间
        # 将当前节点的度量容器绑定到上下文中
        self._token = current_metrics_var.set(self.metrics)
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        latency = time.perf_counter() - self.start_time  # 计算延迟
        if exc_type is not None:
            self.metrics["errors"] = 1  # 记录错误率
        # 模拟火山引擎定价核算（假设输入0.0001元/k，输出0.0002元/k）
        in_cost = (self.metrics["input_tokens"] / 1000) * 0.0001
        out_cost = (self.metrics["output_tokens"] / 1000) * 0.0002
        total_cost = in_cost + out_cost
        # 打印或落库
        print(f"[{self.node_name}] 耗时: {latency:.2f}s | Token: {self.metrics}")
        # 恢复上一层的上下文
        current_metrics_var.reset(self._token)
```

```python
#### 三、业务调用流
with MetricsContext("Doubao_Reasoning_Node"):
    # 1. 模拟网络请求和模型推理
    time.sleep(0.5)
    # 2. 大模型底层SDK收到响应后，在底层悄悄调用track_llm_usage
    # 它会自动找到上面的"Doubao_Reasoning_Node"并把数据塞进去
    track_llm_usage(input_tokens=1200, output_tokens=400)
```

- **本质总结**：MetricsContext 利用 Python 的 `with` 机制在代码生命周期上切入两个钩子（进入和退出），通过 `contextvars` 实现链路间数据传递，完成全链路追踪与成本核算。

## 六、异步并行优化（配图批量生成）

- **问题**：配图 API 是同步 SDK/HTTP 调用，直接 await 会阻塞事件循环。
- **方案**：`asyncio.gather` + `run_in_executor`——把同步 API 封装为协程，丢到线程池并发执行多张配图。
- **重试**：引入**指数退避重试（1s → 2s → 4s）**应对服务抖动，最好再加随机抖动避免同时重试。
- **收益**：整体生成耗时缩减 **70%**（口径：批量 N 张图的总耗时，受并发上限和下游限流影响，所以要设超时和并发控制）。
- **为什么不用 Celery**：当时是请求内的短批量任务，线程池足够；长任务、跨请求任务才适合上队列。

## 七、多模型动态路由与结构化输出

- **路由规则**：根据任务复杂度动态选择不同级别的模型，平衡成本与效果。
  - **简单任务**：使用轻量模型（如 Flash 模型），例如生成文章爆款标题；
  - **复杂任务**：使用旗舰模型，例如根据大纲生成整篇文章。
  - 判断依据：任务类型、输入长度、历史失败做规则判断（也可加分类器，但会增加成本）。
- **结构化约束**：配合 `with_structured_output` 做 **Pydantic Schema 强约束**，底层依赖 function calling / JSON Schema。
- **兼容问题**：使用 **JSON Mode + 手动解析**，解决"结构化输出与 Token 统计不兼容"的问题（部分模型的结构化输出不返回 usage 或格式与统计不兼容）。
- **收益**：通过模型分级调用，可降低约 **40%** 的推理成本（口径：混合路由后的加权推理成本，前提是评测集上质量不掉）。
- **路由错了怎么办**：有离线评测和失败重试，质量不达标升级模型，最终还有模板降级。

## 八、Mock 开关体系（环境变量驱动）

- **核心概念**：通过环境变量控制一个全局开关，在开发阶段用假数据（Mock）模拟整个工作流，提升调试效率。
  - **开发阶段**：开启 Mock 开关（如 `llm_mock` / `image_mock` / `checkpointer_mock`），所有节点（图片、文字、视频）均返回假数据，核心目标是**快速验证链路是否通畅**；
  - **开发完成**：关闭 Mock 开关，接入真实服务进行整体测试。
- **设计思路**：解耦外部服务（LLM / Image / Checkpointer），让开发人员专注业务逻辑与链路测试；开发阶段一个任务可能有十几个节点，测试链路是否通就先开这个 env 里的 mock 开关。
- **核心收益**：避免在调试时等待真实模型生成（如生成一张图需 1 分钟），假数据返回是秒级的，将本地调试效率提升 **3 倍**（也有讲义说团队迭代周期从 2 天缩短至半天）。
- **防止生产误开**：本地默认 Mock，生产配置强制 false 并在启动时校验。
- **配套工具**：配合 **Swagger UI** 进行本地接口可视化调试/评测，配合 **Ngrok 公网映射**便于外部访问与前后端联调。
- **和单测 Mock 的区别**：单测是代码级隔离；这是运行时集成联调开关，方便前后端和外部服务解耦。
- **面试话术**：这不是一个高深的技术，而是体现了对业务和团队提效的思考——通过技术手段解决开发过程中的痛点，而非单纯追求技术难度。

## 十、限流、重试、熔断、降级（高可用）

### 10.1 四个概念

| 概念 | 核心内容 | 考试重点/易混淆点 |
|---|---|---|
| **限流（Rate Limiting）** | 限制接口每分钟/每次调用次数，如"每分钟只能调 5 次"；用 **SlowAPI** 实现接口级限流 | 限流是**控制频率**，防止滥用和浪费成本 |
| **熔断（Circuit Breaker）** | 三个状态：闭合（正常）→ 断开（故障）→ 半开（尝试恢复）；统计错误率，如 10 次调用挂 5 次则断开 | 熔断是**自动切断链路**，与降级不同；半开状态定期尝试恢复 |
| **降级（Degradation）** | 主服务失败后自动切换到备用服务，如 GPT-1 → GPT-2 → Gemini → 豆包生图，持续兜底 | 降级是**服务替换**，熔断是**链路断开**，两者常配合使用 |
| **指数退避重试（Exponential Backoff）** | 重试间隔递增：1s → 2s → 4s，最多重试 3 次后进入熔断 | 与固定间隔重试的区别：指数退避可减轻服务端压力 |

### 10.2 图示（大纲里的伪代码）

```python
slow('5/min')
get('xxxx.com/api')
```

表示该接口每分钟最多只能被调用 5 次，超过限制的请求将被拒绝。

### 10.3 熔断的三个状态

- **闭合**：链路正常，请求可以顺利通过。
- **断开**：当错误率达到阈值（如 10 次调用中挂了 5 次），熔断器断开，所有请求立即失败，不再调用下游服务。
- **半开**：断开后熔断器进入半开状态，每隔一段时间（如 5 分钟）尝试发送一个请求，探测服务是否恢复。
- **状态流转**：闭合 → 错误率超标 → 断开 → 半开（尝试探测）→ 探测成功 → 闭合。

### 10.4 降级链示例

- 主线：调用 GPT-1 生成图片 → 失败。
- 备用 1：降级调用 GPT-2 → 失败。
- 备用 2：降级调用 Gemini → 成功。
- 兜底：如果所有高级模型都失败，最终降级到豆包生图，确保流程不中断。
- 关键点：**降级是逐级向下的，直到找到一个可用的服务为止。**

### 10.5 指数退避与熔断的关系

- 第一次失败后等待 1 秒重试，第二次失败后等待 2 秒重试，第三次失败后等待 4 秒重试。
- **如果重试三次仍然失败，则触发熔断器，进入熔断状态。**

### 10.6 完整保护链路

在一个完整的 LangGraph 流程（如 a → b（图片生成服务）→ c → d → e → f → g）中，每个关键节点都应遵循以下保护顺序：

```
限流 → 指数退避重试 → 熔断 → 降级
```

- **限流**：首先限制接口的调用频率，防止流量突增（如每分钟最多生成 10 次）；
- **指数退避重试**：调用失败后，按指数递增的时间间隔重试；
- **熔断**：重试多次仍失败，触发熔断，断开链路；
- **降级**：熔断后，切换到备用服务，保证流程继续运行。
- **恢复机制**：当熔断器处于半开状态并探测到主服务恢复后，链路重新闭合，降级策略停止，回归主线。

### 10.7 策略应该加在哪：关键节点，而不是全流程

**核心问题**：在一个多节点的流程中（如 A→B→C→D→E→F→G），限流、熔断、降级、重试应该对整个流程施加，还是对某个节点施加？

**答案**：**既不是基于整个流程，也不是基于某个节点，而是在流程中的关键节点去设计不同的策略**。

| 节点 | 分析 | 熔断策略 | 降级逻辑 |
|---|---|---|---|
| 节点 A：`intent_node`（意图识别） | 依赖本地 Prompt 或轻量模型，极少挂掉 | 不加熔断，或只加超长超时保护 | — |
| 节点 B：`search_node`（向量数据库检索知识） | 依赖自建 Milvus 或外部 Pinecone，有断线风险 | 加熔断 | 如果 Milvus 挂了触发熔断，降级为去传统 MySQL 做模糊匹配（Like 查询），虽然不智能，但好歹能查出东西 |
| 节点 C：`generate_image_node`（调用引擎生成商品图） | **高风险节点**！强依赖外部大模型，高延迟，高并发下最容易爆 429 或 502 | **必须加精准熔断** | — |

### 10.8 为什么图片生成服务要重点加策略

- 因为**国内无法直接使用国外图片生成服务，只能找中转服务，中转服务不稳定**。
- 策略组合设计：
  - **限流**：为了省钱，防止有人攻击后白白花钱；
  - **重试**：指数退避重试（如 1s→2s→4s），因为中转服务不是不能用，只是不稳定；
  - **熔断 + 降级**：如果中转服务真的挂了，就熔断并执行降级逻辑。

### 10.9 四者配合总表

| 对比项 | 限流 | 熔断 | 降级 | 指数退避重试 |
|---|---|---|---|---|
| 核心目的 | 控制频率/省钱 | 自动保护链路 | 服务替换/兜底 | 临时故障恢复 |
| 触发条件 | 达到阈值 | 错误率超标 | 主服务不可用 | 请求失败 |
| 状态变化 | 持续生效 | 闭合→断开→半开 | 主→备→兜底 | 递增间隔 |
| 恢复机制 | 时间窗口重置 | 半开状态尝试 | 主服务恢复后切回 | 成功即停止 |
| 应用优先级 | **第一道防线** | **第三道防线** | **第四道防线** | **第二道防线** |

> **顺序不可颠倒**：限流 → 指数退避重试 → 失败后熔断 → 熔断后降级到备用服务；恢复后切回主线。

### 10.10 容器化高可用的配套

- `/health` 健康检查端点 + **优雅关闭（SIGTERM）**：停止接新请求、等待在途请求完成、关闭连接池，保障容器化部署场景下的高可用。
- 限流保护自己，熔断保护下游；10 次/分钟是接口配置，按业务调。

## 十四、高频面试问答速记

**Q1：为什么用 LangGraph，而不是一条 if-else 链路？**
A：这是多阶段内容生成，选题、写作、配图的状态和失败重试需求不同。LangGraph 把流程显式建成节点和边，SubGraph 让每个阶段独立编排，避免整张图耦合。

**Q2：SubAgent 解决什么问题？**
A：业务隔离、团队隔离、技术隔离。类比团队管理——我作为 Leader 带三个人，图片、文字、视频各一个人负责，架构自然拆成三个 SubAgent。**团队架构决定技术架构**：单人项目其实不需要拆。

**Q3：Checkpointer 存在数据库里的是什么？回滚怎么实现？**
A：存的是工作流每一步的 State 快照，按 thread_id、checkpoint_id 落库。所谓回滚到历史节点，是加载对应 checkpoint 重新执行后续节点；增量重试只重跑失败节点。这是 LangGraph 原生能力，配好参数即可，但 State 必须可序列化，存储和清理也要设计。

**Q4：MetricsContext 是什么？为什么不用 LangSmith 算钱？**
A：它是一个 Python 上下文管理器，`__enter__` 记时间戳、初始化计数器，`__exit__` 算耗时、算成本，中间用 contextvars 在链路里传递数据，`with` 包一下就接入。不用 LangSmith 是因为：它看不到图片/视频的 Token（按张计费）、不知道我们的定价策略、私有化成本高、财务和运营也看不到；而且 MetricsContext 只记数字不记文本，更安全。

**Q5：SSE 怎么和 LangGraph 集成？**
A：后端用 `astream_events` 监听 `on_chat_model_stream` 拿到 token 级 chunk，转成 SSE 事件推给前端；前端用 ReadableStream 增量渲染。为什么不用 WebSocket——需求是单向推送，SSE 的 HTTP 特性更好、运维更简单。

**Q6：为什么 gather 和 run_in_executor 一起用？**
A：配图 SDK 是同步的，直接 await 会阻塞事件循环；用 run_in_executor 把它丢到线程池，再用 gather 并发等。70% 是批量生成的总耗时口径，要根据下游限流设并发上限和超时。

**Q7：多模型路由怎么判断简单和复杂？**
A：先按任务类型、输入长度、历史失败做规则判断，简单走 Flash、复杂走旗舰；结构化输出用 with_structured_output + Pydantic 强约束，个别模型结构化输出不带 usage，就用 JSON Mode + 手动解析并单独统计 Token。降本 40% 是加权推理成本，前提是评测集上质量没掉。

**Q8：Mock 开关怎么做才不会在生产误开？**
A：通过环境变量注入，工厂根据开关返回真实客户端或 Mock 实现；本地默认 Mock，生产配置强制 false 并在启动时校验。它不是单测里的 Mock，而是运行时联调开关。

**Q9：限流、熔断、降级、重试加在整条流程还是单个节点？**
A：都不对，加在**流程中的关键节点**。比如意图识别依赖本地轻模型，基本不用加；检索节点依赖外部库，要加熔断 + 降级到 MySQL 模糊匹配；图片生成节点强依赖外部大模型，最容易爆 429/502，必须加精准熔断。顺序是限流 → 指数退避重试 → 熔断 → 降级，恢复后回主线。

**Q10：生图生视频一个月要花多少钱？（成本故事）**
A：文本模型按百万 token 计费且输入远便宜于输出；生图按张（豆包 Seeddream 0.20~0.25 元/张），视频按秒（Seedance 约 1 元/秒）。所以我们做了 MetricsContext 统计并设置金额阈值熔断，防止失控调用把账单打爆。

## 十五、易混淆点自查

- LangSmith = 稳定性/调试（观察者）；MetricsContext = 成本/熔断（上下文管理器，可编程）。**两者互补，不是重复。**
- SubAgent 不是技术必需，而是**团队架构的体现**；单人项目可不用。
- Mock 开关是**运行时**开关，不是单测 Mock。
- 限流、熔断、降级、重试加在**关键节点**，不是全流程也不是每个节点都加。
- 熔断 = 切断链路（状态机）；降级 = 替换服务（兜底）。两者配合使用。
- 指数退避（1s→2s→4s）比固定间隔更省下游压力。
- 生图按张、视频按秒、文本按 token，且**输入比输出便宜**。
