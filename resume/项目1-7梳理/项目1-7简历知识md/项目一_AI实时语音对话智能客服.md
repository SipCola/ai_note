## 一、项目定位与业务背景

- **业务场景**：电商私域销售。海外客户通过独立站引流到 WhatsApp / 销售私人微信，需要智能客服承接 **从商品咨询到引导下单的全流程**。
- **数据来源**：销售在微信 / WhatsApp 的真实聊天记录，经数据中台（项目二）清洗后建立 RAG 知识库。
- **产品形态**：可实时语音对话的智能客服（类比"罗永浩和豆包对话"），同时支持图文。
- **在 8 个项目中的定位**：C 端核心项目（对外），也是最早做的项目；素材中心、自媒体 Agent、直播切片、数据中台、模型微调最终都服务或反哺它。
- **讲述建议**：介绍时只说一个数据源（如微信），避免被追问 WhatsApp 的细节。

## 二、RAG 知识库是怎么建的

### 2.1 RAG 数据来源：数据中台导出的数据

原始数据的加工链路：**数据中台原始数据 = 机器清洗 + 人工审核 / 打标签 + 人工手动补充**，最终落成 PostgreSQL 里的一张表，这张表就是 RAG 数据。

数据量故事（讲义 25《数据中台4》给出的一套自洽口径）：

| 阶段 | 数量 |
|---|---|
| 微信原始脏数据 | 10 万条（5 个销售的数据合并，人均约 2 万条） |
| 机器清洗后 | 剩下 2 万条 |
| 人工清洗后 | 剩下 2000 条 |
| 人工补充后 | 补充 100~200 条，最终约 **2000~2500 条** |

- 2000~2500 条数据对应 **20~30 款商品**；构建 RAG 导出后还会人工审核一遍，最终约 2000 条。
- 平均一个商品约 100 条数据，**有重复很正常**——同一句话有多种表达方式（可以说 50 条 / 20 条 / 30 条，关键是说得像真的）。

> 注意：大纲里另有一套更小的口径——"电商场景 10 个 SKU，每个 SKU 约 100 条数据，共 1000 条"。整理时两套口径都存在，面试时选一套自洽使用（若选 2500 条口径，则"10 个 SKU × 100 条 = 1000 条"要改成"20~30 款商品"）。

### 2.2 电商场景的表结构（PostgreSQL + pgvector，10 个 SKU 方案）

- **微信数据**：清洗后由人工绑定商品 ID（即"人工把每段对话绑定到具体商品 ID 上"）。
- **对话文本表**：商品 id、商品价格、库存、描述、`embedding`。
- **图片数据表**：图片 URL、图片描述、图片描述的 `embedding`、商品 id（关联到具体商品）。
- **视频数据表**：结构与图片表类似（URL、描述、embedding、商品 id）。

关键认知：

1. **结构化数据（价格、库存）必须精确读取，绝不能靠向量检索去"猜"价格**，否则会产生幻觉。
2. embedding 是对"商品描述文本"做语义化处理生成的向量；前面这些商品 ID、价格等信息相当于 **Metadata 标签**。
3. 检索命中图片/视频时，系统能立刻知道该素材属于哪个商品。

## 三、用户一次提问的完整链路（查询流程）

### 3.1 第一步：意图识别

- **任务**：用一个**轻量级 LLM** + 提示词判断两件关键信息：
  1. 用户询问的是哪个商品（识别 **SKU**）；
  2. 应该回复**文字 / 图片 / 视频**。
- **SKU 列表动态获取**：服务端提供接口，动态拉取当前系统中的 SKU 列表（数量可能变化，如 10 个或 11 个），接口必须与数据库同步，避免 SKU 信息过期或遗漏。
- **上下文**：**每一轮对话都必须把完整的会话历史放入上下文**。原因：用户经过多轮对话后，情绪或需求可能发生变化（例如从问商品信息变成"要求下单链接"），没有前文就无法准确判断当前该回什么。
- 意图识别还承担 **Query 改写** 与 **固定套路引导**（见"提升召回率"与"评测"章节）。

### 3.2 第二步：查询（以查文本为例）

1. **精确查询**：根据识别出的 SKU，在数据库中精确匹配，筛出只属于该 SKU 的数据。举例：数据库有 1000 条数据、对应 10 个 SKU（每个约 100 条），精确查询后只保留这 100 条。
2. **向量查询**：在精确查询的结果之上再做向量相似度检索，找到最匹配的内容。
3. **输出结果**：把检索结果交给大模型生成最终回复返回用户。

> **顺序不可颠倒**：先精确查询缩小范围，再做向量查询做语义匹配。

## 四、稠密向量、稀疏向量与混合检索

### 4.1 传统数据库的两种方式

- **精准搜索**：必须一比一完全匹配搜索词。如搜"大专可以学吗"，数据库必须包含完全相同的字符串才能命中。
- **全文检索**：搜索词中的关键词只要在原文中出现即可命中。原文"我大专有个 offer 是 85k"，搜"大专""offer"都能命中该条记录。

### 4.2 向量数据库

- **稠密向量（语义检索）**：通过语义理解进行检索，不依赖字面匹配。
- **稀疏向量**：通过神经网络算法分析提问关键词的**权重**，用权重高的词去做全文检索。
  - 核心概念：稀疏向量引入了"权重"，可以区分用户提问中的重点和非重点。
  - 举例：用户问"我大专可以学 AI 吗"，这句话的重点是"大专"和"AI"，而不是"早上吃了一碗面"。

### 4.3 混合检索

- 混合检索 = **稠密向量（语义检索）+ 稀疏向量（关键词权重检索）**，既保证语义相关，又保证字面相关，一起凑够 15 个候选，避免漏掉真正相关的信息。
- **PostgreSQL + pgvector 本身没有稠密/稀疏的原生概念**，但可以手动模拟实现，效果接近正经稠密+稀疏方案的 **95%**。
  - 缺少的关键参数：`dense_weight`（用于调节语义检索和关键词检索的权重）。
  - 模拟方式：在 SQL 查询中改权重系数，自由调配稠密和稀疏的比例。

### 4.4 教学案例：商品搜索（权重调节）

- 知识 A（商品 1）："我们的山茶花保湿精华，主打深层补水。"
- 知识 B（商品 2）："我们的富勒烯抗衰乳液，主打紧致淡纹。"
- 用户提问："我想买那个抗老紧致的山茶花乳液。"
- 分析：用户把两款混在一起了——"山茶花"字面契合 A，"抗老紧致、乳液"语义更契合 B，用户核心意图是"抗老紧致"而非"山茶花"。

**场景一：偏向字面关键词（alpha = 0.2）**

```sql
(1 - (content_embedding <=> :query_vector)) * 0.2
+ (ts_rank_cd(fts_tokens, to_tsquery('山茶花 & 乳液')) * 0.8) AS hybrid_score
```

- 结果：用户打了"山茶花"，全文检索给知识 A 极高字面分，语义权重只有 0.2 压不过字面分 → 胜出的是知识 A（山茶花保湿精华）。
- AI 回复："亲亲，为您推荐我们的山茶花保湿精华！它主打深层补水哦~"
- 结论：AI 死板地匹配了"山茶花"，忽略了用户想买"抗老乳液"的核心诉求。

**场景二：偏向语义理解（alpha = 0.8）**

```sql
(1 - (content_embedding <=> :query_vector)) * 0.8
+ (ts_rank_cd(fts_tokens, to_tsquery('山茶花 & 乳液')) * 0.2) AS hybrid_score
```

- 结果：向量检索发现"抗老紧致、乳液"与知识 B（富勒烯抗衰乳液）空间距离极近，语义权重 0.8 压过字面分 → 胜出的是知识 B。
- 结论：AI 能像真人销售一样听懂客户"真实意图"。

**核心要点**：通过调整 SQL 中的 alpha 权重（0~1，靠近 1 偏语义，靠近 0 偏字面关键词），可以动态改变 AI 客服的"思考方式"。

### 4.5 方案辩证（面试要点）

| 方案 | 优点 | 缺点 |
|---|---|---|
| PostgreSQL + pgvector | 手动模拟稠密稀疏，权重通过 SQL 运算符实现，**灵活可控** | 需要自己写权重逻辑 |
| 火山引擎等专用向量数据库 | 权重调节是封装好的 SDK 参数，**使用更简单** | 灵活度较低 |

面试是辩证过程：要掌握基础知识、能讨论不同方案的优缺点，不要死记硬背。

## 五、Top K、Top N 与 Rerank

### 5.1 三个概念

- **K（检索数量）**：先从知识库中搜索出 K 条最相关的数据（例如 15 条）。
- **Rerank（重排序）**：对这 K 条数据重新排序，筛出最精准的结果。
- **N（最终数量）**：重排后只保留 N 条（例如 3 条）喂给大模型。

一句话：**搜 15 条（K）→ 排序（Rerank）→ 留 3 条（N）**。

### 5.2 不同技术栈的实现方式

- **火山引擎知识库（Viking DB）**：内置自动 Rerank，无需额外配置。
- **PostgreSQL + pgvector**：需要引入**第三方轻量级 Rerank 小模型**（简历表述为 base-rerank 轻量模型）。

### 5.3 为什么混合检索会翻车（Rerank 的必要性）

- 场景：用户问"有没有适合运动时戴、不容易掉的耳机？"
- 候选 A（正确答案）："这款耳机采用挂耳式设计，专为跑步、健身打造，狂甩不掉。"
- 候选 B（干扰项）："这款耳机适合日常通勤，请勿在剧烈运动时佩戴，容易掉落。"
- 混合检索的缺陷：
  - 全文检索（关键词匹配）：候选 B 命中"适合""运动""掉"等关键词，得分可能高于 A。
  - 向量检索（语义匹配）：A 和 B 的语义相似度得分可能非常接近。
  - 结果：错误数据 B 总分排第一，正确答案 A 被挤到后面。
- **Rerank 的解决方案**：
  - 原理：使用**交叉编码器（Cross-Encoder）**，将用户提问和每条候选数据拼接成完整句子进行通读理解。
  - 效果：能敏锐识别 B 中"请勿""容易掉落"等否定和转折词，判断其与用户意图相反而降权；同时理解 A 中"挂耳式、跑步、健身"与"适合运动"的关联，将其提到第一名。

**总结**：混合检索（数据库）负责"查缺补漏"，保证结果中既有语义相关又有字面相关，凑够 K 个候选；**Rerank（重排模型）负责"审时度势"**，作为最终的大脑，从 K 个候选里剔除伪装得很好的噪声，把真正能解决问题的黄金答案提到最前面。

### 5.4 为什么企业级项目一定要 Rerank

- 业界说法："低配版 RAG 靠向量检索，工业级 RAG 全靠 Rerank 续命。" Rerank 是 RAG 能否达到商用标准的分水岭。
- 解决的三个致命痛点：
  1. **大模型"迷失在中间"**：LLM 有天生弱点，上下文过长（如一次喂 15 条资料）时只记得最前和最后的内容，中间会被忽略导致幻觉。Rerank 保证最有价值的干货排在第 1、2 名，让大模型一眼看到——即使向量检索把正确答案排在第 14 名，Rerank 也能通过深度语义分析把它捞回第 1 名。
  2. **拯救数据库的"低智商"**：数据库（pgvector、全文检索）只能做粗暴的分数拼接，语境理解不到位，常把干扰噪声排第一；Rerank 做真正的深度语义大审判。
  3. **多模态素材的"强行打挤"**：电商富媒体场景下，文字、图片、视频在数据库里算分不公平（字数少的天然吃亏）；Rerank 能基于用户意图把被埋没的图片视频重新捞到最前排。

### 5.5 必须用 Rerank 的场景

| 场景 | 原因 |
|---|---|
| 混合检索（Hybrid Search）落地 | 向量+全文两路分数不一致、数学冲突，Rerank 是天生的"多路分数融合器" |
| 包含多模态素材或结构化表格 | 文字、图片、视频链接、商品参数表（价格/库存/货号）长短不一，单靠向量或字面距离极易翻车 |
| 企业级合规、高客单价售前、严谨知识问答（零幻觉要求） | 对幻觉容忍度为 0，必须用 Rerank 卡死及格线（如得分低于 0.65 直接拦截），宁可呼叫人工也不给大模型瞎编的机会 |
| 知识库极其庞大、文档切片极多 | 一个问题可能海选出 50 条相似切片，直接喂大模型严重影响效果 |

### 5.6 可以不用 Rerank 的场景（辩证用）

> 核心原则：为了省下开发成本和延迟可以不用，但面试时建议说"我们企业级场景，公司不差钱，拉满就完了"——辩证着说。

| 场景 | 原因 |
|---|---|
| 极度追求"首字响应速度"的实时闲聊或客服 | 用户最不能忍受"卡顿"，多加一层 Rerank 即几十毫秒延迟，不如直接 `LIMIT 3` + 流式传输 |
| 知识库数据极单一且标准（单一 QA 库） | 数据太干净、太标准化，查出来第一名 100% 正确，再加 Rerank 是"大炮轰蚊子" |
| 预算极度紧张、服务器没有显卡算力 | 纯 CPU 云服务器上跑 15 条数据交叉深度计算，延迟可能飙到几百毫秒甚至 1 秒以上 |

**面试话术**："我们要求准确性大于速度"，往复杂场景去讲；但**不要写具体指标**（如"召回率 50%→80%"），会被追问评测集。

## 六、向量维度和要不要 Int8 量化

### 6.1 核心结论

私域电商场景：**不需要降维，也完全不需要 Int8 量化**。

根本原因：降维和量化是专门解决"大厂病"的——针对几千万甚至上亿条向量带来的内存撑爆、服务器租金高昂。本项目数据规模太小，不适用。

### 6.2 算一笔账

- 假设 10 个 SKU，每个 SKU 配 100 条纯文本 QA、100 张多模态图文、50 个短视频素材，总共才 2500 条数据。
- 以 BGE-M3（1024 维，float32）为例：一条向量内存 = 1024 × 4 字节 = **4KB**；2500 条 ≈ 10MB，远小于一张大图的大小。
- 结论：强制降维或量化带来的性能提升微乎其微，反而损失精度。

### 6.3 强行降维/量化的后果

- **精度损失**：向量本质是一串浮点数，量化相当于降低数字精度，必然导致查询不准。
- **得不偿失**：为省下微不足道的内存和计算时间，严重降低检索准确率，会砸了私域导购的饭碗。

### 6.4 维度与量化怎么定

- **维度**：数据量不大，直接使用 **1024 维**；降到 512 或 256 等于"查询降智"，会降低检索精度。
- **量化**：没有必要做 Int8 量化（将 float32 的 32 位压缩为 8 位，减少存储空间），因为数据量不大，没必要为省内存牺牲精度。
- **架构优势**：意图识别先通过商品 ID（Metadata 标签）过滤一轮，剩下的数据已经很小（如 250 条），在这个量级上做语义查询无需降维或量化。
- **判断标准**：2500 条不需要降维/量化；若数据量到 1 万或 10 万条，需要重新评估（千万级才需要）。

### 6.5 多模态检索的误区

图片/视频是通过**转文字方式**命中的，而不是直接解析图片本身——所以"精度要求高"的说法有误，实际依赖的是文字匹配。

> 对照简历：简历第 1、3 条写了"Int8 量化""降维 + 精简 Limit"，与讲义 09 的结论（本项目不需要降维和量化）**直接冲突**。若简历保留该表述，需要准备好"为什么这个场景下会做"的解释（例如说成是火山引擎 HNSW 索引侧的默认量化能力，或强调是大数据量演进后的规划），否则容易被自己的细节讲穿。

## 七、知识库数据频繁变动怎么办

### 7.1 什么在变

客服系统里**商品信息频繁变动主要指价格和库存字段的更新**，而不是新增商品链接。

### 7.2 索引选择：HNSW vs IVFFlat

对频繁变动的数据应使用 **HNSW 索引**，而不是 IVFFlat。

- **IVFFlat 的缺陷**：类似"抽屉"结构，建索引时已划分好分区，数据频繁变动后需要**重建索引**，效率极低。
- **HNSW 的优势**：完美支持动态插入和修改，无需重建索引，查询速度极快。

详细对比：

| 特性 | IVFFlat 索引 | HNSW 索引（当前推荐） |
|---|---|---|
| 构建速度 | 极快（几秒钟） | 较慢（建索引时需疯狂连线，消耗 CPU） |
| 查询速度 | 快 | 极快（通常比 IVFFlat 更快） |
| 频繁变动支持 | 极差（频繁增删会导致准确率下降） | 极好（完美支持动态插入/修改） |
| 空表建索引 | 不支持（必须先攒够一定数据量） | 支持 |
| 内存开销 | 较大（为了存储索引表） | 极小（为了存储连线网，多消耗一点内存） |

注意事项：HNSW 内存消耗稍大，但性能优势明显，强烈推荐。

### 7.3 动静分离（分表）

把频繁变动的数据与不常变动的数据**分表存储**：

- **不频繁变动的**放一张表：商品信息表，包含 sku_id、描述、特点等；
- **频繁变动的**放另一张表：价格库存表，包含 sku_id、价格、库存。

优点：数据变动时只需更新"价格库存表"，**无需重建整个索引**，兼顾了知识实时性和查询性能。

## 八、高并发怎么办

### 8.1 第一招：sku_id 过滤数据

先通过意图识别拿到商品 ID（sku_id），从数据库过滤出该商品相关数据（如 100 条），再在这 100 条里做向量检索——**不是每次都查全量知识库（如 1 万条），而是先过滤再检索**。

- 举例：用户问"这个耳机多少钱？"，意图识别先找到"耳机"对应的 sku_id，然后查出该型号耳机的 100 条相关数据，最后在这 100 条里做向量检索。

### 8.2 第二招：Redis 相似度缓存

- **机制**：用户提问向量化后，与 Redis 中缓存的向量做相似度比对，命中则直接返回缓存结果，避免重复计算。
- **向量化**：用户提问通过模型转成空间中的向量（形如 `[0.xxxx]`）。
- **命中条件**：相似度达到一定阈值（例如 **95%**）。
- **缓存内容**：向量检索的 **Top N 结果**（如 3 条）。
- **缓存时间**：根据业务需求设置，可以是 5 分钟、1 小时甚至 1 天（大纲口径："1 天，根据业务来的"）。
- **示例**：
  - "漫步者的樱花耳机多少钱" → `[0.xxxx]`
  - "你这个漫步者的樱花耳机多少钱" → `[0.xxxx]`
  - 在 Redis 中比对，如果非常接近（95%），直接返回缓存的 N 条。
- 注意事项：要注意缓存一致性问题。

### 8.3 第三招：LLM 轻量 + RPM

- **RPM（Requests Per Minute）**：每分钟大模型的回复数量，是衡量并发处理能力的关键指标。
- 大模型厂商默认提供的 RPM 通常在 **500 左右**（如意图识别阶段使用的豆包 lite 模型）；有资料写"默认 500 或几十到 200"，不同厂商/模型有差异。
- **扩容方案**：向云厂商申请扩容至 **1000~2000 RPM**。对电商场景基本够用——按 10% 转化率算，每分钟可产生约 200 单。
- **突破厂商限制**：若需要更高并发（如 2 万 RPM），可开多个 LLM 账号做**负载均衡**——写算法循环使用多个账号，第一个用完切第二个；除非你是抢火车票，否则没必要。

### 8.4 第四招：SKU 预设标签 + 写死 + 系统提示

通过产品功能设计，把高频问题直接写死为缓存，避免重复的意图识别和向量检索：

- 在 AI 对话弹窗中设置**预设标签（tag）**，如"漫步者的樱花耳机多少钱？"，用户点击后直接发送该问题。
- 命中逻辑：大量用户同时点击同一个预设标签时，系统直接命中**写死的 KV 缓存**，返回对应的 Top N 结果。
- 优势：**无需做相似度校验和对比**，极大降低系统压力，零延迟。

### 8.5 四招对比

| 方案 | 实现方式 | 适用场景 | 成本/效益 | 复杂度 |
|---|---|---|---|---|
| sku ID 过滤 | 意图识别 → 数据库过滤 → 向量检索 | 知识库数据量大时 | 高效益，减少检索范围 | 低 |
| Redis 缓存 | 向量比对 → 命中缓存直接返回 | 高频重复查询 | 高效益，减少大模型调用 | 中 |
| 多账号负载均衡 | 循环调用多个大模型账号 | 需要突破厂商 RPM 限制 | 成本高（需多个账号） | 低 |
| 业务辅助缓存（预设 tag） | 预设热门问题 tag，直接返回 | 高峰期热门问题 | 高效益，零延迟 | 低 |

## 九、如何提升召回率

### 9.1 Query 改写（最关键的"基础前提"）

- 核心概念：用户提问通常口语化、带方言或指代不明，直接检索知识库会失败。需要用意图识别模型把用户提问改写为对知识库更友好的标准查询语句。
- 改写原则：把模糊指代（"它""那个""这个"）、口语化表达（"卡不卡""丝滑不""累不累"）和情绪化内容（"急死我了"）转化为明确的商品名、型号、具体功能或参数问题。

讲义中的对照示例：

| 客户原始提问 | 大模型改写后 |
|---|---|
| "那它玩足球卡不卡？"（上一句聊的是 Y9000P 2026 款） | "联想拯救者 Y9000P 2026款笔记本玩 FC Online 足球网游卡不卡？" |
| "那个玩倒脚丝滑不？" / "这电脑打发发有鬼影吗？" | "联想拯救者 Y9000P 玩 FC Online（FIFA Online 4）是否流畅？屏幕是否有画面拖影/残影？" |
| "这款乳液能抗衰吗？" | "这款山茶花乳液是否有抗老、紧致、淡化细纹、抗氧化的功效？" |
| "我经常带出门，这电脑背着累不累？" | "联想拯救者 Y9000P 笔记本的机身重量(kg)、厚度、便携性以及适配器重量是多少？" |
| "家人们谁懂啊，急死我了，昨晚看直播被种草的那个 199 的耳麦，今天下单到底还不送赠品啊？在线等！！" | "售价 199 元的蓝牙耳机当前的下单赠品活动优惠政策是什么？" |

关键作用：改写后的 Query 包含了起因、经过、结果、时间、地点、人物等关键要素，能精准命中知识库里对应的文档，大幅提升召回率。

### 9.2 把 K 变大

- K 值代表从知识库中检索并返回的候选文档数量，增大 K 能覆盖更多潜在相关文档。
- 但 K 不是越大越好，需按业务场景和数据量设定：电商场景 K=10 通常就够了（简历/其他章节又提到"海选池 K 从 10 放大到 25"，属于不同阶段口径）。

### 9.3 混合检索

结合稠密检索（语义，处理同义词、近义词、不同表述）与稀疏检索（关键词/全文，对术语、型号、数字精度高）的优点，实现"语义 + 精准"兼得。

### 9.4 三种手段对比

| 维度 | Query 改写 | K 值调优 | 混合检索 |
|---|---|---|---|
| 核心作用 | 消除用户表述歧义 | 扩大候选集范围 | 融合语义与精准匹配 |
| 实现方式 | 意图识别模型 + 大模型改写 | 调整检索参数 K | 稠密 + 稀疏双通道 |
| 适用场景 | 方言、口语、模糊指代 | 知识库规模较大时 | 需要兼顾语义与精确度 |
| 优先级 | 高（基础前提） | 中（参数调优） | 高（效果提升） |

### 9.5 召回率优化"组合拳"（多模态场景）

Query 改写（把口语化表达转标准表述）+ 多模态图片全语义机洗 + 海选池 K 值从 10 放大到 25；**召回率指标必须死卡在 95%~98% 以上**。

## 十、准确率与召回率（以及怎么统计）

### 10.1 概念

- **准确率（Precision）**：检索出的文档中真正相关的比例——关注"捞出来的对不对"。
- **召回率（Recall）**：知识库中所有相关文档被成功检索出的比例——关注"捞出来的全不全"。

**举例**：知识库有 10 条关于"Y9000P 2026 款屏幕拖影和 FC Online 实测"的黄金干货，系统只捞出了 5 条，且这 5 条全部相关：

- 准确率 = 100%（没有一句废话）；
- 召回率 = 50%（漏掉了另外 5 条）。

**核心目标**：真正要的是**召回率**——把知识库中相关的内容全部命中。即使准确率 100%，只捞一半也不够。

### 10.2 为什么核心是提升召回率而不是准确率

- 举例：K=20、知识库中关于"大专能学吗"的有效数据只有 10 条。
  - 系统捞 20 条，其中 10 条相关、10 条无关 → 准确率 = 10/20 = 50%；召回率 = 10/10 = 100%。
- 结论：因为后续还有 Rerank 和大模型可以过滤无关数据，所以海选阶段的核心目标是"全"而不是"准"。

### 10.3 统计方法（三步）

**第一步：建立黄金测试集（Golden Dataset）**

- 目的：为每个问题人工标注好"标准答案"，作为评判召回效果的基准。
- 收集问题：让业务/销售人员翻看历史微信聊天记录，挑出 **50 个**客户最常问、最刁钻的真实口语化问题。
- 人工标注答案：懂产品的人到知识库里把"最完美的标准答案切片"找出来，并记录其 ID。
  - "那个玩倒脚丝滑不？" → 标准答案 ID：Doc_102（FC Online 实测 240 帧卡顿）
  - "带出门沉不沉？" → Doc_045（机身净重 2.x kg 参数片）、Doc_089（适配器重量）
  - "大专能学吗？" → id1、id3、id8、id9…
- 可参考的另一套口径：知识库 500 条数据，50 条提问，每个提问对应 10 条相关数据，每条 RAG 数据分配唯一 ID。

**第二步：技术盲测（Hit Rate）**

- 目的：测试系统"海选打捞"阶段，看大网能不能网住标准答案。
- 让技术写脚本把 50 个问题输入混合检索系统，**只测海选打捞阶段**（如设置 K=20），先不让 Rerank 和大模型介入。
- 核对：数据库吐出的 20 条里是否包含第一步中的"黄金切片 ID"。
  - 命中（Hit）：输入"那个玩倒脚丝滑不"，20 条里包含 Doc_102。
  - 部分漏报：输入"带出门沉不沉"，20 条里只有 Doc_045，漏了 Doc_089。

**第三步：计算得分**

- 召回率（Hit Rate@K）= 成功把标准答案圈进大名单的问题数 / 总测试问题数（50 个）。
- 及格线：得分 **80% 以下**，说明系统经常"漏题"，上线后一定会频繁答非所问、疯狂胡诌。
- 商用线：经过 Query 改写、多模态洗、海选池 K 从 10 放大到 25 等优化后，召回率必须达到 **95%~98%**。

### 10.4 准确率 vs 召回率对照

| 维度 | 准确率 | 召回率 |
|---|---|---|
| 关注点 | 检索结果的正确性 | 检索结果的全面性 |
| 计算公式 | 正确检索数 / 总检索数 | 正确检索数 / 相关总数 |
| K 值影响 | K 增大，准确率降低 | K 增大，召回率提升 |
| 项目优先级 | 次要（可后续 rank 排序优化） | 核心目标（需优先保证） |

## 十一、如何支持多模态回复

### 11.1 接入多模态素材中心（项目六）

命中图片、视频等素材后，以「文字 + 图片 + 视频」**混排分条返回**，让语音/图文客服具备多模态应答能力。

实现原理：图片和视频的存储结构与文字一致——**商品信息 + 描述向量化，只是额外多一个 URL 字段**。

- 返回给前端的是 **URL**，而不是直接解析图片或视频内容；
- 通过文字描述备注去命中，不是解析图片或视频本身。

### 11.2 多模态检索流程

1. **意图识别**：判断用户需要文字、图片还是视频回复；
2. **Query 改写**：对用户查询改写，提升检索命中率；
3. **向量检索**：通过向量数据库（ANN）分别检索文字、图片、视频。

### 11.3 返回前端

- 多模态素材中心命中后，返回 URL 字段，前端根据 URL 加载图片或视频资源；
- 文字、图片、视频**分条混排**返回，用户看到的是图文并茂的富媒体回复。
- 素材中心的统一应答策略：文字必发、图 ≤3、视频 ≤1，阈值递增（text 0.35 < image 0.40 < video 0.42）。

## 十二、LLM 全链路性能优化（核心亮点）

### 12.1 总成果

**首字延迟（TTFT）从 15s 优化到 2s（甚至 1.5s）。**

优化收益拆解：

| 措施 | 说明 | 延迟变化 |
|---|---|---|
| Prompt Cache 自然生效 | 相同前缀多次调用，KV Cache 逐渐命中 | 15s → 10s |
| 模型选型 | 从 doubao-seed-1.6 切换到 flash 轻量版，速度优先，准确率仅降 2% | 10s → 6~7s |
| 开启深度思考 | 平台对深度思考请求分配更好的 GPU，排队更少 | 6~7s → 更低 |
| 知识库风格与人设风格统一 | 减少模型"风格转换推理"，直接复用知识库原文 | 7s → 2s |
| System Prompt 合并为 1 条 | 将人设 + RAG 结果合并到一条 system 消息 | 2s → 1.5s |

### 12.2 逐项优化措施

**① 提示词缓存（Prompt Cache）**

- 原理：利用固定前缀（系统提示词）+ 不常变化 + 经常变化三部分拆分，充分利用 KV Cache。
- 关键点：**系统提示词建议只写一条，不要搞多条**。

**② 模型选型策略**

- 意图识别用更轻量的模型（如 lite）；
- 回复生成用 flash 模型，无需上旗舰模型；
- 原因：用户提问基本限定在特定范围内，轻量模型足以应对；客服场景回复基于话术稿，不需要复杂推理。

**③ 关闭深度思考**

- 客服场景基于话术稿回复，不需要逻辑推理，关闭深度思考可提升性能。

**④ 知识库风格与人设风格统一**

- 系统提示词风格必须与知识库的话术风格保持一致；
- 原因：风格不一致会导致模型"人格分裂"，影响性能和回复质量。

**⑤ 提示词合并（把多条 system 消息合并成一条）**

- 错误写法：把系统定义、RAG 检索结果等写成多条独立的 system 消息。
- 正确写法：在 Python 后端通过字符串拼接，将 `base_role` 和 `rag_context` 合并成一条庞大的 system 消息。
- 原因：在火山引擎的底层缓存机制中，多条独立的 system 消息会被切成不同数据块，高并发时容易导致缓存扫描算法混乱，判定"前缀不一致"，使 Prompt Cache 无法触发。
- 效果：合并后消息列表只有一条 system 消息 + 一条用户提问，更好地利用前缀缓存，延迟从 2s 降至 1.5s。

**⑥ 固定 RAG 检索片段排序**

- 核心问题：用户提问的微小差异（如"大专可以学吗" vs "专科可以学吗"）会导致向量检索结果排序不稳定，破坏前缀缓存。
- 解决方案：放弃基于语义相似度评分的排序，改用**固定排序**（如首字母排序、数据库 ID 排序）。
- 原因解释：
  - 即使检索出的 Top N 数据完全相同，排序变化也会导致前缀缓存失效；
  - 大模型会自行判断所有检索结果的相关性，**排序顺序不影响最终回复质量**（举例：检索"张飞与吕布的关系"，即使把包含正确答案的片段排在最后，大模型依然能正确识别并回答）。
- 易错点：不要担心低分数据排到前面，因为所有 Top N 数据都会完整交给大模型处理。

**⑦ Temperature 设置**

| 环节 | temperature | 理由 |
|---|---|---|
| 意图识别 | **0** | 完全死板，不允许任何创造力，只做精准分类 |
| 客服回复 | **0.3** | 平衡准确性与自然对话感；0 太机械，0.3 兼顾数据准确和口语化表达 |

**⑧ Max Token 分级控制（软硬双重限制）**

- 软性限制（系统提示词）：在 Prompt 中引导回复长度，如"回复不要超过 200 字"。
- 硬性限制（代码层）：设置 `max_tokens=800` 作保底，防止模型输出过长内容造成截断并降低延迟。
- 作用：缩短回复长度能显著降低延迟、提升响应速度。

**⑨ 流式输出 stream=True**

- 大模型边生成边输出，不等全部生成完毕；
- 配合 TTS（语音合成）可实现"边收边读"，大幅降低用户感知的首字延迟。

**⑩ 回复多段（像真人聊天）**

- 目标：模拟真人聊天习惯，把回复拆成多条短消息发送，提升交互体验。
- 实现原理：大模型只调用一次，但回复内容用分隔符（如 `\n`）拆成多段；服务端根据分隔符通过 **SSE（Server-Sent Events）分多次推送给前端**。
- 举例：用户问"我们去哪吃饭？"，AI 回复内容为"你想吃啥？\n我觉得 xixi 家的火锅不错\n梦想哥家的泡面也不错，我想吃泡面"，前端显示为三条独立消息。
- Prompt 设计：在系统提示词中明确要求"你的回复，帮我用分隔符拆开"。
- 关键点：大模型只调用一次，但用户看到多条消息，感觉回复"更快、更自然"。

### 12.3 核心优化点清单（一页纸版本）

- 提示词缓存：固定 + 不常变化 + 经常变化
- 模型选型：意图识别用 lite，回复用 flash
- LLM 设置：关闭深度思考
- 风格统一：知识库风格与人设风格统一
- 提示词合并：人设与 RAG 结果合并到一条 system 消息
- RAG 排序：固定检索片段排序，按首字母排序
- 参数设置：temperature 设 0.3，Max Token 分级控制
- 流式输出：开启 stream=True，实现 TTS 边收边读

### 12.4 "如何保持语义同时提升专有名词命中率"的回答策略

不要只回答"降维 + 精简 Limit"这一条，应把**整个项目的架构和流程全部展开**：数据来源 → 检索方案 → 多模态应答 → 语音优化 → LLM 推理优化 → RTC 链路优化 → Prompt 管理 → 模型接入。目的不是凑字数，而是在面试中充分展示技术栈与项目广度，让面试官看到你对整个系统的掌控能力。

## 十二·补、简历里那些"讲义没讲透"的词：口径与解释

简历里有几个词在 44 份讲义中没有直接展开，被追问的概率很高，这里给出**材料内的依据**与**安全的解释口径**（不额外编造实现细节，只做口径对齐）。

### 补充 1：自定义标识符切片（解决语义截断）

- **材料依据**：课件里出现在"RAG 优化"的高频表述中——"采用自定义标识符切片解决语义截断"（讲义 02、03、04 的项目亮点里重复出现）。
- **同源口径**：项目五参考资料写"按 **Markdown 标题层级 + 段落边界**语义切分"；项目六写"按 **ASR 时间戳**分段"。
- **安全解释**：本质是**不用固定字数硬切**，而是按业务里天然存在的边界切块（标题/段落/轮次/时间戳），保证一块内容语义完整、不被拦腰截断。我们知识库是对话数据，所以按"一问一答/同一话题"这类标识符切。**不要说成"用了某个开源 splitter 的某个参数"这种具体到代码的说法**。

### 补充 2：HNSW_HYBRID 混合检索

- **材料依据**：简历/课件亮点表述"应用 **HNSW_HYBRID** 混合检索 + Int8 量化"。
- **背景知识（火山引擎 VikingDB）**：`hnsw_hybrid` 是**混合索引算法**，同时对数据集中的**稠密向量和稀疏向量**建索引，检索时返回兼顾两种相似性的结果；**前提是数据集里有** `sparse_vector` **字段**（例如用 **bge-m3** 把 text 字段转成稀疏向量）。距离类型只对稠密向量生效，稀疏向量仅支持内积。官方 int8 量化是把 4 字节 float 压成 1 字节，精度损失约 2~3%，换取性能提升。
- **安全解释**：如果被问"你们 pgvector 哪来的 HNSW_HYBRID"，标准回答是——**混合检索的检索侧我们是用 pgvector 的向量检索 + PostgreSQL 全文检索（**`ts_rank_cd`**/**`tsquery`**）加权融合来模拟的**；`HNSW_HYBRID` 是火山引擎向量库侧的索引类型名称，属于我们评估/迁移方案时对标的写法。见本文第四章 4.3~4.4 的 SQL 权重示例。

### 补充 3：存储空间降低 75% / 检索速度提升 4 倍

- **75% 的依据**：int8 量化把 float32 的 4 字节压成 1 字节，理论就是省 75%；
- **4 倍的依据**：课件原话是"针对语音场景通过降维 + 精简 Limit 策略，引入 base-rerank 轻量模型……检索速度提升 4 倍"。
- **注意**：讲义 09 的结论是"我们场景（约 2500 条）**不需要**降维和量化"。所以这两个数字**只有在"大数据量演进版/线上实测口径"下才讲得通**，见第六章的口径提示。

### 补充 4：Prompt Pilot 管理提示词

- **材料依据**：只出现在简历/课件表述里——"基于 Prompt Pilot 管理提示词，构建评测集实现自动化评分与版本对比；对负样本用智能优化算法做提示词重构，并将高质量样本回流数据中台沉淀"。
- **跨项目呼应**：项目五的"MCP Prompt 服务（YAML 定义参数 Schema、服务端渲染 PromptMessage、改模板即时生效）"就是**同一件事的工程实现**；项目四的"提示词分层治理/Prompt 管理"也是同族。
- **安全解释**：指的是**提示词版本化管理平台**——提示词有版本、有评测集、能对比版本效果、能把负样本回流优化，而不是在代码里硬编码字符串。被追问"是自己写的还是开源工具"时，答"我们自己基于 MCP Prompt 服务封装的模板中心 + 评测集做版本对比"最稳。

### 补充 5：Max Token 分级控制"按 95% 覆盖率边界"

- **材料依据**：简历原文；讲义的等价表述是"**软性限制（提示词引导回复不超过 200 字）+ 硬性限制（代码层** `max_tokens=800`**）**"，以及"缩短回复长度能显著降低延迟"。
- **安全解释**：把历史回复长度做个统计，95% 的回复在这个长度以内，就按这个边界配 `max_tokens` 兜底 + 提示词引导短回复；既防截断又不给过长的输出留预算。（"95% 覆盖率"是**业务统计口径**，不是模型里的某个参数。）

## 十三、RTC 语音链路优化（FEC + 自适应 Jitter Buffer）

> 面试要点："就是火山引擎 RTC 提供的能力，学会借势"。我其实只是开启了 RTC 的参数，默认开启。

### 13.1 FEC 前向纠错

- **核心问题**：实时语音通话（RTC）要求毫秒级同步，网络环境差（如 50% 丢包）会导致声音卡顿、断断续续。
- **传统做法（低效）**：客户端发现丢包后向服务器请求重传，一来一回耗时几百毫秒，用户体验极差。
- **FEC（前向纠错）机制（高效）**：服务器发送数据包时采用"买一送一"策略，在后续包中携带前面包的冗余备份。
  - 举例：一句话"联想拯救者"被拆成两个包：包1 = "联想"，包2 = "拯救者"；服务器发送包2时，包2 的内容是"联想拯救者"。
  - 即使包1 在传输中丢失，只要包2 到达客户端，客户端就能从包2 中提取出"联想"和"拯救者"，直接还原声音。
- **核心优势**：无需往返重传，靠提前多发备份，让客户端具备"自愈"能力；在 50% 丢包率内声音可完美还原。

### 13.2 自适应 Jitter Buffer

- **核心问题**：网络波动（如进入电梯、弱网环境）会导致数据包到达时间不稳定，造成声音"时快时慢"或卡顿。
- **机制**：在客户端建立一个"蓄水池"，不立即播放收到的每个包，而是**先缓存一段时间（如 30~50 毫秒）**，等收到多个包后再连续播放。
  - 生活类比：收快递时，不是收一个拆一个，而是等三五个包裹一起到再拆开，体验更流畅。
- **实现效果**：通过缓存平滑网络波动，消除声音的断续感。

### 13.3 结合 ASR 情绪识别 + TTS 情绪化合成

- 基于 ASR 实时捕获用户情感波动，配合 TTS 声音复刻实现情绪化回复。
- 火山引擎 ASR 服务可返回用户情绪参数（如发怒、平静、开心），**情绪参数直接用于大模型提示词**，如"用户很生气"。
- TTS 合成语音可带情绪，如激动语气"对呀，大专就是可以学呀"。

### 13.4 借势（面试话术）

- 优化项目不一定非要自己实现所有底层技术。使用火山引擎等成熟平台提供的 RTC 能力（FEC、Jitter Buffer），通过开启参数来优化项目，**同样是自己的成果**。
- 标准回答："我开启了火山引擎 RTC 的 XX 参数，实现了 FEC 前向纠错和自适应 Jitter Buffer，优化了语音链路的稳定性。"关键是能讲清两个机制的原理和作用。

| 对比项 | 传统方案 | 优化方案 | 优势 |
|---|---|---|---|
| 丢包处理 | 客户端请求重发（一来一回慢） | FEC 前向纠错（后包含前包） | 用户体验提升 |
| 网络波动应对 | 声音时快时慢、卡顿 | Jitter Buffer 缓存 30~50ms 后连续播放 | 流畅度提升 |
| 情绪处理 | 无情绪感知 | ASR 情绪参数 + TTS 情绪合成 | 回复更自然 |

## 十五、评测集：怎么把握 LLM 的回复质量

### 15.1 从单元测试到模型评测

| 类型 | 构成 | 说明 |
|---|---|---|
| 传统单元测试 | **2 元组**：输入 + 返回值 | 验证函数逻辑，如测一个加法函数，输入 2 和 3，预期输出 5；直接校验输入与返回值是否匹配 |
| 模型评测 | **3 元组**：输入 + 命中的 RAG + 输出 | 输入"我大专可以学吗？"；RAG 命中"大专可以学，案例1、案例2、案例3"；输出"可以学，我们有很多案例……" |

**关键前提**：评测必须基于有 log 的场景。如果没有 log，说明用的是通用大模型，这类模型的评测应由云厂商负责，无需自行评测——**不要对没有 log 的通用大模型做评测，这是无效操作**。

### 15.2 三个交织的维度（过程对了，结果才会对）

模型回复的准确性由三个维度共同决定：

1. **意图识别**（相对稳定）：判断下一步该问啥、Query 改写、回什么（文字/图片/视频）、固定套路引导；
2. **系统提示词**（相对死板）：回复风格（冷漠/热情）、精简程度、套路与策略（业务流程拆得更细，如"遇到用户问价格，统一引导给个联系方式""遇到用户上来就问多少钱，先塑造产品价值"）；
3. **RAG 检索**（频繁变动、数据量大）：核心是命中率、精准率和召回率。

> 类比：考试时小抄（RAG）有了，但笔（意图识别/系统提示词）没墨水，考试依然无法进行。**必须先稳定意图识别和系统提示词，再谈 RAG 检索的准确性。**

### 15.3 评测的核心：过程评测而非结果对比

- 不同大模型（豆包、千问）对同一问题的回复风格不同，直接对比输入输出没有意义。
- 类比：不同学生带同一份小抄考试，由于开放性问题，最终得分可能不同。
- **标准答案的本质不是构建输入输出的对应关系，而是构建过程标准**——为每个提问设定"参考答案"，即**期望命中的 RAG 数据 ID 列表**。
  - 举例：问"大专可以学吗？"，标准答案 = 必须命中 ID 10、11、12 这三条数据。
- 类比：微积分考试，标准答案不是最终分数，而是解题过程中用到的三个关键知识点。

### 15.4 完整评测流程（RAG 黄金数据集）

1. **写 50 条典型提问**，RAG 中有 500 条数据（黄金数据集），每个提问对应 10 条相关数据，每条 RAG 数据给一个唯一 ID。
2. **检索执行**：输入"大专可以学吗？" → TopK（10）→ Rerank TopN（3）→ 命中的 TopN ID 期望为 10、11、12 → 输出"大专可以学。"
3. **检查 TopN 是否包含预设的黄金 ID**；若命中错误，说明意图识别、系统提示词或 RAG 检索（如索引、量化）某个环节有问题。
4. **结果**：评测不是直接看输入输出，而是通过黄金数据集把控 RAG 检索的过程，确保命中的是期望的数据 ID。

### 15.5 LangGraph 工作流怎么评测：过程评测

- 用户："帮我生成一张鞋子的海报" → 调用 Agent A → 调用 Tools B → 调用 Agent C → 输出结果。
- 正确流程应该是 ABC；实际可能调用的是 ADBC（多了一步）、AABBCC（重复调用自己）、EFG（跑偏）。
- **业务流程黄金数据集**：用户提问 + 正确流程 ABC + 结果。提问 A 对应流程 ABC，提问 B 对应流程 EFG，构建这样的参考答案，不符合预期就去排查。
- **粒度控制**（先粗后细）：
  - 粗粒度：只看你调了 Agent A 没有；
  - 细粒度：看 Agent 内部调用的 RAG 是什么、参数是否正确。

| 维度 | 粗粒度评测 | 细粒度评测 |
|---|---|---|
| 关注点 | 是否调用正确 agent | agent 内部调用参数是否正确 |
| 工作量 | 较小 | 可能超过开发工作量 |
| 适用阶段 | 项目初期 | 项目成熟期 |
| 示例 | 检查流程是否为 ABC | 检查 agent A 调用的 R 参数是否正确 |

### 15.6 正确流程 vs 错误流程

| 对比项 | 正确流程（过程评测） | 错误流程（结果评测） | 关键差异 |
|---|---|---|---|
| 评测对象 | 过程（RAG 命中 ID） | 结果（输入输出文本） | 过程可控，结果受模型风格影响 |
| 数据集构建 | 黄金数据集（提问 + 指定 ID） | 直接匹配输入输出 | 黄金数据集有唯一参考答案 |
| 优化顺序 | 意图识别 → 系统提示词 → RAG 检索 | 直接优化 RAG | 基础不牢则 RAG 优化无效 |
| 模型影响 | 不同模型（豆包/千问）不影响过程评测 | 不同模型输出不同，无法统一标准 | 过程评测具有模型无关性 |

### 15.7 AI 测试工程师

- 模型评测是一个单独的岗位，叫 **AI 测试工程师**，对标传统的"测试开发"（懂代码的测试）。
- 工作量可能比开发还大，写单元测试花费的时间可能比开发本身更繁琐。
- 作为 AI 应用开发工程师，掌握上述过程评测的核心思路（黄金数据集、过程把控）就完全够用。
- 抓主要矛盾：意图识别、系统提示词校验、RAG 检索准确 → 结果无大误差。

## 十七、高频面试问答速记

**Q1：你们知识库有多少条数据？**
A：微信原始脏数据 10 万条（5 个销售合并，人均 2 万），机器清洗剩 2 万，人工清洗剩 2000，人工补充 100~200 条，最终 2000~2500 条，对应 20~30 款商品，平均每款约 100 条。构建 RAG 导出后还会人工审核一遍。

**Q2：为什么用 PostgreSQL + pgvector 而不是专用向量库？**
A：数据量小（2500 条、10MB 量级），PG 事务和 pgvector 够用；混合检索可以用 SQL 的权重系数自由调配，灵活；专用向量库配置简单但权重调节是封装参数。缺点是 PG 需要自己实现 dense_weight 的模拟。

**Q3：稠密和稀疏有什么区别？**
A：稠密是语义检索，不依赖字面；稀疏是神经网络分析关键词权重，用高权重词做全文检索，能区分重点——"我大专可以学 AI 吗"重点是"大专"和"AI"，不是"早上吃了一碗面"。

**Q4：为什么一定要 Rerank？**
A：三个痛点——LLM 迷失在中间；数据库打分粗暴会把噪声排前面；多模态素材算分不公平。混合检索负责"海选查缺补漏"，Rerank 用 Cross-Encoder 通读上下文做"终审"。

**Q5：K 和 N 是什么？**
A：K 是检索出的候选数量（如 15），N 是最终喂给 LLM 的数量（如 3），中间过程叫 Rerank。

**Q6：要不要降维/Int8 量化？**
A：不需要。2500 条 × 1024 维 float32 ≈ 10MB，降维等于查询降智，量化损失精度。数据到千万级才需要考虑。

**Q7：数据频繁变动怎么办？**
A：用 HNSW 而不是 IVFFlat（IVF 像抽屉，变动要重建索引），并做动静分离——商品信息（sku_id、描述、特点）放一张表，价格库存（sku_id、价格、库存）放另一张表。

**Q8：高并发怎么扛？**
A：四招——sku_id 先过滤再检索；Redis 相似度缓存（95% 命中，缓存 Top N，TTL 5 分钟到 1 天）；LLM 轻量 + RPM 扩容/多账号负载均衡；预设 tag 写死 KV 缓存。

**Q9：怎么提升召回率？**
A：Query 改写（最关键，把口语/指代/情绪改写成标准查询）、K 值调优（K=10 够用，海选可以放到 25）、混合检索。

**Q10：怎么统计召回率？**
A：黄金数据集 50 问 + 每条 RAG 数据唯一 ID + 人工标注标准答案 ID → 只测海选阶段（K=20）→ 召回率 = 命中标准答案的提问数 / 50。及格线 80%，商用线 95%~98%。

**Q11：TTFT 怎么从 15s 降到 2s？**
A：Prompt Cache 15→10s、换 flash 10→6~7s、开深度思考更低、风格统一 7→2s、system prompt 合并 2→1.5s；另外还有固定 RAG 排序、temperature 0.3、max_tokens=800、stream=True、多段 SSE。

**Q12：多条 system 消息为什么反而更慢？**
A：火山引擎底层缓存会把多条独立 system 消息切成不同数据块，高并发时缓存扫描算法混乱，判定"前缀不一致"，Prompt Cache 触发不了。所以在后端把 base_role 和 rag_context 拼成一条。

**Q13：用户提问差一个字，缓存就失效？**
A：是。"大专可以学吗"和"专科可以学吗"向量检索结果排序可能不同 → 前缀不一致 → 缓存失效。所以放弃按相似度排序，改按首字母/ID 固定排序，反正所有 Top N 都会给大模型，大模型自己会判断相关性。

**Q14：RTC 的 FEC 和 Jitter Buffer 是你自己实现的吗？**
A：是火山引擎 RTC 提供的能力，我们开启参数并在链路中验证效果。FEC 是"买一送一"，后包带前包冗余，客户端能自愈；Jitter Buffer 是客户端"蓄水池"，先缓存 30~50ms 再连续播放，平滑网络抖动。

**Q15：怎么保证 LLM 回复质量？**
A：过程评测。三要素——意图识别、系统提示词、RAG；黄金数据集 50 问、每条数据唯一 ID，看命中 ID 是否与预设一致；LangGraph 流程用"业务流程黄金数据集"评测 ABC 是否被正确调用，粒度先粗后细。

**Q16：语音场景为什么要关深度思考？**
A：客服回复基于话术稿，不需要复杂逻辑推理，关掉能减少推理步骤、降低延迟。

## 十八、易混淆点自查

- K 是候选数，N 是最终数，**顺序不能反**。
- 混合检索是"海选"，Rerank 是"终审"，顺序不可颠倒。
- 准确率关注"对不对"，召回率关注"全不全"；本项目优先保召回率。
- Prompt 缓存要"固定 + 不常变化 + 经常变化"三段式，且 system prompt 只写一条。
- 意图识别在前，RAG 查询在后，不要搞反。
- 图片/视频是"转文字命中"，不是直接解析图片。
- dense_weight 不是 pgvector 原生参数，是自己用 SQL 权重模拟出来的（正经方案含该参数，pgvector 少这个，效果达 95%）。
