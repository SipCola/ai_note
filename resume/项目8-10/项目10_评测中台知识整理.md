# 项目 10｜Agent 自动化评测与监控中台 · 知识整理

原稿开头的六条简历亮点及后面的代码草稿见[项目 10 简历参考](./项目10简历参考.md)。本文整理原稿「需要整理的知识」部分。

## 1. 项目解决什么问题

电商 Agent 同时负责回答和执行操作。一句“已经帮你处理了”只能说明它说过什么。评测还要回答三个问题：它理解的是哪件商品，调用了什么工具，购物车最终发生了什么变化？把验收要求写成用例，将实际对话、工具记录和状态快照放在一起核对，换模型或修改提示词之后就能重跑同一道题。

数据中台把真实交互清洗成可复用的数据。评测中台从中挑出有代表性的成功、失败和边界场景，补齐初始条件及预期结果。模型版本会变，同一批有明确判分依据的用例可以跨版本比较。

## 2. 用一个加购场景理解评测

用户预算 300 元，已看到两款双肩包，随后说“把第二款加入购物车，数量一个”。第二款 P102 推荐时是 299 元，加购时沙箱中的现价是 349 元，库存为 8。

| 验收问题 | 核对什么 | 通过条件 |
| --- | --- | --- |
| 理解了“第二款”吗？ | 推荐顺序、查价工具参数 | 查的是 P102 |
| 用了最新价格吗？ | 查价工具返回值、最终回复 | 依据 349 元判断超出 300 元预算 |
| 有没有尝试加购？ | 工具调用记录 | 加购调用为 0 次 |
| 购物车真的没变吗？ | 运行前后快照 | U001 的购物车仍为空，U002 原有的 P104 数量仍为 1 |
| 有没有如实告知用户？ | 最终回复与执行记录 | 说明涨价超预算、本次未加购，未擅自接受新价格或替换商品 |

**为什么既查调用，又查快照？** 如果 Agent 违规调用了加购工具，工具恰好报错，购物车也会保持原样。只比快照就会把错误决策判为通过。反过来，最终回复即使很得体，也不能抵消一次真实的错误写入。

## 3. 七个维度怎么选

原稿先列出平台关注的七类问题，又针对购物车举了七项具体检查。两份清单的粒度不同。设计用例时先确定这次要验证的业务行为，再选适用指标。

| 平台维度 | 可用的证据与判法 |
| --- | --- |
| 最终结果 | 对照用户目标、最终回复和实际状态。超预算时，正确阻止加购也算完成任务。 |
| RAG 检索 | 用标注的相关切片 ID 对照召回结果。召回率看找回了多少相关切片，准确率看返回的切片中有多少相关。只有明确要求集合完全一致时，多一条也判失败。 |
| 证据使用 | 比对最终回复中的商品、价格或政策与实际工具返回、检索片段，检查是否引用了过期信息。 |
| Agent 过程 | 核对指代解析、工具名、参数、顺序和业务约束。购物车案例重点检查目标商品和加购次数。 |
| 稳定性与异常 | 模拟涨价、缺货、优惠券失效或工具报错，核对是否停止错误操作并向用户说明原因。 |
| 成本与效率 | 从本次运行读取 Token、耗时和调用轮次，按场景预算判定或告警。 |
| 安全与权限 | 检查工具参数中的用户身份、其他用户状态和回复中的敏感内容。核心安全用例要求全部通过。 |

购物车示例按**任务结果、工具调用、上下文记忆、业务规则、异常处理、成本效率、安全合规**出分。历史推荐已在对话中给定，这个用例重点测“第二款”的解析和实时查价。要测 RAG 召回，还需提供预期切片 ID 和本次检索记录。

## 4. 五层架构与一次运行

| 层次 | 文件或目录 | 每层交付什么 |
| --- | --- | --- |
| 配置 | configs/ | 业务提示词约束 Agent 的行为，裁判提示词定义语义检查及输出格式。 |
| 用例数据 | testcases/ | 一条用例保存 case_id、input（身份与对话）、setup（初始状态）、expected（可核验的期望）。 |
| Mock 隔离 | mock_server/ | 按 setup 重置商品、库存和各用户购物车。相同场景重跑时从相同起点出发。 |
| 维度评估 | evaluators/ | 读取 expected 和本次 Trace，按选定维度输出状态、指标及依据。 |
| 调度与报告 | runner.py、reporter.py、main.py | 选择单例或递归加载用例，调用业务 Agent API，收集记录并生成详情和汇总。 |

**执行顺序**：选用例 → 重置沙箱并保存初始快照 → 将用户身份和对话发给 Agent → 收集回复、工具参数及结果、耗时、Token 和结束快照 → 判分 → 汇总报告。业务接口需要返回或关联到这次请求的 Trace。缺少工具日志时，对应检查应标记证据缺失，否则空列表容易被误读成“调用次数为零”。

## 5. 怎样判分，怎样复用裁判

1. **代码断言核实事实。** 对商品 ID、金额、工具次数和购物车快照做精确比较。金额沿用原稿的“分”作为单位，预算为 30000，现价为 34900。
2. **轻量模型判断语义。** 将本例验收要求、相关 Trace 和最终回复交给裁判，要求按检查项返回 id、status、reason。例如“这款现在 349 元，超出预算，我先没加”和“商品已涨价到 349 元，本次未加购”都符合要求。
3. **旗舰模型或人工复核疑难项。** 轻量裁判报错、结论含糊或多轮证据冲突时再升级。语义评分和确定性断言分别留存，复核时能看出争议来自哪项检查。

简历中的“80% 代码断言 + 20% LLM 裁判”是原稿给出的混合判定口径。原稿示例中的关键词匹配用于演示语义检查，示例 Token 和时延也是模拟值。讨论实际运行占比或成本时，需要对应批次的判定记录。

扩充到 100+ 条用例时，业务规则、判分逻辑及报告格式可以共享。新增用例主要填写 **input、setup、expected**。例如缺货用例可继续使用“加购调用次数为 0”的断言，把库存设为 0，并将预期回复改成说明缺货。测试工作量主要花在构造边界、控制沙箱初值和审核标准答案。原稿的“一天开发、一周写用例”属于示例估算。

## 6. 报告、门禁与失败样本回流

| 什么时候跑 | 看什么 | 如何处理 |
| --- | --- | --- |
| 本地调整提示词、工具或检索逻辑后 | 单例详情中的输入、调用、前后快照和裁判理由 | 定位失败环节，重跑受影响用例 |
| PR / MR 合入前 | 总用例数、通过率、分维度失败数、核心安全用例结果 | 核心安全用例须 100% 通过。总体通过率下限按业务设定，原稿中的 90% 为示例 |
| 夜间全量回归 | 与历史批次对比，关注相同用例在新模型或依赖变更后的表现 | 从变化最大的场景回查单例 Trace |
| 线上出现 Badcase 后 | 脱敏对话、触发条件、错误动作及正确预期 | 固化成 JSON 用例，先复现问题，再修复并加入后续回归 |

一次运行的汇总保存在 `outputs/run_xxx/summary_report.json`，单例详情位于 `outputs/run_xxx/details/`。汇总回答“这次能否合入”，详情回答“哪一步偏离预期”。除了线上失败样本，还可以从调试会话录制用例，或根据业务文档生成候选场景，经人工确认后纳入评测集。

## 7. 演示入口与开发方法

原稿给出的演示入口位于[项目仓库](https://codeup.aliyun.com/6a10331c5c14c6ef0af5df51/ai_test)。以下保留原稿配置，尚未在本次整理中运行。

```dotenv
ARK_API_KEY=replace_with_your_local_key
ARK_MODEL=doubao-seed-2-1-lite-260915
```

在仓库根目录配置好 .env 后，原稿的启动命令为：

```powershell
python -B .\examples\seven_dimensions\server.py --port 8765
```

原稿中的演示分三次迭代：先跑通评测，再展示执行过程，最后在界面上显示每个检查项的要求与指标。改用 Spec 驱动开发时，可把“第二款涨价”写成第一条验收场景，先核对预算、初始价格和预期工具次数，再按沙箱、Trace、评估器和报告的顺序实现。这样每一步都有可检查的产物。
