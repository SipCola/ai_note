# 刘伟臣十个项目面试介绍话术

> 面试官说「先做个自我介绍」，可以这样开场。下面的项目标题和编号用来对照简历，口述时接着段落讲就行。

面试官你好，我叫刘伟臣，现在在江苏健汲网络科技做 AI 应用开发。我先简单讲一下我们公司的业务。我们是给微信社群、私域直播和团购渠道供货的，主要做保健品和滋补品。比如一个团购渠道要上新，我们这边除了供货，还要给他们商品规格、包装图和直播讲解素材。

我刚进公司的时候做全栈，主要在做商品、SKU、包装版本和渠道素材相关的接口，也跟运营一起联调后台。后来转到 AI 应用开发，我负责搭建公司的 AI 应用体系，主要做架构设计、核心链路开发和上线验证。我们当时想解决的都是日常问题。客户在群里问某款商品有什么规格、还有没有货，导购得查资料。直播讲解过这个商品，运营还得去回放里找片段。我可以从这个售前场景讲起，顺着介绍一下我们这十个项目是怎么接起来的。

> 面试官点头后，从客户在群里问商品这个场景往下讲。

## 项目五 保健品与滋补品私域售前咨询 Agent

我先讲售前咨询 Agent。比如客户说「上次团购的那款还有吗」，这里其实有两个问题，得先弄清楚是哪款，再查现在有没有货。碰到同名商品有不同规格，Agent 会先问清楚是哪一个 SKU，再按对应版本做 RAG 检索，查商品资料。可供库存就调库存工具，确认之后再引导客户下单。我们也接了实时语音。语音里等十几秒，客户就容易以为断了，所以我们固定了检索片段的排序、合并提示词来提高前缀缓存的复用，把复杂 RAG 场景的首字延迟从 15 秒压到了 2 秒以内。

## 项目二 保健品与滋补品私域 AI 数据资产中台

那客服用的这些知识从哪儿来？一部分就来自我们自己在微信社群和团购业务里的真实咨询。比如同一个规格问题，客户的问法可能有十几种，群里也会夹着闲聊和个人信息。我们就做了 AI 数据资产中台，把聊天记录导进来，做会话切分、去重、过滤和脱敏，再交给业务人员审核。审核通过的数据可以提成问答给客服做检索，也可以保留多轮上下文给后面的模型微调。导购考核的题目和参考答案，用的也是这里沉淀下来的知识。

## 项目七 多模态知识库与商品素材管控中心

客服能回答文字之后，客户也会问「新版包装长什么样」「有主播讲过这个规格吗」。我们就做了商品素材中心，把商品详情、包装图和直播讲解视频按商品关联起来。为了让一句话能搜到图和视频，我们先给素材建一段可检索的描述，图片补上识别出的文字和画面信息，视频补上转写摘要和时间戳。这样客服回复时，可以把规格说明和对应的包装图一起发过去。命中直播讲解的话，客户点开就能跳到主播讲这款商品的位置。

## 项目六 私域内容运营与多阶段内容生成 Agent

素材中心里的图和介绍，有一部分来自内容运营 Agent。比如一款商品要上团购，运营经常要准备商品介绍、推广文案和配图。我们用 LangGraph 把选题、写文案、配图拆成几个步骤，中间状态存到 PostgreSQL。配图出错，就从那一步接着跑，已经写好的文案可以保留。生成内容走人工审稿，商品图按商品编号进入素材中心，后面客服也能搜到。

## 项目八 私域直播切片与音视频处理 Agent

素材中心里还有一类内容是直播讲解。运营想找某个商品的介绍，以前要在几小时的回放里一点点拖进度条。我们做了直播切片 Agent，先在浏览器用 FFmpeg.wasm 提取音频。以一个 2.5 GB 的回放文件为例，上传的音频大约只有 30 MB。服务端转写之后，让模型按时间轴找商品讲解和团购活动的片段，生成标题和文案。浏览器再按这些时间段批量裁切导出。切片关联到素材中心供客服调用，语音转写也会回到数据中台。

## 项目九 私域导购培训与智能考核 Agent

同一批商品知识和咨询记录还能用来带新人。比如新人来了，我们就让考核 Agent 从数据中台取审核过的资料，按难度出题。题目可以是「客户没说清楚买的是哪个规格，问你能不能跟这次团购一起下单，你会怎么回？」新人直接用自己的话作答，模型再看有没有问清楚需求、销售策略合不合适、说法自然不自然、有没有踩业务红线，给出分数。业务人员也可以复核这些评分。

## 项目十 基于私域导购对话的销售模型微调

真实咨询对话还有一个用处，就是教客服怎么说话。商品规格和活动信息随时会更新，我们继续用 RAG 查资料。多轮对话里的表达方式，比如怎么追问、怎么把两个规格讲清楚，我们用数据中台审核过的样本做 SFT。先在本地用小模型跑一轮验证数据，再到火山方舟对豆包做 LoRA 微调。我们请人做了盲评，话术风格一致性从 2.1 分提到 4.3 分，满分是 5 分。微调后的模型接回了实时语音客服。我们还规划了 DPO 这一步，让销售主管对同一个问题的几种答法标偏好。

## 项目三 私域商品咨询的 Harness 与 Agent Loop 引擎

客服还得处理这种问题。比如客户说「这两款包装有什么区别，哪款还有货」，就得结合上下文判断具体是哪两款，再决定调哪些工具。为此我们做了 Harness，也就是 Agent 的运行时。模型在循环里选工具，拿到结果再决定下一步，规格和库存查询也可以并行发起。如果工具报错，会把错误结果回填给模型，超过步数或时间上限就转人工。业务专家还可以补充标准答法和原因，确认之后沉淀进提示词规则。下次客户换个说法问同类问题，这些规则也能用上。

## 项目一 Agent 自动化评测与监控中台

工具和模型都在变，那怎么知道改完以后，原来能处理的场景还好使？我们做了评测与监控中台。比如 Agent 查库存的时候传的 SKU 对不对，加购之后购物车状态对不对，这些用代码断言。回复有没有理解客户的意思、有没有按业务口径解释，这类开放题就交给分级的模型裁判。改模型或提示词可以批量跑一百多条用例，核心安全用例必须全过才能合入。线上如果发现 Agent 把新版包装答成了旧版，我们就顺着 Trace 看是哪一步出错，把这条对话固化成用例，修完再跑一遍。

## 项目四 私域渠道 Agent 分层治理网关与 AI 研发效能提升

最后讲一下这些应用怎么一起维护。客服、内容生成、直播切片都会调模型，有些还要查商品和库存。我们把供应商接入、模型路由、工具执行权限、质量评测、协议接入收在一套分层治理平台里。像商品和库存查询就通过 MCP 做成共享能力，实际执行由平台校验权限。换模型时在网关调路由，再用评测中台按场景跑回归。我们试过按不同场景分配模型，整体质量持平，模型成本下来了 30%。

研发协作这块也用了同一套回归机制。比如要改库存查询，我们先在实现规格里约定哪些字段必须校验、查不到怎么处理。实现规格和代码放在同一个 PR，独立的任务可以开不同的 git worktree 并行做。提交之后先跑自动化门禁和 AI 初审，再由人看业务规则和架构。改提示词也会跑一遍对应的 Agent 评测。
